# 2026-10-06 · wxpush 推送通道集成

## 本轮做了什么

把 wxpush（Cloudflare Workers 上的公众号模板消息推送服务）集成进项目，
并推翻 PRD v0.2 里「不采用测试号推送」的结论，升级为 **v0.2.1**。

### 关键判断转变

v0.2 的判断：测试号推送「消息跳不回小程序 + 无品牌感」→ 不采用。
本轮推翻，因为：

1. 模板消息 payload **支持 `miniprogram` 字段**，配置后点击直达小程序
2. 即使不生效，还有**中转页 + 小程序码长按识别**兜底
3. 它换来的是「**无限次推送 + 能推给别人**」—— 正好补上产品最大短板

## 核实到的硬事实（别再想当然）

| 事实 | 结论 |
| --- | --- |
| URL Link（`wxaurl.cn`） | ❌ **官方明确「针对非个人主体小程序开放」**，且必须小程序已发布。个人主体不可用 |
| `wx-open-launch-weapp` 开放标签 | ❌ 需认证公众号 + JSSDK，测试号不具备 |
| 小程序码（长按识别） | ✅ 个人主体可用 —— **中转页跳小程序的主力手段** |
| 测试号能否关联小程序 | ❌ 无关联入口 → `miniprogram` 字段大概率不生效（假设 A6，待实测） |

> 教训：网上大量「公众号跳小程序」教程用的是 URL Link / 开放标签，**对个人主体都不通**。

## 单位决策：用 px 不用 rpx ⭐（用户提问触发）

用户问「为什么用 px 而不是 rpx」。查证微信官方 WXSS 文档后发现**官方立场与社区习惯相反**：

> rpx 有取整精度问题；现在优先推荐 `vw`；
> **不建议滥用 `vw` `rpx` 等基于屏幕宽度比例的单位**（要考虑 PC / 大屏）。

结论：**本项目统一用 px**，理由四条（已写入 docs/07 §5.2）：
1. 小程序也跑在 iPad / 微信 PC 端，750rpx 恒等于屏宽 → 大屏上元素失控放大
2. 家庭工具，物理尺寸一致比等比缩放更重要（375pt 手机上的按钮，换 430pt 不该变大）
3. 设计基调是留白，px 在大屏只会更空不会挤破
4. 避开官方点名的 rpx 取整误差

代价：大屏上内容占比变小 → 对策 `.page { max-width: 480px; margin: 0 auto; }`（已实现，手机端不受影响）。

## 三、⭐ 时区方案推翻重做（本轮最重要的判断）

原文档（`AGENTS.md` §4.3 / `docs/01` §4.3）写着：

> `DATABASE_URL` 必须带 `timezone=+08:00`，否则 Prisma 写入的 DATETIME 会差 8 小时。

**这条是错的。** 查证 `prisma/orm#29517`（2026-04 open，至今未实现）确认：
**Prisma 的 MySQL 连接器不支持连接串里的 `timezone` 参数**，会被静默忽略。
它固定按 UTC 处理 DATETIME：

| 操作 | 实际行为 |
| --- | --- |
| 写 `new Date()` / `@default(now())` | 按 UTC 格式化，作为绑定参数发出 |
| 读 DATETIME | 把库里的串**无条件当作 UTC**，构造带 Z 的 Date |
| DATETIME 列本身 | 原样存墙钟串，**不随会话 `time_zone` 转换** |

所以「应用写 → Prisma 读」自洽；**但绕过 Prisma 写入的数据会差 8 小时** ——
而原方案里 MySQL 容器设的是 `+08:00`，`DEFAULT CURRENT_TIMESTAMP` 正好会踩这个坑。

**新方案：存储层统一 UTC，北京时间只在接口层格式化一次。**

| 层 | 约定 |
| --- | --- |
| 存储 | UTC（顺着 Prisma，不对抗 ORM） |
| MySQL 会话时区 | `+00:00`（docker-compose 已改） |
| 时间戳来源 | Prisma 侧 `@default(now())` / `@updatedAt`，不用 `dbgenerated` |
| Node 进程 | `TZ=Asia/Shanghai`（本地 getter 直接得北京时间） |
| 接口输出 | `common/serialize/beijing-time.ts` |

产品目标（用户只看北京时间、业务代码不做换算）**不变**，只是把换算从
「存储层用本地时间」改成「收敛到一个函数」。
代价：直连数据库看数据时时间是 UTC，比北京时间少 8 小时。

已同步修正：`AGENTS.md` / `docs/01` / `docs/04` / `docs/06` / `docs/08` /
PRD §27.5 / `db/schema.sql` / `docker-compose.yml` / `server/.env(.example)`。

### 22.2 新发现的沙箱硬限制：Node 无法创建子进程（EBUSY）

**这是本次最有价值的发现，比脚本本身更重要。**

现象：脚本最初用 `execFileSync('docker', ['exec','-i','family-things-mysql','mysql',...])`
做数据库夹具，全部报：

```
Error: spawnSync C:\Program Files\Docker\Docker\resources\bin\docker.exe EBUSY
```

排查（4 种调用方式全部失败，见下表）后确认根因不是 docker：

| 探测项 | 结果 |
| --- | --- |
| `execFileSync(process.execPath, ['-v'])` | ❌ EBUSY |
| `execFileSync('cmd', ['/c','echo','hi'])` | ❌ EBUSY |
| `execSync('echo hi')` | ❌ EBUSY |
| `spawnSync(docker, ['--version'])` | ❌ EBUSY |
| `require('@prisma/client')` | ✅ OK |

结论：**WorkBuddy 沙箱 hook 了 Node 的 `child_process`，任何子进程创建都直接
EBUSY —— 连 Node 自己启动自己都不行。** 但 `Bash` 工具（bash.exe）起 docker 正常，
说明限制只作用于**当前 Node 进程的 spawn**，不是程序黑名单。

解法：**数据库夹具改走 Prisma Client。**
Prisma 6 默认用 **N-API library 引擎**（`engineType = "library"`），在进程内跑，
不 spawn `query-engine.exe`，所以在沙箱里依然能连库读写。

> 推论（以后写脚本都用得上）：**在这台机器上，Node 脚本想碰外部系统，
> 只能走「进程内协议」—— HTTP、Prisma(N-API)、Redis 客户端。
> 任何 `exec` / `spawn` / `execSync` 都会被 EBUSY 拦掉。**

### 23.2 最重要的工程决策：小程序端不能引 shared 的运行时值

**官方依据**（`developers.weixin.qq.com/miniprogram/dev/devtools/compilets.html`）：

> 目前的 ts 代码转换成 js 代码的逻辑，是由 `@babel/plugin-transform-typescript`
> 插件进行处理的，因此在编译过程中，**仅仅是移除了 ts 代码中类型声明等信息**。

即**只做类型擦除，不解析 `tsconfig.json` 的 `paths`**。于是：

| 写法 | 结果 |
| --- | --- |
| `import type { ApiResponse } from '@shared/dto/common'` | 整条被擦除 → 运行时安全 ✅ |
| `import { ErrorCode } from '@shared'` | 保留 `require('@shared')` → 运行时 `MODULE_NOT_FOUND` ❌ |

**落地方式**：
1. 类型照常从 `@shared` 引（`import type`），`tsc --noEmit` 用真实 tsconfig，paths 生效
2. 运行时常量在 `miniprogram/constants/` 下**重新定义镜像**
3. 镜像用 `as const` 对象而不是 `enum` —— Babel 的 TS 插件默认不转换 `enum`
4. `tools/check-shared.mjs` 逐个成员比对防漂移，已接入 `pnpm check`

已写进 `docs/04 §5.2`（硬规则）。

> 备选方案（**未采用**）：把 shared 编译成 JS 走「构建 npm」。
> 放弃原因：需要用户多一步手动操作（微信开发者工具里点「构建 npm」），
> 且 pnpm 的 symlink 结构与微信构建 npm 有兼容风险，而我在沙箱里**无法验证**。

## 27. M2-B9 文本内容安全（msgSecCheck）完成

### 27.1 最重要的实测结论（推翻了一个担忧）

**个人主体小程序可以调用 `security.msgSecCheck`** —— 没有 48001「api unauthorized」。
之前担心「个人主体可能没这个接口权限」，实测不成立。

用 `node tools/probe-seccheck.mjs` 实测（真实 openid `oiRGc7…bw8Q`，库里 id=5）：

| 输入 | 微信原始返回 |
| --- | --- |
| `明天记得买牛奶和鸡蛋` | `{"errcode":0,"result":{"suggest":"pass","label":100}}` |
| `澳门线上博彩娱乐城 真人荷官 点击开户` | `{"errcode":0,"result":{"suggest":"risky","label":20006}}` |

响应结构（v2）：
```json
{
  "errcode": 0, "errmsg": "ok",
  "detail": [
    { "strategy": "keyword", "errcode": 0 },
    { "strategy": "content_model", "errcode": 0, "suggest": "pass", "label": 100, "prob": 90 }
  ],
  "trace_id": "6ac4cc88-…",
  "result": { "suggest": "pass", "label": 100 }
}
```
- 结论看 `result.suggest`（`pass` / `review` / `risky`）
- `detail[]` 是分策略的明细，排查误判时有用
- 老接口形态用 `errcode=87014` 表示违规，**两种都要认**

### 27.2 架构决定：唯一的策略点

`server/src/modules/wechat/content-security.service.ts`

| 微信结论 | 处理 |
| --- | --- |
| `risky` | **拦**，抛 40002 |
| `review` | 放行 + 记日志（家庭场景没有人工复核队列，拦了就是永久损失） |
| `pass` | 放行 |
| 判不了（网络 / 凭证 / 接口未开通） | **放行** + 记 warn（**fail-open**） |

**为什么必须有这一层**：`msgSecCheck` 只回答「判成什么」，
而「判不了时放不放行」是个**产品判断**，必须只写一遍 ——
否则今天这里放行、明天那里拦截，就成了随机行为。

**fail-open 的理由**：微信抖一下就让「阿妈，记得买牛奶」发不出去，
家里人只会觉得小程序坏了；而 V0.1 是自用、没有公开传播面，违规内容实际风险为零。
⚠️ 公开传播场景（V1.0 若有分享 / 广场）要重新评估。

### 27.3 两个工程细节

1. **检测超时设 3 秒**（其他微信接口 8 秒）：检测在「创建一条小事」的**同步路径**上，
   微信慢 8 秒用户就干等 8 秒。检测是辅助能力，不值得让家人等。
   `WechatService.request()` 因此加了可选 `timeoutMs` 参数。
2. **接入点三处，都在写库之前**：
   - 创建小事：标题 + 说明**并发**检测（串行会白等一次往返）
   - 编辑小事：**只测本次真改了的字段**
   - 叮一下（不带 thingId 那条）：正文取 `content`
   带 `thingId` 的 nudge 不改内容 → 不检测，不做无用的微信调用。

3. 开关 `CONTENT_SECURITY_ENABLED`，**默认开**，只有显式 `false` 才关。
   生产必须 true（审核硬性要求）；本地关掉只是为了不被超时拖慢。

### 27.4 冒烟的诚实边界（别被「全绿」骗了）

冒烟 176 项仍全通过，但**验的是 fail-open 路径**：夹具 openid 是造的假值
（`smoke_xxx`）→ 微信必回 40003 → 走「判不了 → 放行」。

所以冒烟只能保证「不误拦、不阻塞」，**验不了「违规被拦」**。
已在冒烟脚本的观察项里写明。

**怎么确认链路真的被调用**（避免假绿）：跑完冒烟看服务日志，
本次实测出现 **24 条** `[ContentSecurityService] 内容安全判不了，放行`，

### 28.3 三个踩点 / 判断

1. **`skipped` 必须与 `failed` 分开**：「小事已完成 / 接收人已退出」是正常跳过。

3. **`client_msg_id` 是微信侧的 24 小时去重键** —— 补偿重发必须换成 `log-{id}-r1`，

5. **单位陷阱**：`RedisTtl.CRON_LOCK` 是**秒**（300），`acquireLock(key, ttlMs)` 收**毫秒**。

几百毫秒，再 `Promise.all` 并发打 3 次 → 后两次必然撞上锁。
断言三条：至少一次 `locked=true`、被挡住的那次 `scanned=0`、没被挡住的正常扫到。

### 29.2 六条设计判断（写进 docs/05 了，这里记「为什么」）

1. **组件一律不读 store、不发请求。** P08 叮谁要排除自己、P09 派给谁要把自己

6. **23:30 点「今天」时（now+2h 跨到明天）切到「指定」**，而不是显示

### 31.3 本仓库第一个行为断言工具（值得记住的做法）

**动机**：`buildThingDetailView()` 全是纯函数但分支多（3 种状态 × 我是执行人 /
我是发起人 / 都与我无关 × 有没有提醒），而 `tsc` 只能保证**类型**对，
保证不了「不限时间前完成」这种**语法通顺但意思错**的文案。

**写它的当天就抓到一个真 bug**：`describeDue()` 出来是「明天 18:00」，
直接拼「前完成」少了空格 → 「明天 18:00前完成」，与 docs/03 的
「明天 18:00 前完成」不一致。**38 项里红了一项**，说明断言真的在比。

**实现要点（两个坑，都踩过了）**：
- 小程序端是 TS，node 不能直接 require → 用仓库里已有的 `typescript`
  把 `miniprogram/` 编到**系统临时目录**再 require 产物。**不新增依赖**，
  也不往仓库里写产物（`mkdtempSync(tmpdir())` + 结尾 `rmSync`）。
- **不要 spawn `tsc`**：本机执行环境会拦子进程 —— `node_modules/.bin/tsc.cmd`
  报 `spawnSync EINVAL`（Windows 上 `.cmd` 的经典问题），换成
  `process.execPath` + `lib/tsc.js` 又报 `EBUSY`。
  → 改用 **TypeScript 编译器 API 在进程内编译**：
  `ts.readConfigFile` → `ts.parseJsonConfigFileContent` → `ts.createProgram` → `program.emit()`。
  既不依赖 shell，也省一次进程启动（全程 3.4s）。
- 产物路径是 `<out>/miniprogram/utils/thing-view.js`（不是 `<out>/utils/...`）：
  tsconfig 的 `include` 含 `../packages/shared/src`，tsc 推断 `rootDir` 为仓库根。

### 31.4 一个刻意的产品判断：后端的「创建者兜底」不露出

服务端 `complete` / `cancel` / `reopen` 都允许**家庭创建者**越过
「执行人 / 发起人」身份直接操作（`thing.service.ts` 的 `ctx.isOwner`）。
那是防止一件事因执行人退出家庭而永远卡住的**数据阀门**，不是产品要主推的动作 ——
「只提醒，不监督」意味着不该把「我替你点完成」摆在手边。

所以界面只认「我是执行人 / 我是发起人」。**代价**：极少见的死锁
（发起人与执行人都已不在这个家庭时，创建者打开 P10 什么都做不了）。
已记入 `docs/未来需求池.md`，**并写明修复时不要把权限判断搬到前端**。
