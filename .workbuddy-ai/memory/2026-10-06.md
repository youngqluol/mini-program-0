# 2026-10-06 · wxpush 推送通道集成

## 本轮做了什么

把 wxpush（Cloudflare Workers 上的公众号模板消息推送服务）集成进项目，
并推翻 PRD v0.2 里「不采用测试号推送」的结论，升级为 **v0.2.1**。

### 关键判断转变

v0.2 的判断：测试号推送「消息跳不回小程序 + 无品牌感」→ 不采用。
本轮推翻，因为：

1. 模板消息 payload **支持 `miniprogram` 字段**，配置后点击直达小程序
2. 即使不生效，还有**中转页 + 小程序码长按识别**兜底
3. 它换来的是「**无限次推送 + 能推给别人**」—— 正好补上产品最大短板

## 核实到的硬事实（别再想当然）

| 事实 | 结论 |
| --- | --- |
| URL Link（`wxaurl.cn`） | ❌ **官方明确「针对非个人主体小程序开放」**，且必须小程序已发布。个人主体不可用 |
| `wx-open-launch-weapp` 开放标签 | ❌ 需认证公众号 + JSSDK，测试号不具备 |
| 小程序码（长按识别） | ✅ 个人主体可用 —— **中转页跳小程序的主力手段** |
| 测试号能否关联小程序 | ❌ 无关联入口 → `miniprogram` 字段大概率不生效（假设 A6，待实测） |

> 教训：网上大量「公众号跳小程序」教程用的是 URL Link / 开放标签，**对个人主体都不通**。

## 单位决策：用 px 不用 rpx ⭐（用户提问触发）

用户问「为什么用 px 而不是 rpx」。查证微信官方 WXSS 文档后发现**官方立场与社区习惯相反**：

> rpx 有取整精度问题；现在优先推荐 `vw`；
> **不建议滥用 `vw` `rpx` 等基于屏幕宽度比例的单位**（要考虑 PC / 大屏）。

结论：**本项目统一用 px**，理由四条（已写入 docs/07 §5.2）：
1. 小程序也跑在 iPad / 微信 PC 端，750rpx 恒等于屏宽 → 大屏上元素失控放大
2. 家庭工具，物理尺寸一致比等比缩放更重要（375pt 手机上的按钮，换 430pt 不该变大）
3. 设计基调是留白，px 在大屏只会更空不会挤破
4. 避开官方点名的 rpx 取整误差

代价：大屏上内容占比变小 → 对策 `.page { max-width: 480px; margin: 0 auto; }`（已实现，手机端不受影响）。

## 三、⭐ 时区方案推翻重做（本轮最重要的判断）

原文档（`AGENTS.md` §4.3 / `docs/01` §4.3）写着：

> `DATABASE_URL` 必须带 `timezone=+08:00`，否则 Prisma 写入的 DATETIME 会差 8 小时。

**这条是错的。** 查证 `prisma/orm#29517`（2026-04 open，至今未实现）确认：
**Prisma 的 MySQL 连接器不支持连接串里的 `timezone` 参数**，会被静默忽略。
它固定按 UTC 处理 DATETIME：

| 操作 | 实际行为 |
| --- | --- |
| 写 `new Date()` / `@default(now())` | 按 UTC 格式化，作为绑定参数发出 |
| 读 DATETIME | 把库里的串**无条件当作 UTC**，构造带 Z 的 Date |
| DATETIME 列本身 | 原样存墙钟串，**不随会话 `time_zone` 转换** |

所以「应用写 → Prisma 读」自洽；**但绕过 Prisma 写入的数据会差 8 小时** ——
而原方案里 MySQL 容器设的是 `+08:00`，`DEFAULT CURRENT_TIMESTAMP` 正好会踩这个坑。

**新方案：存储层统一 UTC，北京时间只在接口层格式化一次。**

| 层 | 约定 |
| --- | --- |
| 存储 | UTC（顺着 Prisma，不对抗 ORM） |
| MySQL 会话时区 | `+00:00`（docker-compose 已改） |
| 时间戳来源 | Prisma 侧 `@default(now())` / `@updatedAt`，不用 `dbgenerated` |
| Node 进程 | `TZ=Asia/Shanghai`（本地 getter 直接得北京时间） |
| 接口输出 | `common/serialize/beijing-time.ts` |

产品目标（用户只看北京时间、业务代码不做换算）**不变**，只是把换算从
「存储层用本地时间」改成「收敛到一个函数」。
代价：直连数据库看数据时时间是 UTC，比北京时间少 8 小时。

已同步修正：`AGENTS.md` / `docs/01` / `docs/04` / `docs/06` / `docs/08` /
PRD §27.5 / `db/schema.sql` / `docker-compose.yml` / `server/.env(.example)`。

### 22.2 新发现的沙箱硬限制：Node 无法创建子进程（EBUSY）

**这是本次最有价值的发现，比脚本本身更重要。**

现象：脚本最初用 `execFileSync('docker', ['exec','-i','family-things-mysql','mysql',...])`
做数据库夹具，全部报：

```
Error: spawnSync C:\Program Files\Docker\Docker\resources\bin\docker.exe EBUSY
```

排查（4 种调用方式全部失败，见下表）后确认根因不是 docker：

| 探测项 | 结果 |
| --- | --- |
| `execFileSync(process.execPath, ['-v'])` | ❌ EBUSY |
| `execFileSync('cmd', ['/c','echo','hi'])` | ❌ EBUSY |
| `execSync('echo hi')` | ❌ EBUSY |
| `spawnSync(docker, ['--version'])` | ❌ EBUSY |
| `require('@prisma/client')` | ✅ OK |

结论：**WorkBuddy 沙箱 hook 了 Node 的 `child_process`，任何子进程创建都直接
EBUSY —— 连 Node 自己启动自己都不行。** 但 `Bash` 工具（bash.exe）起 docker 正常，
说明限制只作用于**当前 Node 进程的 spawn**，不是程序黑名单。

解法：**数据库夹具改走 Prisma Client。**
Prisma 6 默认用 **N-API library 引擎**（`engineType = "library"`），在进程内跑，
不 spawn `query-engine.exe`，所以在沙箱里依然能连库读写。

> 推论（以后写脚本都用得上）：**在这台机器上，Node 脚本想碰外部系统，
> 只能走「进程内协议」—— HTTP、Prisma(N-API)、Redis 客户端。
> 任何 `exec` / `spawn` / `execSync` 都会被 EBUSY 拦掉。**

### 23.2 最重要的工程决策：小程序端不能引 shared 的运行时值

**官方依据**（`developers.weixin.qq.com/miniprogram/dev/devtools/compilets.html`）：

> 目前的 ts 代码转换成 js 代码的逻辑，是由 `@babel/plugin-transform-typescript`
> 插件进行处理的，因此在编译过程中，**仅仅是移除了 ts 代码中类型声明等信息**。

即**只做类型擦除，不解析 `tsconfig.json` 的 `paths`**。于是：

| 写法 | 结果 |
| --- | --- |
| `import type { ApiResponse } from '@shared/dto/common'` | 整条被擦除 → 运行时安全 ✅ |
| `import { ErrorCode } from '@shared'` | 保留 `require('@shared')` → 运行时 `MODULE_NOT_FOUND` ❌ |

**落地方式**：
1. 类型照常从 `@shared` 引（`import type`），`tsc --noEmit` 用真实 tsconfig，paths 生效
2. 运行时常量在 `miniprogram/constants/` 下**重新定义镜像**
3. 镜像用 `as const` 对象而不是 `enum` —— Babel 的 TS 插件默认不转换 `enum`
4. `tools/check-shared.mjs` 逐个成员比对防漂移，已接入 `pnpm check`

已写进 `docs/04 §5.2`（硬规则）。

> 备选方案（**未采用**）：把 shared 编译成 JS 走「构建 npm」。
> 放弃原因：需要用户多一步手动操作（微信开发者工具里点「构建 npm」），
> 且 pnpm 的 symlink 结构与微信构建 npm 有兼容风险，而我在沙箱里**无法验证**。

## 27. M2-B9 文本内容安全（msgSecCheck）完成

### 27.1 最重要的实测结论（推翻了一个担忧）

**个人主体小程序可以调用 `security.msgSecCheck`** —— 没有 48001「api unauthorized」。
之前担心「个人主体可能没这个接口权限」，实测不成立。

用 `node tools/probe-seccheck.mjs` 实测（真实 openid `oiRGc7…bw8Q`，库里 id=5）：

| 输入 | 微信原始返回 |
| --- | --- |
| `明天记得买牛奶和鸡蛋` | `{"errcode":0,"result":{"suggest":"pass","label":100}}` |
| `澳门线上博彩娱乐城 真人荷官 点击开户` | `{"errcode":0,"result":{"suggest":"risky","label":20006}}` |

响应结构（v2）：
```json
{
  "errcode": 0, "errmsg": "ok",
  "detail": [
    { "strategy": "keyword", "errcode": 0 },
    { "strategy": "content_model", "errcode": 0, "suggest": "pass", "label": 100, "prob": 90 }
  ],
  "trace_id": "6ac4cc88-…",
  "result": { "suggest": "pass", "label": 100 }
}
```
- 结论看 `result.suggest`（`pass` / `review` / `risky`）
- `detail[]` 是分策略的明细，排查误判时有用
- 老接口形态用 `errcode=87014` 表示违规，**两种都要认**

### 27.2 架构决定：唯一的策略点

`server/src/modules/wechat/content-security.service.ts`

| 微信结论 | 处理 |
| --- | --- |
| `risky` | **拦**，抛 40002 |
| `review` | 放行 + 记日志（家庭场景没有人工复核队列，拦了就是永久损失） |
| `pass` | 放行 |
| 判不了（网络 / 凭证 / 接口未开通） | **放行** + 记 warn（**fail-open**） |

**为什么必须有这一层**：`msgSecCheck` 只回答「判成什么」，
而「判不了时放不放行」是个**产品判断**，必须只写一遍 ——
否则今天这里放行、明天那里拦截，就成了随机行为。

**fail-open 的理由**：微信抖一下就让「阿妈，记得买牛奶」发不出去，
家里人只会觉得小程序坏了；而 V0.1 是自用、没有公开传播面，违规内容实际风险为零。
⚠️ 公开传播场景（V1.0 若有分享 / 广场）要重新评估。

### 27.3 两个工程细节

1. **检测超时设 3 秒**（其他微信接口 8 秒）：检测在「创建一条小事」的**同步路径**上，
   微信慢 8 秒用户就干等 8 秒。检测是辅助能力，不值得让家人等。
   `WechatService.request()` 因此加了可选 `timeoutMs` 参数。
2. **接入点三处，都在写库之前**：
   - 创建小事：标题 + 说明**并发**检测（串行会白等一次往返）
   - 编辑小事：**只测本次真改了的字段**
   - 叮一下（不带 thingId 那条）：正文取 `content`
   带 `thingId` 的 nudge 不改内容 → 不检测，不做无用的微信调用。

3. 开关 `CONTENT_SECURITY_ENABLED`，**默认开**，只有显式 `false` 才关。
   生产必须 true（审核硬性要求）；本地关掉只是为了不被超时拖慢。

### 27.4 冒烟的诚实边界（别被「全绿」骗了）

冒烟 176 项仍全通过，但**验的是 fail-open 路径**：夹具 openid 是造的假值
（`smoke_xxx`）→ 微信必回 40003 → 走「判不了 → 放行」。

所以冒烟只能保证「不误拦、不阻塞」，**验不了「违规被拦」**。
已在冒烟脚本的观察项里写明。

**怎么确认链路真的被调用**（避免假绿）：跑完冒烟看服务日志，
本次实测出现 **24 条** `[ContentSecurityService] 内容安全判不了，放行`，

### 28.3 三个踩点 / 判断

1. **`skipped` 必须与 `failed` 分开**：「小事已完成 / 接收人已退出」是正常跳过。

3. **`client_msg_id` 是微信侧的 24 小时去重键** —— 补偿重发必须换成 `log-{id}-r1`，

5. **单位陷阱**：`RedisTtl.CRON_LOCK` 是**秒**（300），`acquireLock(key, ttlMs)` 收**毫秒**。

几百毫秒，再 `Promise.all` 并发打 3 次 → 后两次必然撞上锁。
断言三条：至少一次 `locked=true`、被挡住的那次 `scanned=0`、没被挡住的正常扫到。

**动机**：`buildThingDetailView()` 全是纯函数但分支多（3 种状态 × 我是执行人 /
我是发起人 / 都与我无关 × 有没有提醒），而 `tsc` 只能保证**类型**对，

**写它的当天就抓到一个真 bug**：`describeDue()` 出来是「明天 18:00」，
直接拼「前完成」少了空格 → 「明天 18:00前完成」，与 docs/03 的
「明天 18:00 前完成」不一致。**38 项里红了一项**，说明断言真的在比。

**实现要点（两个坑，都踩过了）**：
- 小程序端是 TS，node 不能直接 require → 用仓库里已有的 `typescript`
  把 `miniprogram/` 编到**系统临时目录**再 require 产物。**不新增依赖**，
  也不往仓库里写产物（`mkdtempSync(tmpdir())` + 结尾 `rmSync`）。
- **不要 spawn `tsc`**：本机执行环境会拦子进程 —— `node_modules/.bin/tsc.cmd`
  报 `spawnSync EINVAL`（Windows 上 `.cmd` 的经典问题），换成
  `process.execPath` + `lib/tsc.js` 又报 `EBUSY`。
  → 改用 **TypeScript 编译器 API 在进程内编译**：
  `ts.readConfigFile` → `ts.parseJsonConfigFileContent` → `ts.createProgram` → `program.emit()`。
  既不依赖 shell，也省一次进程启动（全程 3.4s）。
- 产物路径是 `<out>/miniprogram/utils/thing-view.js`（不是 `<out>/utils/...`）：
  tsconfig 的 `include` 含 `../packages/shared/src`，tsc 推断 `rootDir` 为仓库根。

### 32.1 新增第 5 个共用组件 `swipe-cell`（左滑露出操作）

三个设计点（都是「必须由组件负责、页面做不了」的）：

1. **横滑与竖滚要仲裁。** 手指斜着划时得先判出用户到底想滚列表还是想滑开这一行。
   判据：**位移先超过 `AXIS_THRESHOLD = 6px` 的那个方向**。判成纵向就彻底不管，
   把滚动还给页面。
   → 所以用 `bindtouchmove` 而**不是** `catchtouchmove`：后者会吃掉事件，
   列表就再也滚不动了；宁可让横滑时列表轻微跟动一下。
2. **同一时刻只允许开一行** → 「哪一行开着」由**页面**持有（`openId`），
   组件只回答「我这一行该不该开着」——**受控组件**。
   否则每行各自记状态，开第二行时没人关第一行，最后满屏都是开着的抽屉。
3. **`actions` 为空就完全不响应手势。** 抽屉宽度是算出来的
   （操作个数 × `ACTION_WIDTH`），空数组直接得 0，手势也提前返回。
   → 语义是「这一行**不可滑**」，不是「滑开一个空抽屉」。

**踩到的坑**：手势中间态（`touchStartX/Y`、`touchStartOffset`、`touchAxis`）
**不能挂 `this.xxx`** —— 小程序组件的 TS 类型里没有自定义实例字段的位置
（项目里也没有任何 `Component<...>` 泛型用法可参考）。放进 `data` 里，
它们不参与渲染，多两次 setData 的代价可忽略。

⚠️ **`ACTION_WIDTH = 84` 是 ts 与 wxss 的跨文件耦合**：
`.swipe__action { width: 84px }` 必须与它一致，对不上就会出现
「滑到底了还露着一条白边」或「操作被裁掉一半」。

### 32.2 两个「过期响应」类的静默 bug（都是本轮想清楚的）

**① 列表请求的过期响应。** 快速连点两个 Tab 时，先发的那次可能**后到** ——
结果是「Tab 高亮着『都完成』，列表里却是『派给我的』」，而且**不报错**。
→ `reload()` / `loadMore()` 开头记下本次的筛选条件（`tab` + `statusIndex`），
响应回来用 `isStale()` 对一下，不一致就丢弃。
`loadMore` 还额外检查 `this.data.page !== next - 1`
（中间被一次 `reload` 接上了就别再往后拼）。

**② `reload()` 里不能加 `if (this.data.loading) return`。** 看起来能防重复请求，

## 33. P12 消息中心（M2-F13）

### 33.1 先修了一个后端 bug：通知的 title 是泛化短语

消息中心的列表**只显示 `title`**，而 `notify.templates.ts` 里的 `title` 原本写死成

用户只能挨个点进去看，**这一页等于白做**。

```ts
// 改前：TASK_ASSIGNED → '有个活儿到你啦'
// 改后：
title = withWhat(fromRoleName, '派了个活', thingTitle);  // 「阿妈 派了个活：买酱油」

function withWhat(from: string, action: string, what: string): string {
  const head = from ? `${from} ${action}` : action;
  return what ? `${head}：${what}` : head;
}
```
五个类型全改：`派了个活：X` / `提醒你：X` / `X 把「Y」弄好啦` / `欢迎加入「X」` / 事项名兜底。

**这不是新需求，是实现与设计不符** —— docs/02 §9.1 的示例 JSON 本来就是具体的。

**不碰推送字段**（推送走 `data` 里的 `first` / `keyword*`）。

> 教训：展示层字段的措辞属于**实现责任**，不是「先随便写、以后再说」。
> 列表只显示一个字段时，那个字段就必须能独立说明白一件事。

### 33.2 通知的元数据与展示模型

- `miniprogram/constants/notice.ts`（新增）：

    emoji 五种两两不同（🎯派活 / 🔔叮一下 / ❤️搞定了 / 🏠家庭 / 📢通知）+ `NOTICE_FALLBACK_META` 兜底。
  - `NOTICE_DELIVERY_TEXT: Record<NotificationItem['status'], string>` —— 六种文案。
  - `WECHAT_CHANNELS = ['MP_TEMPLATE', 'SUBSCRIBE']`。
- `miniprogram/utils/notice-view.ts`（新增）：`buildNoticeView(item): NoticeView`。
  **`deliveryText` 空串 = 正常推到微信了，页面据此不显示标签**。

**最关键的一条判断（有专门断言）：必须同时看 `channel` 和 `status`。**
`SENT` 只说明「这次发送成功了」，而 `channel === 'IN_APP'` 的 `SENT`
意思是「只写进了站内」—— 只看 `status` 会把「只在小程序里」说成「已发到微信」，
是一句**安静的假话**：
```ts
function deliveryTextOf(item: NotificationItem): string {
  if (item.status === 'SENT' && WECHAT_CHANNELS.includes(item.channel)) return '';
  return NOTICE_DELIVERY_TEXT[item.status] ?? '只在小程序里';
}
```

**文案纪律**：「站内」是禁用词（AGENTS.md §6），所以 `IN_APP + SENT` 说成

所以 `NOT_BOUND` 说成「还没开微信提醒」。

### 33.3 时间文案的第三个出口

`miniprogram/utils/time.ts` 新增 `describeMoment()`，并让 `describeDue()` 复用它：

| 函数 | 用在 | 输出 |
| --- | --- | --- |
| `describeMoment(value)` | 单独出现、要定位是哪天 | 「今天 17:30」 |
| `shortMoment(value, base?)` | 成对出现（开始/截止） | 「17:30」 |
| `describeDue(value \| null)` | 要求完成时间、可为空 | 「不限时间」 |

```ts
export function describeMoment(value: string): string {
  const day = describeDay(value);
  if (!day) return '';
  const time = hhmmOf(value);
  return time ? `${day} ${time}` : day;
}
export function describeDue(value: string | null): string {
  if (!value) return '不限时间';
  return describeMoment(value) || '不限时间';
}
```
> iOS 不认 `new Date('2026-10-06 12:00:00')`，`describeMoment` 内部走的
> `parseBeijingTime` 已经换过斜杠，别再自己 `new Date`。

## 34. P20「我的」Tab（M2-F2）

### 34.1 底部 Tab 不补图标（一个明确的取舍）

`app.json` 的 `tabBar.list` 四项都只有 `text`，没有 `iconPath`。
微信允许纯文字 tabBar，所以这是合法的。**本轮不补图标**，理由：
- 要补就得往仓库里放 8 张 PNG（选中 / 未选中各 4 张），而 `miniprogram/assets/` 至今是空的
  （`docs/04` 里标着「⏳ 尚未使用（插画与图标目前都用 emoji）」）。
- 视觉规范（docs/07）的风格是「emoji 装粉彩 squircle 色块」，换成线性图标是**另一套视觉语言**，
  不该顺手引入。
- 这是**打磨**，不是**通路**。V0.1 的验收标准是「4 个 Tab 都能切换，未读角标正常」。

### 34.2 角标：三个容易漏的点

```ts
const MINE_TAB_INDEX = 3;   // app.json tabBar.list 第 4 项

export function syncUnreadBadge(count: number): void {
  const badge = buildUnreadBadge(count);
  const quiet = { fail: (): void => undefined };
  if (badge.show) wx.setTabBarBadge({ index: MINE_TAB_INDEX, text: badge.text, ...quiet });
  else wx.removeTabBarBadge({ index: MINE_TAB_INDEX, ...quiet });
}
```

1. **`0` 条要显式 `removeTabBarBadge`。** 只调 `setTabBarBadge` 的话，角标会一直停在
   最后一个数字上 —— 用户看完消息回到「我的」，还挂着一个「3」。
2. **超过 99 说「99+」。** 微信的 tabBar 角标**最多显示 4 个字符**，再多会截成
   「前 3 个字符 + …」。与其让微信把「128」截成一个看不懂的东西，不如自己先说「很多」。
   数字一律 **`Math.floor` 向下取整** —— 2.7 条未读显示成 3 条是**凭空多报**。
3. **只在「我的」的 `onShow` 里刷。** 我的未读数只会因为**别人**做了事而变化，
   本地没有任何触发点 —— 想实时只能轮询，不值当。

**`MINE_TAB_INDEX = 3` 与 `app.json` 是跨文件耦合，而且是「静默失败」那一类** ——
挂错 Tab **不报错、不白屏**，只是红点出现在「留个念」上。
→ `tools/check-mp.mjs` 新增**检查项 ⑩**：解析 `utils/tab-badge.ts` 里的
`MINE_TAB_INDEX`，与 `app.json` 的 `tabBar.list.findIndex(pagePath === 'pages/mine/index')`
比对。**已反向验证**（改成 2 → 脚本报错）。

### 34.3 `utils/` 拆成两半：纯函数 vs 有副作用

### 34.4 抬头：不把称谓说两遍

昵称授权（`chooseAvatar` + `input type="nickname"`）还没做，`AuthUser.nickname`
**一直是 null**，所以大字那行实际就是家庭称谓。此时小字那行如果照原稿写
「在我们家 · 阿爸」，就成了「阿爸 / 在我们家 · 阿爸」—— 读起来像卡带。

```ts
const shown = nickname || family.roleName;
const roleLine = shown === family.roleName
  ? `在${family.familyName}`                     // 大字已经是称谓 → 只说家庭
  : `在${family.familyName} · ${family.roleName}`; // 有真昵称 → 家庭 + 称谓
```
昵称补上后自动恢复成原稿的样子。**昵称和称谓恰好相同**（用户微信名就叫「阿爸」）
也走同一条分支，不会重复。

### 34.6 两个请求各自独立失败

const [detail, unread] = await Promise.all([

| | 公众号二维码 | 小程序码 |
| --- | --- | --- |
| 长相 | 方形二维码 + 中间头像 | 放射状圆码 + **右下角绿色小程序角标** |

| wxpush 中转页要的 | ❌ | ✅ 长按识别跳回小程序 |
| 本项目位置 | `miniprogram/assets/mp-account-qr.jpg` | `wxpush/assets/miniprogram-code.png` |

肉眼很容易混。

> 这一对的判据是**角标**。共同点：**都比对不出名字**，只能看「实际长什么样」。

**小程序码为什么放 `wxpush/` 而不是 `miniprogram/assets/`：**

`MP_QRCODE_URL` 要的却是**小程序码** —— 沿用这个名字会把这个坑埋得更深。
所以入库名是 `miniprogram-code.png`。

### 35.2 「扩展名是常量的一部分」—— 又一个静默失败

P21 落地时 `MP_ACCOUNT_QR` 写的是 `'assets/mp-account-qr.png'`，但**那个文件不存在**
（图片得人工从公众号后台下载）。页面靠 `<image binderror>` 降级成一句文字说明 ——
**不报错、不白屏**，`check-mp.mjs` 输出末尾那行 `⏳` 就是在提示这件事。

用户实际给的是 `.jpg`。**没有转码**，直接把常量改成 `.jpg`：
转 PNG 只会放大体积，并不会把 JPEG 已经丢掉的信息找回来（QR 的纠错能力完全够用）。

⚠️ **代价：扩展名成了常量的一部分。** 换格式要**连常量一起改** —— 改漏了不会报错，
只会静默退回文字说明。这是「上线后才发现」那一类问题，所以在
`config.ts` / `docs/03` / `docs/04` / `docs/05` 四处都写了同一句话。

**`check-mp.mjs` 检查项 ⑪ 读的是常量本身**（正则从 `config.ts` 里抓），
不是写死的文件名 —— 所以这次只改常量，检查自动跟上，`⏳` 提示自行消失（已验证）。

### 35.3 P21 页面的四个实现取舍

1. **只在「还没开、手里又没有还没过期的数字」时才生成新数字。**
   `POST /notify/mp-bind/code` 会**换掉**正在展示的那一串，而用户此刻可能正拿着它
   在微信里打字 —— 一进页面就换码会把他的操作作废。
   所以 `onShow` 只重新**查**状态（`GET status` 会带回还在有效期内的那一串），不碰数字。
2. **轮询用「查一次、再排下一次」，不用 `setInterval`。** 查询本身是异步的，
   固定间隔会在网络慢的时候叠起好几个并发请求，而且**停不掉正在飞的那一个**。
   句柄 `pollTimer` / `pollCount` 挂在 `this` 上（不参与渲染，不进 `data`）。
3. **`onHide` / `onUnload` 必须停轮询。** 不停的话，用户切走后定时器还在跑，
   1 分钟后会 `setData` 到一个已经不可见的页面，期间还每 3 秒白打一次接口。
   配套：`onShow` 回来时立刻重查一次。
4. **不做「重新绑定」。** docs/03 草图里有这一行，但它没有真实语义：绑定关系挂在
   **用户**身上，换一个微信号就是换一个人。**已从 docs/03 删掉** ——
   挂一个点不出结果的入口，比不挂更糟（M2-F3、P20 那三行同一个判断）。

**文案：** 六位数字按 **3+3 分组**（「735 241」）。用户要做的事是
「看着屏幕、在微信里把这串数字打出来」—— 一长串连读容易念错，也容易看串行。

### 35.4 `describeExpire()` 补「分钟」档 —— 一个共用函数

它原来只有小时 / 天两档，而绑定码只活 **10 分钟** —— 会说成「1 小时内过期」，等于没说。
补上分钟档后：`< 1 小时` → 「n 分钟后过期」，且 **不足 1 分钟也说「1 分钟」**
（说「0 分钟」等于说已经没了）。

⚠️ **这个函数 P15（邀请码 72 小时）也在用**，所以改动必须**一起钉住** ——
断言里有 5 项，覆盖三档边界。

### 35.5 本轮新踩的三个坑

**① TS 字面量类型：`export const MP_ACCOUNT_QR = '...'` 会被推断成字面量类型。**

```text
error TS2367: This comparison appears to be unintentional because the types
'"assets/mp-account-qr.jpg"' and '""' have no overlap.
```

页面里 `MP_ACCOUNT_QR !== ''` 被判成「不可能成立」。**必须显式标 `: string`。**
注释写在 `config.ts` 里了 —— 这个错很费解（明明是在判空，编译器说不可能）。

**② 断言里造「相对当前时间」的时刻，要留余量。**

`describeExpire()` **向下取整**。造出 `now + 9 分钟` 并丢掉秒（`...:00`）后，
到断言执行之间过去几毫秒，正好卡在整分钟边界 → 算成「8 分钟」，期望 9 实际 8。

修法：辅助函数改名 `expiresInMinutes(n)`，留 **+0.5 分钟**余量并保留秒。
另外「不到 1 分钟」那条要用 `expiresInMinutes(0)`，**不能用 `-1`** ——
`-1` 会变成「已经过期了」，测的就不是同一档了。

**③ `check-mp.mjs` 的正则要容忍类型标注。**

`/MP_ACCOUNT_QR\s*=\s*'([^']*)'/` 在加了 `: string` 之后抓不到 → 报「找不到定义」。
改成 `/MP_ACCOUNT_QR[^=\n]*=\s*['"]([^'"]*)['"]/`（容忍 `: string` 与双引号）。

### 36.1 ⚠️ 本轮最重要的发现：布尔查询参数被全局隐式转换吃掉

**这是项目级的地雷，不是 menu 模块的局部问题。**

`app.module.ts` 的全局 `ValidationPipe` 开了 **`enableImplicitConversion: true`**。
class-transformer 在 `PLAIN_TO_CLASS` 下的执行顺序是
**先隐式转换、后跑自定义 `@Transform`**：

```js
// class-transformer/cjs/TransformOperationExecutor.js
finalValue = this.transform(subSource, subValue, type, ...);      // ← 隐式转换
finalValue = this.applyCustomTransformations(finalValue, ...);    // ← @Transform
```

`boolean` 字段的 `design:type` 就是 `Boolean` → 查询串 `'false'` 先被
`Boolean('false')` 变成 **`true`**，`@Transform(toQueryBoolean)` 才拿到这个布尔值
（函数里 `typeof === 'boolean'` 直接原样返回），**原始字符串已经丢了**。

**症状：`?excludeRecent=false` 静默等于 `true`。** 不报错、不抛异常、没有日志，
只有行为是错的；而且只在「显式传 false」时才暴露（不传时走默认值一切正常）。

**修法**：新增 `ParseBoolean()` 装饰器（`common/utils/query.util.ts`），
内部先 `@Type(() => String)` 把类型元数据改成 `String`（`@Type` 元数据优先级高于
隐式转换），再 `@Transform(toQueryBoolean)`。对 `null`/`undefined` 安全 ——
class-transformer 的标量分支显式 `if (value === null || value === undefined) return value;`。

**不能**直接删掉 `enableImplicitConversion`：项目里有一批数字字段
（`report-subscribe-quota.dto.ts` 的 `count`、`create-invite.dto.ts` 的 `expireInHours`、
`thing.dto.ts` 的 `pageSize` …）**没写 `@Type(() => Number)`**，正靠它把 `'5'` 转成 `5`，
关掉会让那些接口的 `@IsInt` 直接报错（M2 冒烟的 `pageSize=1` 就依赖它）。

**为什么之前没发现**：`toQueryBoolean` 是本轮新写的第一个布尔查询参数；
而且 M2 冒烟里没有任何布尔参数。**发现方式是写 M3 冒烟脚本时比对 `poolSize`** ——
如果用「这次抽到了什么」去断言，这个 bug 会被随机性掩盖。

已写进 `docs/04 §5.3`（含 class-transformer 源码行号）与 §十 自查清单。

### 37.1 `ThingService.create` 拆三段（本轮的架构动作）

原 `create` 是一坨：校验 + 内容安全网络往返 + 写库 + 通知全在一起。
拆成：

| 段 | 时机 | 干什么 |
| --- | --- | --- |
| `prepareThing(ctx, dto)` | **事务外** | 内容安全（网络往返）+ 校验 + 归一化 → `PreparedThing` |
| `insertThing(tx, ctx, prepared)` | **事务内** | 写 `family_things` + `thing_reminders` → `CreatedThing` |
| `dispatchCreatedThing(ctx, created)` | **提交后** | 派活通知 + 立即叮 |

`create` = prepare → `$transaction(insertThing)` → dispatch。
`decideAndAssign` = prepare → `$transaction([writeMealRecords, insertThing])` → dispatch。
**两处共用同一套 `prepare` / `insert` / `dispatch`**，所以「派活」和「直接创建小事」
产出的东西形状一致 —— 冒烟逐字段比对了键集合，**完全一致**。

⚠️ **为什么内容安全必须在事务外**：它是网络往返（微信接口），docs/02 §6.8 明令
「事务里不做网络调用」。代价见 37.4。

### 37.2 `PATCH /menu/items/:id` 不挂守卫（与小事模块同一模式）

`FamilyMemberGuard` 靠 URL / body 里的 `familyId` 拿家庭上下文，而这两个 PATCH
路由里**都没有** `familyId`。挂上去的结果是守卫直接判「缺少家庭信息」→ 18 项断言全挂。

改用**由资源反查家庭**：`MenuService.contextForItem(userId, itemId)` 先查菜谱拿
`familyId`，再校验调用者是该家庭成员。与 `ThingService.contextForThing` 同一模式。

失败语义（**照搬 contextForThing**）：
- 资源不存在 → **40400**
- 资源存在但不是你家 → **40300**（不是 40400 —— 不涉及隐私内容，给准确原因更好排查）

### 37.3 同家庭菜名唯一（40900）

菜名是池子里的唯一标识（系统菜谱没有 `id`，接口上 `id` 恒为 `null`）。
同家庭重名 → 随机连出同名菜 + 「排除最近吃过的」一次误伤两道。

两道防线：
1. 写入前 `assertNameFree(familyId, name, exceptId?)` → 40900
2. `buildPool()` **按菜名去重，家庭版覆盖系统版**

### 39.3 ⭐ COS 不引 SDK，且签名**可以自检**（本轮最值钱的一条）

### 39.4 图片类型与宽高：服务端自己解析文件头

`image-meta.ts`，零依赖，只认三种魔术字节：PNG 签名 / JPEG 的 `FFD8` / RIFF+WEBP。

- **类型判断直接决定「允不允许存进桶里」**，所以不能信客户端的 `Content-Type`
  （把 `.exe` 改名成 `.png` 是零成本的）。
- **宽高也由服务端读**（进 `memory_attachments` 供九宫格占位）。让客户端上报
  等于把布局交给客户端，一张错报 10000×10000 能把页面撑爆。
- 解不出来时给 `null`（两列本来就允许 NULL），**不编造、也不拒绝上传**。
- JPEG 要**逐段扫描**才能找到 SOFn（前面可能有 EXIF / 缩略图 / 注释），
  而且 SOFn 里**高在前、宽在后** —— 自检夹具里故意放了带 EXIF 段的样本
  （SOF 不在最前面）与各种截断 / 长度非法的输入。

### 39.5 multer 的取舍（为什么手搓 multipart 是错的）

`FileInterceptor` + `memoryStorage()`，只加了 `multer` + `@types/multer` 两个依赖。

**关键理由**：multer 的 `limits.fileSize` 在**流式解析时**就中止超限上传，
而手搓的 `Request.formData()` 会先把整个大文件读进内存 —— 那是个 DoS 面。

两个连带结论：
- 业务层**不再重复判 5MB**（multer 已在上游中止，再判一次是永远走不到的死代码）；
- 413 由 `AllExceptionsFilter` 归一到 40001 并**换成中文**
  （multer 带的是英文 `File too large`，会原样漏给用户）。

⚠️ `@nestjs/common` **已经导出了一个叫 `UploadedFile` 的装饰器** ——
自定义类型不能叫这个名字，会 `Duplicate identifier`。本轮踩到，改成
`UploadedImageFile`。

### 39.6 `img_sec_check` 是 1.0 版（微信 2021-09 起停止维护）

仍用它的理由：它是**唯一同步**的图片检测接口，能塞进「发布留念」这条同步路径。
异步的 `mediaCheckAsync` 要传公网可达的图片 URL、结果几秒后经消息推送回调回来，
意味着「发布」得变成「先发出去、后判、判违规再下架」—— 要新增附件状态列 +
回调处理器 + 产品决策。对 V0.1（家庭内部、个人主体、无公开传播面）代价不成比例。

⚠️ **它有 1MB 上限**（比产品允许的 5MB 小得多），超限的图**检测不了**，
fail-open 放行并记 warn。**P18 用 `sizeType: ['compressed']` 的真实原因就是这个**
（压缩后通常 100–500KB），不是为了省流量。

### 39.7 ⭐ 时间线游标必须是 `id`，不能是 `created_at`

docs/02 §7.2 原本写的是时间戳。`created_at` 是 `DATETIME(0)`（**秒**精度），
**同一秒发两条就会有相同时间戳**，`created_at < cursor` 翻页会**静默漏掉**
并列的那几条 —— 而且只在真的翻到边界时才出现。

冒烟脚本里那 5 条记录正是同一秒创建的，所以「无重复、无遗漏、顺序与一次拉完
完全一致」这三条断言在时间戳方案下会挂。已同步改 `CursorQuery` 的注释。

### 39.8 图片是**不可变**的（铁律 × 无状态位）

「全库不做物理 DELETE，一律状态位逻辑删除」是 AGENTS.md 铁律，而
`memory_attachments` **没有状态位**（DDL 是字段唯一真相）——
无法逻辑删除旧行，于是「替换图片」只能物理删，违反铁律。

结论：`UpdateMemoryRequest` **刻意没有 `attachments`**，`PATCH` 只改正文与
可见范围。发错了删掉重发。已记入未来需求池。

对照：`thing_reminders` 有 `status` 列，所以它能「全量替换（旧置 status=3）」。
**子表能不能软删，看 DDL 给不给状态位。**

### 39.9 别人的私密记录回 40400，不是 40300

40300 等于告诉对方「这里有一条你看不到的东西」—— 那本身就是一次泄露。

而且这条判断在 `MemoryService.detail()` 里**再判一次**，不依赖调用方已经过了
`contextForMemory`：**「调用方已经校验过」正是这条铁律最容易被绕过的方式**
（多一个调用点就漏一次）。

### 39.10 冒烟脚本真的抓到一个 bug

### 39.18 ⚠️ 工具坑：带沙箱升级的 Bash 命令会**执行两次**

本轮多次出现「插入的内容重复了两遍」。根因：命令先沙箱跑一遍失败/被升级，
再以「Sandbox bypassed (escalation-approved)」跑第二遍 —— 于是
`node -e "...splice 插入..."` 跑了两次。

**对策：所有「插入 / 追加」类脚本都要写成幂等的** ——
插入前先检查标记字符串是否已存在，存在就跳过。本轮后半段都加了守卫
（输出 `已存在，跳过`），再没出问题。

另：`docs/05` 是 **CRLF**（其余 docs 是 LF）。`git config core.autocrlf=true`
会在提交时归一，所以 diff 不会变成整文件重写；但**拼接内容时要按文件自己的
行尾**（`raw.includes('\r\n') ? '\r\n' : '\n'`），否则会出现混合行尾。

### 39.19 ⚠️ 冒烟必须打「用新代码起的服务」——旧进程会让全部断言挂在 40400

M4 收尾时独立复跑冒烟，第一次全挂在
`{"code":40400,"message":"这个内容找不到了"}`，连 **M3 的 `/api/menu/random`**
也 404 —— 说明**不是业务 bug，是路由根本不存在**：
当时 :3000 上跑着 4.9 小时前的旧进程，:3100 上是 74 分钟前的。
`/api/health` 正常返回（它一直在），所以「服务活着」不代表「服务是新的」。

**判据（一眼分辨旧服务）**：拿一个**确定存在**的老路由探一下，比如
`curl -s "http://127.0.0.1:PORT/api/menu/random?familyId=1"`。
回 `40100 请先登录` = 路由在（只是没带 token）；回 `40400 这个内容找不到了` = 旧进程。

**对策**：冒烟前先 `pnpm --filter @jyss/server run build`，
再用 `PORT=32xx node dist/server/src/main.js` 起一个**独立端口**的进程，
`SMOKE_BASE_URL=http://127.0.0.1:32xx pnpm run smoke:m4`。
不要复用长跑的 dev server —— 它的路由集合是启动那一刻的。

（本次实测：3200 上是带 M4 路由的服务，m1 83 / m2 215 / m3 180 / m4 76
= **554 项全过**，与提交信息里写的数字一致。）
