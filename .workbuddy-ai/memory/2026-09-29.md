# 2026-09-29

## PRD v0.1 → v0.2 深度评审与完善

### 方式
以「高级产品经理 vs 甲方」的方式做了一轮需求评审：先通读 PRD 找问题，输出问题清单，再逐条与用户确认决策，最后落到文档。

### 评审发现的核心问题（已全部解决）
1. **地基性漏洞**：PRD 隐含假设「系统可随时推送给任何家庭成员」，但小程序一次性订阅要求「接收人本人授权、授权一次只能发一条」→ 定时提醒场景直接失效
2. **矛盾1**：重复功能在 6.3/第8节说支持、第24节说 V0.2 才做
3. **矛盾2**：叮一下私密 vs 派活可见，`visibility` 只挂在小事层装不下
4. **空白**：多家庭（模型支持但产品未定义）、完成→留个念关联、吃啥呢决策记录 vs 执行记录
5. **缺失**：编辑撤回、成员退出边界、单人家庭体验、通知节流、状态回滚、称谓规则、菜谱冷启动、审核策略、非功能需求、用户故事、术语表、风险假设

### 关键决策（用户拍板）
- **推送模型**：定时推 + 引导预授权（三层机制：额度累积 / 站内兜底 / 首页承载）
- **重复功能**：V0.1 只做低频（每周/每月），不做「每天」
- **多家庭**：模型支持，产品 V0.1 只开放单家庭；切换入口放【我的】Tab
- **吃啥呢**：卡片随机（不用转盘）
- **编辑撤回/状态回滚/通知节流**：V0.1 都不做，V0.2 再做
- **称谓**：不可重名、可修改、1-10 字符
- **菜谱**：系统菜谱写死在代码常量（约 60-80 条），不进数据库
- **审核策略**：做正式功能「示例家庭」（前端 mock，只读）
- **成员退出**：自动取消其未完成小事 + 停止其提醒 + 复用原 member 记录

### 关于推送通道的调研结论（重要）
- **wxpush**（github.com/frankiejun/wxpush）：基于 Cloudflare Workers + 微信公众号模板消息，主流用法是「微信公众平台测试号」。技术上可无限主动推送，但**产品上不可用**：① 消息只能跳网页，跳不回小程序 ② 用户要关注一个沙箱测试号，无品牌感 ③ 测试号有用户上限、会被回收 ④ 上架后必须拆除
- **「引导订阅服务号」思路**：方向对但对象错。认证服务号模板消息需企业营业执照 + 对公账户，**个人主体注册不了服务号**
- **正确解法**：累积小程序订阅消息额度。关键机制是用户首次授权时勾选「**总是保持以上选择，不再询问**」，之后每次调用静默返回同意并累积额度。⚠️ 此机制**需 M0 阶段写技术验证 demo 确认**（记为假设 A4）
