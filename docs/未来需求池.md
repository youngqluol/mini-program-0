## V0.1 已知缺口（不影响上线，但要知道）

这些是开发期实测出来的**能力边界**，不是 bug，也不是待办 ——
记在这里是为了下次有人问「为什么这条没推到微信」时能直接找到答案。

- [ ] **派活不设时间时，发不出小程序订阅消息**
  - 原因：订阅消息模板「待办事项提醒」（编号 2983）的 `time23` 是**必填的 `time` 字段**，
    而 `time` 类型只接受 `yyyy-MM-dd HH:mm` 这种真实时间，
    硬填「不限时间」会直接返回 `47003`。公共模板库的模板**不可改字段**。
  - 现状：代码里 `buildSubscribeData()` 会返回 `null`，通道二自动跳过，
    降级到站内消息。**公众号模板消息（主力通道）不受影响**，照常能推。
  - 价值：目前只是少一条辅助推送，主力通道 + 站内兜底都在，不致命。
  - 成本：小 —— 若将来想补，可选方案是换个把时间字段设为「非必填」的公共模板，
    或在产品上把「派活时间」改为必填（但后者违反「家庭不是公司」的纪律，不建议）。
  - 归属：V0.2 观察后再定

- [ ] **消息中心只能「全部已读」，没有「单条已读」**
  - 原因：docs/02 §九 只定义了 `POST /notifications/read-all`，
    没有 `POST /notifications/{id}/read`。
  - 现状：`notification_logs.read_at` 字段已就绪（单字段表达「未读 / 已读 + 时刻」），
    后端补单条已读只是一个 `updateMany` —— 这是**接口契约缺口，不是技术缺口**。
    因此点开一条通知不会清掉角标，用户只能点「全部已读」。
  - 价值：消息一多，「全部已读」会连带清掉还没看的，属于**体验瑕疵**。
  - 成本：小 —— 补一个接口 + 前端点开时调用。
  - 归属：V0.2（若内测反馈「角标清不掉」强烈，可提前）
  - 记录位置：`server/src/modules/notify/notification.controller.ts` 顶部注释
