# 未来需求池

>
> 不要顺手实现，不要为了「以后可能用到」做抽象。

## V0.1 已知缺口（不影响上线，但要知道）

这些是开发期实测出来的**能力边界**，不是 bug，也不是待办 ——
记在这里是为了下次有人问「为什么这条没推到微信」时能直接找到答案。

- [ ] **派活不设时间时，发不出小程序订阅消息**
  - 原因：订阅消息模板「待办事项提醒」（编号 2983）的 `time23` 是**必填的 `time` 字段**，
    而 `time` 类型只接受 `yyyy-MM-dd HH:mm` 这种真实时间，
    硬填「不限时间」会直接返回 `47003`。公共模板库的模板**不可改字段**。
  - 现状：代码里 `buildSubscribeData()` 会返回 `null`，通道二自动跳过，
    降级到站内消息。**公众号模板消息（主力通道）不受影响**，照常能推。
  - 价值：目前只是少一条辅助推送，主力通道 + 站内兜底都在，不致命。
  - 成本：小 —— 若将来想补，可选方案是换个把时间字段设为「非必填」的公共模板，
    或在产品上把「派活时间」改为必填（但后者违反「家庭不是公司」的纪律，不建议）。
  - 归属：V0.2 观察后再定

- [ ] **消息中心只能「全部已读」，没有「单条已读」**
  - 原因：docs/02 §九 只定义了 `POST /notifications/read-all`，
    没有 `POST /notifications/{id}/read`。
  - 现状：`notification_logs.read_at` 字段已就绪（单字段表达「未读 / 已读 + 时刻」），
    后端补单条已读只是一个 `updateMany` —— 这是**接口契约缺口，不是技术缺口**。
    因此点开一条通知不会清掉角标，用户只能点「全部已读」。
  - 价值：消息一多，「全部已读」会连带清掉还没看的，属于**体验瑕疵**。
  - 成本：小 —— 补一个接口 + 前端点开时调用。
  - 归属：V0.2（若内测反馈「角标清不掉」强烈，可提前）
  - 记录位置：`server/src/modules/notify/notification.controller.ts` 顶部注释

- [ ] **P08「常用短语」（历史提醒标题 Top 5）没有对应接口**
  - 原因：docs/03 P08 的交互细节 3 要求「常用」短语来自该用户历史创建的提醒标题
    Top 5，但 **docs/02 里没有这个接口** —— `GET /family-things` 只有 `keyword`
    过滤，没有聚合。
  - 现状：P08 不渲染这一块。用户照样能叮，只是每次都要自己打字。
  - 价值：中 —— 「带水杯 / 拿快递 / 交费」这类短语高度重复，一键填入能省不少事，
    是这个页面「3 步内完成」目标的一块拼图。
  - 成本：中 —— 后端要加一个聚合查询（`GROUP BY title ORDER BY count DESC LIMIT 5`，
    注意只取该用户创建的、且要过滤掉逻辑删除的），前端加一排 chips。
  - 归属：V0.2
  - 记录位置：`miniprogram/pages/nudge/create.ts` 顶部注释

- [ ] **P08 的 `NO_QUOTA` 半屏引导未做（M2-F14）**
  - 原因：docs/03 要求 `NO_QUOTA` 时弹半屏「再开一次，帮我把话带到」→
    `wx.requestSubscribeMessage`。该能力需要**小程序侧的订阅模板 ID**，
    而模板 ID 目前只存在于服务端环境变量（`WX_TEMPLATE_*`），仓库里没有。
  - 现状：退化为三档 toast。文案是准的（「已记下，阿妈再开一次微信提醒就能收到」），
    用户知道该做什么，只是少了一个「顺手就办了」的按钮。
  - 价值：中 —— 少一次引导就少一次额度补充，辅助通道的到达率会低一些。
    注意 V0.1 的主力是公众号模板消息，`NO_QUOTA` 本来就少见。
  - 成本：中 —— 要把模板 ID 配到小程序侧（`config.ts` 或构建期注入），
    写 `requestSubscribeMessage` 封装 + 调 `POST /auth/subscribe-quota` 上报。
  - 归属：M2-F14（已在 docs/05 登记，未做）
  - 记录位置：`miniprogram/pages/nudge/create.ts` 顶部注释

- [ ] **P10 详情页不露出「家庭创建者也能完成 / 取消」这条兜底**
  - 原因：服务端 `complete` / `cancel` / `reopen` 都允许**家庭创建者**越过
    「执行人 / 发起人」身份直接操作（`thing.service.ts` 的 `ctx.isOwner`），
    这是防止一件事因执行人退出家庭而永远卡住的**数据阀门**。
    但 P10 的界面只认「我是执行人 / 我是发起人」两种关系 ——
    「只提醒，不监督」意味着不该把「我替你点完成」摆在手边（docs/03 P10）。
  - 现状：出现一种极少见但真实的死角 —— 若某件事的发起人与执行人都已不在
    这个家庭（例如发起人被创建者移除），创建者打开 P10 会看到一个完全不能操作的
    页面，既不能完成也不能取消。此时只能从后端改数据。
  - 价值：低到中 —— 触发条件很窄（V0.1 只有 1–4 人的家庭，且需要有人被移除），
    但一旦撞上就是**死锁**，没有自助出口。
  - 成本：小 —— 详情响应加一个「我能不能操作这件事」的服务端判定字段
    （而不是让前端去猜 `isOwner`），前端据此多给一个入口。
    **不要在前端自己查 `isOwner` 再拼权限**：权限判断必须留在服务端一处。
  - 归属：V0.2 观察后再定
  - 记录位置：`miniprogram/utils/thing-view.ts` 的 `buildThingDetailView()` 顶部注释

- [ ] **P10 的提醒行假定「提醒接收人 = 执行人」**
  - 原因：`ThingDetail.reminders` 里**没有接收人字段**，所以页面只能拿执行人的
    称谓去拼「🔔 17:30 提醒阿爸」。V0.1 这个假设成立：P08 / P09 创建提醒时都不传
    `recipientMemberId`，后端默认取执行人。
  - 现状：显示是对的。但 `docs/02 §5.1`（`POST /family-things/{id}/reminders`）
    允许显式指定接收人 —— 哪天做了「提醒别人」的入口，这一行就会说假话，
    而且是**安静的**假话（页面照常渲染，只是名字错了）。
  - 价值：中 —— 这是「以后会错」而不是「现在错了」，属于埋在地里的坑。
  - 成本：小 —— 详情响应的 `reminders[]` 补上 `recipient` 简要信息，
    前端改成用它；顺手把 V0.1 里那条「接收人取不到就退回执行人」的兜底写清。
  - 归属：和「提醒别人」功能同一批做
  - 记录位置：`miniprogram/pages/thing/detail.ts` 顶部注释、docs/05 M2-F9 实现说明

- [ ] **P01 首页「未开微信提醒」提示条未做（M2-F3）**
  - 原因：docs/03 P01 要求它出现在「**别人**没开微信提醒」时（仅在自己是发起人的场景下），
    但 `GET /notify/mp-bind/status` 只回**我自己**的绑定状态 ——
    后端**没有「家庭成员谁开了微信提醒」的接口**，这个显示条件现在算不出来。
    另外它要跳 P21 微信提醒页，而 P21（M2-F1）也还没做。
  - 现状：首页不渲染这个条。用户照样能叮，只是少一个「顺手提醒家人去开」的入口。
  - 价值：中 —— V0.1 的主力通道是公众号模板消息，**必须家人关注了才有用**；
    没有这个条，就只能靠发起人在微信里口头说，容易出现「派了活但对方根本收不到」。
  - 成本：中 —— 后端要给家庭维度的成员绑定状态（`family_members` 或 `users.mp_openid`
    的聚合查询，注意**只暴露「开 / 没开」这个布尔值**，不要漏 `mp_openid` 本身 ——
    它是机制词，用户界面禁用）；前端按 P21 就绪后一起做。
  - 归属：和 M2-F1（P21 微信提醒页）同一批做
  - 记录位置：`miniprogram/pages/index/index.ts` 顶部注释、docs/05 M2-F3

- [ ] **P01 首页不显示 `stats.overdue`（过期未完成数）—— 这是刻意的，别改回来**
  - 原因：接口 `GET /family-things/today` 会回 `stats.overdue`，但首页**刻意不显示**。
    「今天有 2 件事已经过了时间」是一句**催办话** —— AGENTS.md §6 的用户界面禁用词里
    就有「逾期」。
  - 现状：单条小事上那个变红的时间**保留**（`thing-card` 的 `tcard__time--late`）——
    那是**信息**：这件事本来定在几点。聚合成一个数字挂在页面顶部就变成**监督**了。
  - 价值：这是**纪律**，不是缺口。「只提醒，不监督」的边界正好落在这里。
  - 成本：零 —— 只是不渲染。
  - 归属：不要做。若哪天想加，先回去读 PRD §2 与 AGENTS.md §6。
  - 记录位置：`miniprogram/pages/index/index.ts` 顶部注释、docs/03 P01 v0.2.4 实现约定

- [ ] **P20 的「微信提醒」那一行未露出**
  - 原因：docs/03 P20 的「消息与提醒」区块有两行，第二行是「微信提醒（已开启 / 还没开）」，
    点击进 P21。**P21（M2-F1）还没做** —— 挂一个点了没反应的入口，比暂时不挂更糟
    （和 M2-F3 同一个判断）。
  - 现状：「还没开微信提醒」这件事目前由 **P12 消息中心**在送达失败时告诉用户
    （「还没开微信提醒」标签），信息没丢，只是没有一个常驻的状态位。
  - 价值：中 —— 这是「叮一下真能叮到人」的唯一常驻入口。
  - 成本：小 —— P21 做出来后，把这一行加回 `pages/mine/index.wxml` 即可，
    展示模型 `buildWechatNotifyRow()` 与样式 `.cell__extra--warn` 都是现成的。
  - 归属：**随 M2-F1（P21）一起做**
  - 记录位置：`miniprogram/pages/mine/index.ts` 顶部注释

- [ ] **P20 的「隐私政策」与「注销账号」两行未露出**
  - 原因：docs/03 P20 的「其他」区块列了它们，但
    ① **隐私政策**需要一份**真实**的合规文案（本项目实际收集：微信登录凭证、昵称头像、
    家庭称谓、消息记录、公众号绑定关系），不是一张空页面；
    ② **注销账号**需要后端的删除链路 —— 而本库**全库不做物理 DELETE**，
    注销只能置状态 + 匿名化，涉及 `users` / `family_members` / 各类业务表的处理口径。
  - 现状：两行都不渲染（不做假入口）。`docs/06` §4.6 与 §264 已把它们列为**上线前必做**
    （注销入口、隐私政策页面、注销后的数据处理说明），提审自查清单里也有对应项。
  - 价值：**高** —— 隐私指引与注销入口是**过审硬性要求**（docs/06 §4.1 / §4.6）。
  - 成本：中 —— 隐私政策页 1 张 + 注销的后端链路（状态位 + 匿名化 + 30 天清除口径）。
  - 归属：**上线前（M5）**，与 `docs/06` §四「隐私与合规」一起做
  - 记录位置：`miniprogram/pages/mine/index.ts` 顶部注释

- [ ] **微信昵称 / 头像授权未做（所以 `AuthUser.nickname` 一直是 null）**
  - 原因：`wx.getUserProfile` 早已被微信收回，现在要拿昵称头像得用
    `<button open-type="chooseAvatar">` + `<input type="nickname">`，
    而 P04 登录页只有一个「开始」按钮（刻意不弹任何授权框）。
  - 现状：`users.nickname` / `users.avatar_url` 两列一直是空。
    影响很有限：**家庭里认的是称谓，不是微信名** —— P20 抬头大字显示称谓、
    P14 成员列表也有称谓，所以界面看起来是正常的。
  - 价值：低到中 —— 只在「两个家称谓一样、想区分」这类场景才有用。
    真要做，注意**不要**为了它把登录流程改成「先授权才能用」。
  - 成本：小到中 —— 一个「改我的资料」入口（P14 里点自己那条）+ 上传头像到云存储。
  - 归属：V0.2
  - 记录位置：`miniprogram/utils/mine-view.ts` 的 `buildMineProfile()` 顶部注释

- [ ] **后端 `leave()` 的报错文案含「转给别人」，而转让创建者这个功能不存在**
  - 原因：`FamiliesService.leave()` 抛的是
    「你是这个家的创建者，得先解散或者转给别人」—— 但 `families.controller.ts` 里
    **没有转让创建者的接口**，前端 P20 也刻意不提这四个字（说了就是承诺一个不存在的出口）。
  - 现状：P20 已经绕开它（创建者看不到「退出家庭」按钮，看到的是一行指向「家庭设置」的说明），
    所以这句报错在正常路径上碰不到。但它是**服务端的一处不实陈述**，
    别的调用方（或以后的自己）读到会被误导。
  - 价值：低 —— 是一致性问题，不是功能问题。
  - 成本：极小 —— 改一句文案；或者真去补一个「转让创建者」接口（成本就大了）。
  - 归属：V0.2（若做「家庭切换 / 家庭管理」时一并处理）
  - 记录位置：`server/src/modules/families/families.service.ts` 的 `leave()`、
    `miniprogram/utils/mine-view.ts` 的 `buildLeaveRow()`

## 明确不做（至少 MVP 阶段）

这些在《产品需求文档》**第二十六章「MVP 明确不做」**被明确排除，记在这里是为了**每次想加的时候回来看看**：

```text
❌ 家庭聊天
❌ 家庭账本
❌ 家庭商城 / 购物平台
❌ 家庭相册（与「留个念」区分：不做大规模照片管理）
❌ 儿童教育
❌ 积分系统
❌ 勋章系统
❌ 排行榜 / 家庭 PK
❌ 监督系统 / 催办
❌ 复杂权限 / 角色矩阵
❌ 多人协作任务（共同完成一件事）
❌ 子任务
❌ 任务审批 / 工作流
❌ 任务优先级体系
❌ 公开社交 / 动态广场
❌ 好友关系

❌ AI 聊天机器人
❌ 复杂家庭数据分析
```

## 记录模板

新增想法时按这个格式追加：

```markdown
- [ ] 想法一句话描述
  - 来源：什么时候、什么场景下想到的
  - 价值：解决什么问题
  - 成本：大概工作量（小 / 中 / 大）
  - 归属：V0.2 / V0.3 / V1.0 / 待定
```
