# 一、产品概述

## 1.1 产品定位

「家有小事」是一款面向家庭成员的轻量事务协作工具。

它不试图成为复杂的家庭管理系统，而是专注于帮助一家人解决日常生活中的三类问题：

> **重要的事情不会忘记。**
> **事情有人负责。**
> **纠结的事情不再纠结。**

核心能力：

* 🔔 叮一下：提醒家人某件事情
* 🎯 派活：把一件事情交给指定家庭成员
* 🍽️ 吃啥呢：帮助家庭快速决定吃什么
* 📖 留个念：记录值得留下的家庭时刻

---

# 二、产品理念

## 2.1 核心理念

> **家有小事，不必放心上。**

家庭生活中存在大量“不值得专门记住，却又不能忘”的事情：

* 下午 6 点拿快递
* 明天记得带水杯
* 今天谁去接孩子
* 周末买菜
* 每个月交物业费
* 晚上谁负责做饭
* 今天到底吃什么

这些事情单独看都很小，但每天都会不断消耗家庭成员的注意力。

「家有小事」的目标，就是：

> **把这些小事从人的脑子里拿出来，交给产品处理。**

---

# 三、产品原则

## 3.1 少操作

家庭事务已经足够琐碎，产品不能让用户为了记录一件小事而进行复杂操作。

**量化标准：** 创建一条「叮一下」不超过 3 步；创建一条「派活」不超过 4 步。

## 3.2 少打扰

提醒的目的是帮助，而不是监督。

产品不会设计：

* 催办排行榜
* 逾期处罚
* 家庭积分惩罚
* “你怎么还没做”
* 强制确认

## 3.3 少纠结

能够快速帮用户做决定，就不要让用户面对复杂选择。

例如：

> “今天吃什么？”

应该尽量做到：

> 打开 → 点一下 → 决定。

**因此「吃啥呢」的决策方式确定为「卡片随机」**，不使用需要多次操作和等待的大转盘（详见第十六章）。

## 3.4 少管理

家庭不是公司。

产品避免出现类似企业协同软件的复杂概念：

* 审批
* 工作流
* KPI
* 项目
* 权限矩阵
* 任务优先级体系

## 3.5 有人情味

系统语言尽量像家人在说话。

例如：

不要：

> 您有一项任务待完成。

而是：

> **阿妈，有个活儿到你啦～**

# 四、用户与家庭模型

## 4.1 用户

每个人拥有独立账号。

用户本身不绑定“爸爸”“妈妈”等固定身份。

## 4.2 家庭

多个用户可以组成一个家庭。

```text
家庭：我们家

├── 用户A
├── 用户B
├── 用户C
└── 用户D
```

## 4.3 家庭称谓

用户加入某个家庭以后，需要设置自己在这个家庭里的称谓。

例如：

```text
用户A → 阿爸
用户B → 阿妈
用户C → 阿公
用户D → 阿嬷
```

### 称谓规则

| 规则 | 定义 |
| --- | --- |
| 长度 | 1–10 个字符 |
| 唯一性 | **同一家庭内不允许重名。** 两个人不能都叫「阿妈」 |
| 可修改 | **支持随时修改**，修改后家庭内所有历史记录展示同步更新 |
| 内容限制 | 支持中文、字母、数字、emoji；禁止纯空格；需通过内容安全检测 |
| 修改权限 | 只能修改**自己**的称谓。家庭创建者也不能改别人的称谓 |
| 冲突处理 | 提交时若重名，提示「家里已经有人叫『阿妈』了，换一个吧～」 |

不限制具体称呼：爸爸、妈妈、爷爷、奶奶、儿子、女儿，也可使用方言或家庭内部称呼（阿妈、阿爸、阿嬷、老爸、老婆、媳妇、哥哥……）。

## 4.4 多家庭

数据模型上，一个用户可以加入多个家庭：

```text
用户：张三

家庭A：我的小家
称谓：阿爸

家庭B：爸妈家
称谓：儿子
```

### V0.1 范围界定

> **V0.1 产品上只开放「单家庭」。**
>
> 即：一个人同一时间只处于一个家庭，首页、消息、叮一下、派活全部只面向这个家庭。
> 数据模型保留多家庭能力（`family_members` 表结构不变），但产品层不提供创建/加入第二个家庭的入口。

**家庭切换**在 V0.2 开放，入口位置已预留：**底部导航「我的」Tab → 家庭区 → 切换家庭**（详见第五章）。

> **为什么这样切：** 多家庭会带来「当前家庭」上下文、消息归属、成员选择器范围等一系列复杂度，而 MVP 阶段（你和老婆两个人）用不到。数据模型先支持，避免以后改表。

# 六、核心模块一：🔔 叮一下

## 6.1 产品定义

“叮一下”用于提醒某个家庭成员一件事情。

它不一定产生任务。

例如：

> “阿妈，明天记得给宝宝带水杯。”

可以只是一个提醒。

## 6.2 两种叮法

### 立即叮

创建后立即发送提醒。**发起人在当下操作，消耗发起人自己的订阅额度，送达确定性高。**

### 定时叮

指定未来时间发送提醒。**依赖接收人提前授权过订阅额度**（详见 6.5）。

## 6.3 重复规则

### V0.1 支持范围

> **只做低频重复：每周、每月。不做「每天」。**

| 类型 | V0.1 | 理由 |
| --- | --- | --- |
| 不重复 | ✅ | — |
| 每周 | ✅ | 额度消耗可控（约 4 次/月），覆盖「周末买菜」「每周大扫除」 |
| 每月 | ✅ | 额度消耗极低（1 次/月），覆盖「交物业费」「还信用卡」 |
| 每天 | ❌ 移入 V0.2 | 一年 365 次，订阅额度撑不住；且高频重复实质上接近「自动催办」，与「少打扰」原则冲突 |
| 自定义规则 | ❌ 移入 V0.2 | 交互复杂，MVP 不需要 |

### 重复提醒的产品语义

> **重复提醒是「周期性事件提醒」，不是「未完成催办」。**

含义界定：

* ✅ 「每周六上午 9:00，提醒买菜」——这是**到点该做了**
* ❌ 「买菜还没完成，再提醒一次」——这是**催办，产品不做**

系统永远不会因为「上一件没完成」而追加提醒。

## 6.4 提醒隐私与可见性

> **v0.2 澄清：`visibility` 只定义在「小事」这一层，提醒不单独设置可见性。**

| 小事类型 | 默认可见性 | 可选 |
| --- | --- | --- |
| 🎯 派活（TASK） | 家庭可见 | 可改为「只有我俩」 |
| 🔔 叮一下（REMINDER） | 仅发起人 + 接收人 | 可改为「家里人都能看到」 |

**挂在派活上的提醒，跟随派活的可见性。**

例如：

> 阿妈派活给阿爸「今晚买菜」（家庭可见），并挂了一条「17:30 提醒阿爸」。
> 阿公可以看到这条派活，也可以看到「17:30 提醒」这个信息。

理由：「阿妈派了活并设了个提醒」本身没有什么需要隐藏的。真正需要私密的场景是**纯叮一下**（不挂在任何派活上），例如「明天记得拿身份证」——这种默认只有两个人能看到。

## 6.5 消息送达机制 ⭐

> **本章为 v0.2 新增，是 v0.1 中最严重的一处漏洞的修补。**

### 6.5.1 问题：v0.1 的错误假设

v0.1 隐含假设了「系统可以随时把消息推给任何家庭成员」。

**这个假设在小程序订阅消息体系下不成立：**

* 微信小程序的**长期订阅消息**仅对政务民生、医疗、交通、金融、教育等特定行业开放
* 家庭生活工具类目**只能使用一次性订阅**
* 一次性订阅的规则是：**用户授权一次，只能下发一条**
* 且授权必须由**「接收消息的那个人」本人**在小程序内点击确认

于是这个场景直接失效：

```text
阿妈想「明天 7:00 提醒阿爸带水杯」

阿妈在自己手机上操作  →  能拿到的是「阿妈自己」的订阅授权
7:00 要推的是「阿爸」  →  阿爸没授权过  →  这条推送发不出去
```

### 6.5.2 解法：三层机制

> **V0.2.1 更新：** 本节描述的是**小程序订阅消息**这一条通道的兜底机制。自 v0.2.1 起系统新增了更可靠的 **wxpush 公众号模板消息通道**（见 6.5.7），它承担主力推送职责，本节的额度累积机制降为**辅助通道**（额度用得上就用，用不上不影响送达）。三层的兜底思想不变，仍然有效。

#### 第一层：授权额度累积（主通道）

**关键机制：** 用户在首次授权弹窗中勾选「**总是保持以上选择，不再询问**」后，后续每次调用订阅授权接口都不再弹窗、直接静默返回「同意」，且**每次都累积一次订阅额度**。

因此设计为：

```text
① 加入家庭时  →  一次性授权引导
   文案：「授权一下，家里人有事才能及时找到你」
   引导用户勾选「总是保持以上选择」

② 之后所有自然交互点  →  静默累积额度
   · 每次打开小程序
   · 每次创建叮一下 / 派活
   · 每次完成任务
   （后端调用授权接口，静默 +1）

③ 额度池  →  Redis 计数管理
   key: subquota:{userId}:{templateId}

④ 额度监控  →  额度 < 2 时
   首页顶部出现轻提示条：「提醒快用完了，点一下补上 →」
```

> ⚠️ **待验证假设（A4）：** 「勾选『总是保持以上选择』后每次调用是否真的累积额度」，需要在开发启动前写一个技术验证 demo 确认。这是社区通行做法，但微信官方文档未明确说明。**这是 M0 阶段必须完成的验证项。**

#### 第二层：站内消息兜底

额度耗尽时**不静默失败**：

```text
① notification_logs 照常写入（channel = 站内消息）
② 首页顶部出现家庭内提示：「有 2 条提醒今天发不出去，点这里补一下授权」
③ 消息中心（「我的」Tab）承载完整的历史通知
```

#### 第三层：首页承担主要提醒职责

> **产品承诺的底线不是「一定推送到微信」，而是「打开小程序一定看得到」。**

因此首页的「今天家里有什么事」区块是整个产品的**核心提醒载体**，订阅消息只是锦上添花。

### 6.5.3 明确不做

| 方案 | 为什么不采用 |
| --- | --- |
| 引导用户关注**认证服务号** | 认证服务号模板消息需要**企业营业执照 + 对公账户**，个人主体注册不了服务号 |
| 使用**企业微信**应用消息 | 需要企业微信组织，家人需加入企业，使用门槛远高于小程序 |
| 依赖**短信**做常规提醒 | 成本按条计费、需报备模板、跳回小程序链路对个人主体走不通（详见 6.5.5） |

> **修订说明（v0.2.1）：** v0.2 曾把「微信测试号推送（wxpush 类方案）」列入「明确不做」，理由是「消息跳不回小程序 + 无品牌感」。**该结论已推翻**——见 6.5.7。跳转问题有解，品牌感问题在验证期可以接受，而它带来的收益（**无限次主动推送**）恰好补上了本产品最大的短板。

### 6.5.4 专项评估：改成原生 App 能不能解决推送问题？

> **结论：技术上能，但代价是摧毁产品的地基。不做。**

#### 技术事实

推送能力确实能解决，但 iOS 和 Android 是两回事：

| 平台 | 推送能力 | 代价 |
| --- | --- | --- |
| **iOS** | 用户授权「允许通知」一次后，**可以无限次推送**。问题真正被解决 | 需 Apple Developer Program（$99/年）+ App Store 审核 |
| **Android** | 走厂商通道（华为 / 小米 / OPPO / vivo / 荣耀 / 魅族），App 被杀也能收到，到达率约 90%+ | **生态碎片化**：要接入 5–6 家厂商推送 SDK，各需单独申请开发者账号；厂商通道对**新应用 / 低活跃应用有推送配额限制**；部分厂商要求企业资质 |

也就是说：**推送问题在 iOS 上真能解决，在 Android 上能解决但工程成本显著。**

#### 但真正的代价不是技术成本

> **换成 App 会摧毁「家人愿意用」这个前提——而这恰恰是本项目第一阶段要验证的核心（第二十八章）。**

目标用户是**家庭成员，包括爸妈和老人**。让爸妈为了收一条「记得拿快递」去下载 App、注册账号、开通知权限，这个转化漏斗比小程序长得多：

```text
小程序：  微信里点一下  →  用
App：     应用商店搜索 → 下载 → 安装 → 注册 → 授权通知 → 用
```

**你解决了推送，但用户没进来。**

#### 成本对比

| 维度 | 微信小程序 | 原生 App |
| --- | --- | --- |
| 推送能力 | 一次性订阅（1 授权 = 1 条） | iOS 无限；Android 厂商通道基本无限但碎片化 |
| 开发量 | 1 套 | iOS + Android 至少 2 套（推送仍需原生桥接） |
| 分发 | 分享即用，零安装 | App Store 审核 + 各安卓应用商店逐个上架 |
| **合规** | 小程序备案 | **App 备案（工信部强制，未备案面临下架）** + 软著 + 隐私政策 + 商店资质 |
| 迭代 | 提交即更新 | 每次发版过审，用户手动更新 |
| 费用 | 云托管约 100 元/月 | Apple $99/年 + 服务器 + 短信 + 更多人力 |
| **家人安装意愿** | **高** | **低** ← 决定性因素 |

#### 什么时候 App 才是对的

不是永远不做，而是**顺序不能反**：

```text
现在：  小程序验证「家人愿不愿意用」
          ↓ 验证通过
以后：  小程序 + App 双端
        小程序负责「零门槛拉新」，App 负责「可靠推送 + 留存」
```

**先证明有人用，再考虑用什么载体。**

### 6.5.5 备选增强通道：重要提醒走短信（待评估）

如果将来「提醒送不到」成为真实痛点，比做 App 更务实的补充是**短信**：

| 项 | 说明 |
| --- | --- |
| 优势 | **到达率 100%**，无需安装、无需授权、无需关注 |
| 成本 | 约 0.04 元/条，按量付费 |
| 适用 | 仅对用户主动标记为「重要」的提醒启用，普通提醒不走 |
| 障碍 | ① 需收集手机号（隐私指引要更新）② 短信模板需报备审核 ③ **短信跳回小程序的链路对个人主体可能走不通**（`wx-open-launch-weapp` 需认证公众号 JSSDK 权限），可能只能引导用户「打开微信搜索小程序」 |

**状态：列入 V0.2 备选，V0.1 不做。** 先观察真实痛点强度再决定是否投入。

### 6.5.6 发送状态对用户透明

发起人必须知道「到底叮到了没有」——**这是信任问题，不能含糊**。

| 返回状态 | 含义 | 用户看到 |
| --- | --- | --- |
| `SENT` | 已下发（wxpush 或订阅消息） | toast「已经叮到阿妈啦 🔔」 |
| `NO_QUOTA` | 额度不足，已转为站内消息 | toast「已记下，阿妈再开一次微信提醒就能收到」+ 补提醒引导 |
| `NOT_BOUND` | 对方还没绑定微信提醒 | toast「已记下，阿妈还没开微信提醒，她打开小程序就能看到」 |
| `FAILED` | 微信接口报错 | toast「没叮成功，稍后再试」 |

> 状态对用户是**三档而非两档**：成功 / 有条件的成功 / 失败。**「有条件的成功」必须说清楚条件**，否则用户会以为对方已经收到了，反而制造误会。

> ⚠️ **上表文案不得出现机制词**（绑定 / 授权 / 公众号 / openid / 订阅 / 模板消息 / 测试号）——
> 用户只需要知道「微信提醒 开 / 关」（AGENTS.md §6）。
> 文案的唯一定义处是 `packages/shared/src/dto/notify.ts` 的 `DELIVERY_TOAST`，改文案改那里。

### 6.5.7 增强通道：wxpush 公众号模板消息 ⭐

> **本章为 v0.2.1 新增。结论：V0.1 验证期采用，作为主力推送通道。**
>
> 完整技术方案见 `docs/08-wxpush推送集成方案.md`。

#### 为什么值得为它破例

| 维度 | 小程序订阅消息 | wxpush 公众号模板消息 |
| --- | --- | --- |
| 推送次数 | 1 次授权 = 1 条 | **无限次主动推送** |
| 授权方式 | 用户在小程序内逐次授权 | **关注一次即可** |
| 能否推给「别人」 | ❌ 不能（必须接收人本人授权） | ✅ **能**（只要对方关注过） |
| 到达形态 | 服务通知 | 服务通知（**同样的原生弹窗 + 声音提醒**） |
| 成本 | 0 | 0（Cloudflare Workers 免费额度） |
| 合规 | 小程序备案 | 依赖测试号，**产品化前必须拆除** |

**最关键的一行是「能否推给『别人』」**——它直接解开了 6.5.1 里那个死结：

```text
阿妈想「明天 7:00 提醒阿爸带水杯」

v0.2 的结论：  阿妈能拿到的只有「阿妈自己」的授权  →  推不出去  ❌
v0.2.1 的解法：只要阿爸关注过推送号  →  7:00 直接推给阿爸  ✅
```

#### 两个已知硬伤与处置

| 硬伤 | 处置 | 状态 |
| --- | --- | --- |
| **① 消息跳不回小程序** | 三级跳转：模板消息 `miniprogram` 字段（直接跳）→ 中转页**小程序码长按识别** → 纯文案引导搜索 | 有解 |
| **② 用户需关注一个叫「微信公众平台测试号」的沙箱账号，无品牌感** | 验证期（只有自己家人用）接受；产品化之前必须替换 | 已知，接受 |

#### 跳转能力的真实边界（务必知悉）

经核实微信官方文档，个人主体小程序在跳转上有硬约束，不能想当然：

| 手段 | 个人主体可用？ | 说明 |
| --- | --- | --- |
| 模板消息 `miniprogram` 字段 | ⚠️ 待实测 | 官方要求「服务号已关联该小程序」，测试号无关联入口，**大概率不生效**。M0 必须实测 |
| URL Link（`wxaurl.cn`） | ❌ 不可用 | 官方明确「**只针对非个人主体小程序开放**」，且必须小程序已发布 |
| `wx-open-launch-weapp` 开放标签 | ❌ 不可用 | 需认证公众号 + JSSDK 权限，测试号不具备 |
| **小程序码（长按识别）** | ✅ **可用** | 中转页展示小程序码图片，用户长按识别即打开。**这是主力手段** |
| 纯文案引导 | ✅ 可用 | 「打开微信，搜索小程序『家有小事』」——保底 |

**因此中转页的形态是：** 展示消息全文 + 一张小程序码（长按识别）。这在微信内是很自然的操作，体验可接受。

#### 边界与纪律（不可突破）

1. **wxpush 是验证期的临时通道，不是长期方案。** 进入产品化（面向非家人用户）之前必须替换。
2. **不允许让用户为了收消息而付出额外成本**——关注动作只在小程序内一次完成，不做任何站外引导。
3. **推送失败绝不静默**——所有发送结果写入 `notification_logs`，站内消息中心始终完整（见 6.5.6）。
4. **它不改变产品原则**——推送只是「把已有的事说一声」，不引入催办、不引入监督（第三章）。

#### 通道优先级（V0.1 实际运行逻辑）

```text
要发一条提醒
   ↓
① 接收人已绑定 wxpush（已关注推送号）  →  公众号模板消息    ✅ 主力
   ↓ 未绑定 / 发送失败
② 接收人有小程序订阅额度               →  小程序订阅消息    ⚠️ 辅助
   ↓ 额度耗尽 / 失败
③ 一律写入站内消息中心                 →  首页可见          ✅ 兜底（永不失败）
```

> **产品承诺不变：** 「打开小程序一定看得到」仍是底线。wxpush 只是把「**不用打开也能看到**」的比例大幅提高。
>
> **待验证假设（A5）：** 测试号模板消息的 `miniprogram` 字段是否生效；中转页小程序码长按识别是否稳定。**M0 阶段与 A4 一并验证。**

# 七、核心模块二：🎯 派活

## 7.1 产品定义

“派活”用于把一件需要完成的事情交给家庭成员。

例如：

> 阿爸 → 阿妈：拿快递

## 7.2 创建派活

基本字段：

```text
干啥？
派给谁？
什么时候？
要不要叮？
是否重复？
备注？
```

## 7.3 派活的可见性

默认**家庭可见**。

```text
🛒 买菜
阿爸
今天 18:00
待完成
```

这不是为了监督，而是因为：

> **家庭成员需要知道家里有哪些事情已经有人负责了。**

例如阿妈就不会再次问：「菜买了吗？」

也可以改为「只有我俩」——适用于不想让全家人看到的私事。

---

# 八、派活时间

支持：

| # | 类型 | 示例 |
| --- | --- | --- |
| ① | 不限时间 | 有空买瓶酱油 |
| ② | 今天 | 今天买菜 |
| ③ | 指定时间 | 今天 18:00 拿快递 |
| ④ | 指定日期 | 9月30日交物业费 |
| ⑤ | 重复 | 每周六上午买菜（**V0.1 仅支持每周 / 每月，见 6.3**） |

---

# 九、派活执行人

> **一个小事只能有一个主要执行人。**

例如：

```text
买菜
↓
阿妈
```

暂不支持「阿爸 + 阿妈共同完成」，避免过早引入复杂协作逻辑。

---

# 十、自己给自己派活

允许。

```text
🎯 派活

干啥？
洗车

派给谁？
我自己

什么时候？
周六上午

🔔 10:00 叮一下
```

这样产品同时具备轻量 Todo 能力。

---

# 十一、派活状态

MVP 只需要：

```text
待完成
   ↓
已完成
```

另外支持：

```text
已取消
```

暂不设计：进行中、阻塞、延期、审批、等待确认。

## 11.1 状态回滚

> **V0.1：不支持。** 误点「搞定啦」无法撤销。

理由：撤销需要设计「谁能撤」「撤销后对方收到什么」等一整套规则，V0.1 不值得。**V0.2 开放**（允许完成人自己或发起人撤销）。

---

# 十二、完成通知

任务执行人完成任务后：

> 派活的人默认收到轻量通知。

例如：

> **阿妈已经把“拿快递”搞定啦 ❤️**

而不是企业软件式的「任务执行状态已变更」。

**边界说明：** 只有「完成」会通知。**「没完成」永远不会有任何通知、提醒或追问**——这符合第十三章的监督原则。

---

# 十三、监督原则

产品：

> **只提醒，不监督。**

例如任务：

```text
18:00  🔔 叮一下
18:30
```

即使任务没有完成，系统也不会自动说：

> “阿妈，你怎么还没完成？”

除非用户主动设置了额外提醒。

---

# 十四、派活与叮一下的关系

两者可以独立，也可以组合。

| 组合 | 说明 |
| --- | --- |
| 只有叮一下 | 不产生任务，例如「明天记得带水杯」 |
| 只有派活 | 不设置提醒，例如「有空买瓶酱油」 |
| 派活 + 叮一下 | 最常见组合，例如「18:00 拿快递，17:30 提醒」 |

---

# 十五、编辑与撤回

> **本章为 v0.2 新增。**

## 15.1 V0.1 规则

> **已创建的内容一律不可编辑、不可撤回、不可收回。**

> ⚠️ **本条的适用范围是小事（派活 / 叮一下）** —— 下面每一行说的都是
> 「派出去的活 / 叮出去的消息」。**留个念不在此列**：它是个人时间线（§18.1），
> 发布者可以改删**自己那一条**（改正文与可见范围；删是逻辑删除 `status=0`）。
> 唯一的例外是**图片不可改** —— `memory_attachments` 没有状态位，而全库不做
> 物理 DELETE，所以「替换图片」只能物理删、违反铁律。发错了就删掉重发。
> 见 `docs/02` §7.4 与 `docs/未来需求池.md`。

| 对象 | V0.1 行为 |
| --- | --- |
| 派出去的活 | ❌ 不能修改内容、时间、执行人 |
| 派出去的活 | ❌ 不能撤回 |
| 叮出去的消息 | ❌ 不能收回 |
| 唯一允许的操作 | **「取消」**（状态置为已取消） |

**「取消」的规则：**

| 项 | 定义 |
| --- | --- |
| 权限 | 创建人，或家庭创建者 |
| 效果 | 小事状态置为「已取消」，挂在其上的提醒一并停止 |
| 对方是否收到通知 | **V0.1：不发送通知。** 对方在列表里看到状态变为「已取消」即可 |
| 是否可恢复 | V0.1 不可恢复 |

## 15.2 设计理由

「不可撤回」是刻意的约束，不是偷懒：

1. **产品原则是「少操作」**，编辑/撤回会引入大量状态分支（已读未读、已推送未推送、对方是否已看到）
2. **它逼迫用户在派活前想清楚**，这本身就是「把事情从脑子里拿出来」的一部分
3. V0.1 的验证目标是「家人愿不愿意用」，不是「功能全不全」

## 15.3 V0.2 规划

| 能力 | 规则 |
| --- | --- |
| 修改派活 | 创建人可改；改后通知执行人 |
| 撤回派活 | 创建人可撤；撤回后执行人收到微信通知 |
| 收回叮一下 | 发起人可收回；仅限未送达时，已送达则发一条「已取消」更正通知 |

# 十六、核心模块三：🍽️ 吃啥呢

## 16.1 产品定义

帮助家庭解决：

> **“今天吃什么？”**

## 16.2 决策方式

> **确定为「卡片随机」。**

```text
打开
  ↓
立即呈现一张菜品卡（带横向滑动的备选）
  ↓
[ 换一个 ]  [ 就吃这个 ]
```

**为什么不用大转盘：**

大转盘需要「点转 → 等转完 → 不满意再转 → 决定」，至少 3 步且有等待，与 3.3「打开 → 点一下 → 决定」的原则直接冲突。卡片随机可以做到**打开即出结果**。

转盘作为「一家人一起玩」的趣味玩法，列入 V0.3 备选。

## 16.3 一次推荐几道菜

| 场景 | 推荐数量 |
| --- | --- |
| 默认（晚餐） | **3 道**：一荤 + 一素 + 一汤/主食（尽量组合搭配） |
| 早餐 / 午餐 / 其他 | 1–2 道 |
| 用户手动调整 | 可以「换掉其中一道」，不需要全部重来 |

## 16.4 菜谱来源与冷启动

> **系统菜谱写死在代码默认配置里，第一次打开就可用，零配置。**

| 来源 | 存放位置 | 说明 |
| --- | --- | --- |
| 系统默认菜谱 | **代码常量**（`server/src/modules/menu/default-menu.ts`） | 共 **72 条**，覆盖家常菜 24 / 素菜 16 / 汤 11 / 主食 13 / 外食 8 五类 |
| 家庭自定义菜谱 | 数据库 `menu_items`（`family_id` 非空） | 家庭自己添加 |

> **v0.2.4 修正：常量位置由 `miniprogram/config/default-menu.ts` 改为
> `server/src/modules/menu/default-menu.ts`。** 产品口径一个字没变（内置、零配置、
> 约 60–80 条、五类），变的只是**放在哪一端** —— 而这是技术决定，权威来源是 docs/04。
>
> 原因：**后端必须持有这份名单，否则两个接口实现不了。** docs/02 §6.2 的
> `GET /menu/items` 要返回「系统菜谱 + 本家庭自定义菜谱」的**合集**；
> docs/02 §6.1 的 `GET /menu/random` 要返回 `poolSize` 与 `source: "SYSTEM"`；
> docs/03 P02 又明确「进入页面自动随机一次（`GET /menu/random?count=3`）」——
> 池子大小、随机、「排除最近 3 天吃过的」全在服务端算。
>
> 顺带避开一个坑：小程序端**不能 import 运行时值**（只做类型擦除，不解析
> tsconfig 的 paths），所以这份名单一旦放进 `packages/shared`，就会埋下
> 「看着能用、运行时 `MODULE_NOT_FOUND`」。放后端是唯一没有歧义的位置。
> 小程序端并不需要它 —— P02 走 `/menu/random`、P17 走 `/menu/items`。

**南北口味差异的处理：**

* 内置菜谱**只收全国通吃的大众家常菜**（番茄炒蛋、青椒肉丝、红烧肉、紫菜蛋花汤、饺子、面条……）
* 明显带地域偏好的（如折耳根、酸菜白肉）**不放进默认库**
* 用户可自行添加自家常吃的菜，几次之后「吃啥呢」自然贴合本家口味

**后续演进：** V0.3 考虑接入 AI 推荐 / 联网菜谱库（见第十七章）。

## 16.5 决策记录 vs 执行记录

> **明确了：`meal_records` 记录的是「决定了吃什么」，与是否派人做无关。**

* 点了「就吃这个」→ 写入 `meal_records`（无论之后是否派活）
* 选了「算了，自己解决」→ **同样写入** `meal_records`

理由：「吃啥呢」的价值是**帮家庭做决定**，决定了就是决定了。「最近吃过」的防重复逻辑也基于此——今天已经决定吃番茄炒蛋，明天就不该再推它，不管最后做没做。

派活与否则单独记录：若选择了派活，生成的那条派活就是「执行记录」，
`POST /menu/decide-and-assign` 会把它的 `thingId` 一并返回给前端。

> **v0.2.4 修正：** 原文写「`meal_records.thing_id` 关联到生成的那条派活」，
> 但 **`meal_records` 表里没有 `thing_id` 这一列**（`db/schema.sql` 是字段的唯一真相，
> 见 docs/README 的文档权威性表）。V0.1 也**不需要**它：
> 从「最近吃过」点进那顿饭看「谁做的」这个入口，docs/03 里没有。
> 前端拿 `thingId` 当场跳转就够了。
>
> 若 V0.2 真要做「用餐记录 → 派活详情」的反查，再给 `meal_records` 加
> `thing_id`（已记入 `docs/未来需求池.md`）。

## 16.6 与派活联动

确定菜单以后：

```text

番茄炒蛋 / 青椒肉丝 / 炒青菜

        ↓

要不要派活？

[ 派给阿妈 ]  [ 派给阿爸 ]  [ 算了，自己解决 ]
```

# 十九、「完成 → 留个念」的关联

## 19.1 两种留念

| **完成纪念** | 完成一件小事后顺手记一笔 | `family_memories.thing_id = 该小事ID` |

点击后进入发布页，**自动带上关联和预填标题**：

```text

├──────────────────────────────┤
│  来自：🎯 买牛奶              │  ← 自动带上的关联标记
│  ┌────────────────────────┐  │
│  │ 买牛奶 搞定啦            │  ← 预填，可改
│  └────────────────────────┘  │
```

## 19.3 时间线的呈现

关联记录在时间线上**不做视觉区分**（避免变成「任务日志」），只有在记录详情页底部显示一行极淡的标注：

```text

```

## 19.4 设计理由

「完成 → 留个念」在 v0.1 的闭环图里存在，但从未被定义。这里选择**打通但不强调**：

* 打通：让「搞定了」这件事有机会沉淀成家庭记忆
* 不强调：一旦主动提示「要不要留个念？」，产品就从「家庭时间线」滑向「任务日志」，违背 18.1 的定位

# 二十一、成员退出与家庭解散

> **本章为 v0.2 新增。原则：V0.1 一切从简，V0.2 再优化。**

## 21.1 成员主动退出

用户在「我的 → 退出家庭」发起。

### 退出时系统自动执行

| # | 处理对象 | V0.1 规则 |
| --- | --- | --- |
| ① | **派给他、且未完成的小事** | **自动置为「已取消」**，并给创建人发一条通知：「阿公退出了家庭，你派的『买菜』已自动取消」 |
| ② | **他派给别人、且未完成的小事** | 同样自动取消（创建人已离开，这件事无人跟进） |
| ③ | **他创建的定时提醒** | **全部停止**（`thing_reminders.status = 已取消`） |
| ④ | **他已完成的历史记录** | **原样保留**，称谓和历史都不变 |
| ⑤ | **他发布的留个念** | 保留（`visibility=家庭可见` 的仍对家人可见） |
| ⑥ | **成员记录本身** | 不删除。`family_members.status = 0` + 记录 `left_at` |

**为什么自动取消而不是保留？**

保留会产生「无人负责的活」和「幽灵提醒」，反而制造混乱。家庭产品里，**干净地了结比模糊地挂起更符合「不必放心上」**。

## 21.2 重新加入

> **V0.1 规则：重新加入 = 恢复原成员身份。**

* **复用原 `family_members` 记录**（把 `status` 改回正常、清空 `left_at`）
* `member_id` 不变 → 历史数据自动重新关联
* **允许重新设置称谓**（进入设置称谓页，预填原称谓）
* 若原称谓已被他人占用 → 提示重名，要求换一个

> 数据模型上 `family_members` 有 `(family_id, user_id)` 唯一约束，复用记录是唯一不冲突的方案，同时也是最符合直觉的——还是同一个人，还是同一个家。

## 21.3 创建者退出

> **V0.1：创建者不能「退出家庭」，只能「解散家庭」。**

「我的 → 家庭设置」里，创建者看到的按钮是「解散家庭」而非「退出家庭」。

解散时二次确认：要求**输入家庭名称**确认，防止误操作。

**解散后：** `families.status = 0`，**数据全部保留**（可支持后续恢复），所有成员不再能进入该家庭。

## 21.4 V0.2 优化方向

* 创建者可转让创建者身份
* 退出时允许用户选择「保留我派出的活」还是「一并取消」
* 家庭解散后 30 天内可恢复
* 已取消的小事支持恢复

# 二十三、通知与打扰控制

> **本章为 v0.2 新增。**

## 23.1 V0.1 规则：不做节流

> **派几个活，就收到几条推送。不做合并、不做汇总。**

## 23.2 会触发推送的场景

| 场景 | 推送对象 | 时机 |
| --- | --- | --- |
| 派活通知 | 执行人 | 创建时 |
| 叮一下 | 接收人 | 立即 / 定时 |
| 完成回执 | 创建人 | 对方完成时 |
| 加入家庭 | 家庭创建者 | 新成员加入时 |

**不会触发推送的场景：** 未完成、逾期、取消、编辑。

## 23.3 已知问题与 V0.2 规划

**问题：** 阿妈一口气派 10 个活，阿爸会连收 10 条订阅消息，体验很差，且快速耗尽额度。

**V0.2 优化方向：**

* **按日汇总**：同一天派给同一个人的多条活，合并为一条「今天有 3 个活到你啦」的汇总消息
* **静默窗口**：22:00–07:00 创建的即时提醒，延后到次日 07:30 发送
* **优先级**：只有设置了明确时间的才推送，无时间要求的只进站内消息

> V0.1 先把功能跑通，观察真实使用频次后再决定优化力度。

# 二十七、非功能需求

> **本章为 v0.2 新增。**

## 27.1 性能

| 指标 | 目标 |
| --- | --- |
| 首页首屏可交互时间 | ≤ 1.5s（4G 网络） |
| 接口响应时间 | P95 ≤ 500ms |
| 图片上传（压缩后 500KB） | ≤ 3s |
| 小程序主包体积 | ≤ 2MB |
| 冷启动 | ≤ 2s |

## 27.2 弱网与异常

| 场景 | 处理 |
| --- | --- |
| 请求超时 | 10s 超时，GET 自动重试 1 次 |
| 网络不可用 | 顶部轻提示条 + 「重试」按钮，不弹模态框 |
| 提交中重复点击 | 按钮置 disabled，防止重复提交 |
| 图片上传失败 | 保留已填内容，允许单张重试 |
| 服务端异常 | 统一提示「出了点小问题，再试一次」，不上抛技术错误 |

## 27.3 数据一致性

| 场景 | 处理 |
| --- | --- |
| 一家人同时操作同一条小事 | 状态变更走乐观锁（`updated_at` 校验），冲突时提示「这条已经被改过啦」 |
| 定时任务多实例并发 | Redis 分布式锁，同一提醒只发一条 |
| 提醒重复发送 | `notification_logs` 判重 + 状态机单向推进 |

## 27.4 安全与隐私

* 所有接口走 HTTPS
* 数据权限过滤**全部在服务端完成**，前端不承担安全职责
* `familyId` 不从请求体信任，一律做归属校验
* 敏感配置（AppSecret / JWT Secret / 数据库密码）全部走环境变量，不进代码库
* 用户注销后，30 天内清除其个人数据（保留家庭共享内容的匿名化记录）

## 27.5 时间与时区

* 用户侧统一北京时间，界面与消息里只出现北京时间
* 存储层用 UTC（Prisma 原生行为），北京时间在接口层格式化一次
* 业务代码里不做时区换算 —— 换算只存在于 `common/serialize/beijing-time.ts` 一个文件
* 完整推导见 `docs/01` §4.3

## 27.6 可用性

* 个人项目，**不做 SLA 承诺**
* 目标：月度可用性 ≥ 99%
* 提醒发送失败率超过 5% 时，通过日志告警

# 二十九、第一版成功标准

不以注册用户数、DAU、留存率作为第一阶段最重要指标。

第一阶段最重要的是：

> **这个产品能不能真正进入一个家庭的日常生活。**

建议第一阶段只观察：

```text
每天：
有没有创建小事？
有没有完成小事？
有没有使用吃啥呢？
有没有使用叮一下？

一个月后：
你和老婆还在不在用？
```

**判定口径（v0.2 补充）：**

| 结论 | 标准 |
| --- | --- |
| ✅ 值得继续做 | 第 4 周仍有 ≥ 3 天/周的活跃使用 |
| ⚠️ 需要调整 | 前 2 周活跃，第 3 周开始衰减 |
| ❌ 需要重新思考 | 第 2 周就不再打开 |
