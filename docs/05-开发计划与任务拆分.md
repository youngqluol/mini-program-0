## 一、总体策略

### 1.1 先打通一条竖切

不要按「先把所有表建好 → 再写所有接口 → 再写所有页面」的横切方式做。那样在最后联调时才会暴露问题。

**正确做法：选一条最短的完整链路，从数据库一路打通到 UI。**

```text
选中链路：创建家庭 → 邀请阿妈 → 阿妈登录加入 → 阿妈派活给阿爸 → 阿爸收到 → 阿爸完成
```

这条链路一旦跑通，`users / families / family_members / family_invites / family_things` 五张核心表、鉴权体系、家庭上下文、权限守卫全部就位。剩下的模块只是在已验证的地基上添砖。

**小程序端实现说明（2026-10-06）：**

- **F7 与 F6 的拆分方式调整**：原表把 P07 写成「创建/加入共用」的称谓页，
  但 F6 的验收又是「填家庭名 + 称谓后进入首页」——两者冲突。实际做法是
  **P05/P06 各自内嵌称谓输入**（创建/加入都是一次性的引导动作，用户此刻
  耐心最短，能一屏问完的不拆两屏），**P07 改为「修改我的称谓」独立页**
  （入口在 P14 点自己那一条）。F7 的验收「称谓重复有明确提示」由
  P06 加入时与 P07 保存时的 40900 文案承载。
- **新增 `utils/route.ts`**：小程序没有全局路由钩子，守卫写成普通函数在
  需要登录的页面 `onShow` 里调。用 `redirectTo` 而非 `navigateTo`，
  被拦下的页面不该留在返回栈里。
- **新增 `utils/time.ts`**：iOS 不认 `new Date('YYYY-MM-DD HH:mm:ss')`，
  必须先换成斜杠。这个坑只在真机 iOS 暴露，模拟器与安卓都不报错。

> **✅ M2-B9 文本内容安全已完成（2026-10-06）**，实测结论：
> 1. **个人主体小程序可以调用 `security.msgSecCheck`** —— 没有 48001「api unauthorized」。
>    实测：正常文案回 `suggest=pass`；违规文案回 `suggest=risky` + `label=20006`。
>    复现方式 `node tools/probe-seccheck.mjs`（这是唯一能看到微信原始结论的地方）。
> 2. **策略集中在 `ContentSecurityService`**，是全项目**唯一的放行策略点**：
>    `risky` → 拦（40002）；`review` 或判不了 → **放行** + 记 warn。
>    为什么必须有这一层：`msgSecCheck` 只回答「判成什么」，而「判不了时放不放行」是个
>    **产品判断**，必须只写一遍 —— 否则今天这里放行、明天那里拦截，就成了随机行为。
> 3. **fail-open 的理由**：微信抖一下、access_token 过期、接口没开通，都会让检测失败。
>    失败就拦的话，「阿妈，记得买牛奶」也发不出去，家里人只会觉得小程序坏了；
>    而 V0.1 是自用、没有公开传播面，违规内容的实际风险为零。
>    ⚠️ 这个取舍在**公开传播场景下要重新评估**（V1.0 若有分享 / 广场类功能）。
> 4. **超时故意设短**（3 秒，其他微信接口是 8 秒）：检测在「创建一条小事」的**同步路径**上，
>    微信慢 8 秒用户就干等 8 秒；检测是辅助能力，不值得让家人等。
> 5. **接入点**：小事创建（标题 + 说明**并发**检测，串行会白等一次往返）、
>    小事编辑（**只测本次真改了的字段**）、叮一下的正文。
>    带 `thingId` 的 nudge 不改内容，所以不检测 —— 不做无用的微信调用。
> 6. **开关** `CONTENT_SECURITY_ENABLED`：**默认开**，只有显式写 `false` 才关。
>    生产必须为 true（审核硬性要求）；本地关掉只是为了不被超时拖慢。
>
> ⚠️ **冒烟脚本验的是 fail-open 路径**：夹具 openid 是造的假值 → 微信必然回 40003 →
> 走「判不了 → 放行」。所以冒烟只能保证「不误拦、不阻塞」，**验不了「违规被拦」**。
> 确认链路真的被调用：跑完看服务日志里的 `[ContentSecurityService] 内容安全判不了，放行`
> （本次实测 24 条，对应夹具的每一次创建）。

## 九、V0.1 上线后的观察指标

按《产品需求文档》第二十九章「第一版成功标准」，第一阶段不看 DAU / 留存率，只看五个问题：

```text
每天：
  ① 有没有创建小事？
  ② 有没有完成小事？
  ③ 有没有使用吃啥呢？
  ④ 有没有使用叮一下？
  ⑤ 一个月后，你和老婆还在不在用？
```

**建议埋点（极简，不做数据平台）：**

在 `notification_logs` 之外，增加一张轻量的 `event_logs`（可选，V0.1 也可先不做），或在服务端日志里打点：

| 事件 | 触发点 |
| --- | --- |
| `family_created` | 创建家庭成功 |
| `member_joined` | 接受邀请成功 |
| `thing_created` | 创建派活/叮一下 |
| `thing_completed` | 完成小事 |
| `nudge_sent` | 立即叮一下成功 |
| `menu_decided` | 确认今天吃什么 |
| `memory_posted` | 发布留个念 |
| `mp_bound` | 微信提醒绑定成功 |

> `mp_bound` 尤其值得看——它直接反映「推送通道」这个最大技术风险在真实使用中的接受度。

每周拉一次，看趋势即可。

## 十、明确的开发纪律

写代码过程中，以下行为一律禁止（对应《产品需求文档》第二十六章「MVP 明确不做」）：

```text
❌ 开发过程中顺手加「积分」「勋章」
❌ 觉得「评论功能很简单」就加上
❌ 给任务加「进行中」「阻塞」状态
❌ 给家庭加「管理员/普通成员」角色
❌ 做家庭聊天
❌ 做数据统计看板
❌ 引入不必要的第三方库
❌ 为了「以后可能用到」做抽象
```

**任何超出 V0.1 范围的想法，一律记到 `docs/未来需求池.md`，然后继续做手上的事。**
