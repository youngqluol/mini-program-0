**注意事项：**

- ⚠️ **订阅消息的模板 ID 与公众号模板 ID（`MP_TEMPLATE_*`）完全不是一回事，不能互换。**
  判别方法看**字段名**：`first` / `keyword1` 属于公众号，`thing1` / `time23` 属于订阅消息。
  （曾经踩过这个坑，见 `docs/08` §9.4。）
- 模板字段是**固定结构**的，不是任意文本 —— 公共模板库的模板**字段不可改**。
  代码里的 `data` 结构必须严格匹配模板字段名。
- 字段内容有**长度限制**：`thing` 类型**最多 20 个字符**，超长会发送失败（`47003`）。
  代码里 `truncateThing()` 会统一截断。
- `time` 类型只认 `yyyy-MM-dd HH:mm` 或 `yyyy年MM月dd日 HH:mm` 两种写法，
  代码里 `formatSubTime()` 统一格式化。
- **已知缺口**：`time23` 是必填的 `time` 字段，所以**派活不设时间时订阅消息发不出去**，
  会自动降级到站内消息（公众号模板通道不受影响）。见 `docs/未来需求池.md`。

> **重要：订阅消息是辅助通道，不是唯一通道。** wxpush 通道已能独立支撑核心场景，
> 这就是四通道降级的价值。
>
> 自检：`curl https://<你的域名>/api/health/templates` —— 两条通道的模板配置与字段名一次全查完。

**隐私指引填写要点：**

```text
收集的信息：
  ✓ 微信昵称、头像 —— 用于家庭成员识别与展示
  ✓ 相册图片 —— 用于「留个念」记录发布

  ✗ 手机号
  ✗ 位置信息
  ✗ 通讯录

数据删除：用户可自行删除内容；注销账号后 30 天内清除
```

> ⚠️ **只声明实际收集的信息。** 声明了不用的信息会被驳回，收集了没声明的信息会被下架。
>
> ⚠️ **公众号 openid 是 V0.2.1 新增的收集项**，必须一并声明。用户可在「我的 → 微信提醒」随时关闭。

**关于 4.4 隐私弹窗的实现口径（2026-10 核实官方文档）：**

```text
微信的机制（《小程序隐私协议开发指南》）：
  · 2023-10-17 之后，不论 app.json 是否配 __usePrivacyCheck__，隐私功能都会启用
    → 所以**不需要**再配这个字段，配了也没有额外作用
  · 微信自带「官方隐私弹窗」：调用隐私接口时若开发者没有响应
    onNeedPrivacyAuthorization，微信会主动弹一个
  · 官方弹窗只在**用户真正触发隐私接口**的那一刻才弹 —— 首次进来看不到任何提示
```

本项目的做法（`miniprogram/pages/index/index.ts` 的 `checkPrivacy()`）：

| 做什么 | 为什么 |
| --- | --- |
| P01 首页**首次进入主动提示**一次 | 官方弹窗只在「点选图片」时才弹，而提审自查要求「首次进入有弹窗」 |
| **不接管** `onNeedPrivacyAuthorization` | 接管就得自己实现一套弹窗、还要处理「多个隐私接口同时调用」的边界；不接管时官方弹窗自动兜底，效果一致、代码为零 |
| 文案用「**同意**」而不是「授权」 | AGENTS.md §6 把「授权」列为界面禁用词（指微信推送机制那套术语）。这里用「同意」，既满足合规又不破纪律 |
| 允许点遮罩收起 | 不同意也照样能用不碰隐私的功能；等他真要用相册，官方弹窗会再问一次 |

> ⚠️ 本项目目前**只用到 `wx.chooseMedia`（相册）** 一个隐私接口，所以后台指引里
> **只需声明与「相册」相关的那一项**（具体名称以指引页面给的选项为准）。
> `wx.setClipboardData`（复制邀请码）是**写入**剪贴板，不需要声明；分享也不需要。
>
> ⚠️ 本项目**不用地理位置**，所以 `app.json` 里**不需要** `requiredPrivateInfos` ——
> 那个字段是地理位置类接口专用的，别被网上的教程带偏。

**关于 4.6 注销账号的实现口径（v0.2.11 落实）：**

入口在 P20「我的 → 其他 → 注销账号」，**两步确认**：

```text
① confirm()           把后果逐条说清（提审要求「注销后数据有明确的处理说明」）
② confirmWithText()   要求把「注销」两个字打出来 —— 打字让手停一下
        ↓
DELETE /auth/account  →  200 → logout() + reLaunch 回登录页
```

**数据处理口径一句话：「认人的抹掉，家里的事留下但不再署名」。** 完整处理表见 `docs/02` §2.6，三处要记住：

| 数据 | 处理 |
| --- | --- |
| `users` | 匿名化 + 禁用 + **openid 换成墓碑值**（`deleted:<id>`）→ 同一个微信再登录是**全新空账号**，不是登回原号 |
| `family_members` | 保留行，`status=0` + 称谓改为「已注销的家人」（历史仍能追到，但认不出是谁） |
| `notification_logs` | **物理删除**（全库唯一例外，因为它整张表都是个人数据） |

> ⚠️ **两个容易漏的实现要点**（都已在 `smoke:m5` 里被断言锁住）：
> ① 发给他的**未发出**提醒必须显式取消 —— `userIdOfMember()` 不看成员状态，
>    否则注销之后调度器还会继续叮他；
> ② 创建者注销时家庭要**交接给最早加入的成员**（没有别人则解散）——
>    V0.1 没有「转让创建者」，但不能因此拒绝注销。
>
> ⚠️ **验收方式：** `pnpm run smoke:m5`（42 项断言，打真库，覆盖上面全部口径）。
> 它会**物理清理** `smoke5_` 前缀的夹具，只对本地开发库跑。

### 5.A 部署前必读：构建上下文与 `.dockerignore` ⚠️

云托管「自定义部署」要填**两个**东西，填错一个就直接构建失败：

```text
Dockerfile 路径  →  server/Dockerfile
构建上下文        →  仓库根（.）
```

**为什么上下文是仓库根、而不是 `server/`：** Dockerfile 的 COPY 源里有
`package.json`、`pnpm-workspace.yaml`、`packages/shared` —— 这些都在仓库根下。
上下文填成 `server/` 的话，第一步 `COPY package.json ...` 就找不到文件。

由此带来一个**静默的坑**：Docker 只读取**上下文根**的 `.dockerignore`。
规则曾经放在 `server/.dockerignore` 里 —— 那个位置**从不生效，也不报任何错**。

不生效的后果不是「多拷几个文件」这么轻：

```text
本机是 Windows → server/node_modules 里是 **Windows 版 Prisma query engine**
   ↓
容器里 pnpm install（装的是 Linux 版）
   ↓
紧接着 COPY server ./server —— 把宿主机那份**原样盖回去**
   ↓
容器启动即报「找不到当前平台的 query engine」，镜像还白背 45MB+
```

这类错误**只在云端构建时才暴露**，本地怎么跑都复现不出来。

> ✅ 自检：`node tools/check-docker.mjs`（已挂进 `pnpm run check`）——
> 校验每个同阶段 COPY 的源有没有被忽略规则误伤，并断言 `.dockerignore` 的位置。

> ⚠️⚠️ **两套模板 ID 绝对不能互换**（`WX_TEMPLATE_*` 是订阅消息、`MP_TEMPLATE_*` 是公众号）。
> 判别方法看**字段名**：`thing1` / `time23` 属于订阅消息，`first` / `keyword1` 属于公众号。
> 填错的后果是 `47003`，而报错信息几乎无法定位。详见 `server/.env.example` 第 6 / 7 节。

> ⚠️ **漏配不会拦住部署** —— 除 `DATABASE_URL` / `WX_APPID` / `WX_SECRET` / `JWT_SECRET`
> 这四个之外，其余缺了只是**打一行 warn 然后静默降级**。所以部署完**必须看一次启动日志**
> （§5.15），把 warn 列表逐条对完。
>
> ⚠️⚠️ **`INTERNAL_CRON_SECRET` 是特例，它不会「优雅降级」，而是整个提醒功能静默死掉。**
> 没配它时 `InternalSecretGuard` 会**一律拒绝**（这是对的，配置缺失绝不能变成后门）——
> 于是云托管 Cron 打进来的 `tick` 全 403，**提醒永远发不出去**（连站内记录都不会写，
> 因为写入发生在推送那一步），而**服务照常启动、接口照常返回 200**，
> 从外面完全看不出来。它原本不在任何启动校验清单里，漏配时**连一行 warn 都没有**；
> 现在已加进 `configuration.ts` 的告警清单，所以**看到这行 warn 就必须补上**：
>
> ```text
> [env] 以下环境变量未配置，相关功能会自动降级（不影响启动）：
>   INTERNAL_CRON_SECRET
> ```
>
> 补完之后还要**确认 Cron 真的打进来了**：云托管定时任务里能看到调用记录，
> 且服务日志有 `tick` 的痕迹（§5.10 / §5.15）。

### 5.C 关键配置项

```text
服务名称：family-things-api
监听端口：3000（与 Dockerfile 的 EXPOSE 一致）
最小实例数：1（不要设 0，冷启动会影响首屏）
最大实例数：2（家庭规模用不到更多）
CPU / 内存：0.25 核 / 0.5G 起
Dockerfile 路径：server/Dockerfile
构建上下文：仓库根
```

### 5.D 建议的部署顺序

```text
① 开通云托管 → 建环境（建议 test / prod 两个）
② 建 MySQL（utf8mb4 / 时区 +00:00）与 Redis，记下**内网**地址
③ 执行 db/schema.sql（M5-3）
④ 建服务，填 §5.B 的环境变量（COS_* 可先留空）
⑤ 首次部署 —— 目标是「接口能起来」，不是「功能全通」
⑥ **看启动日志**，把「未配置的环境变量」warn 逐条对完（§5.15）
⑦ 配 **2 个**定时任务（M5-4）并确认 `tick` 真的在触发
⑧ 补 COS 凭证（等云部署完再做），跑一次真实上传
```

> ⚠️ **只有 2 个定时任务，别去配第 3 个。** 两个端点是：
>
> ```text
> POST /api/internal/scheduler/tick        * * * * *      每分钟
> POST /api/internal/scheduler/compensate  0 3 * * *      每天凌晨 3 点
> ```
>
> 两个都带 `X-Internal-Secret: <INTERNAL_CRON_SECRET>`（云托管定时任务里填请求头）。
>
> **为什么没有 `recurring`（重复任务生成）这个 Cron：**
> `docs/02` §10.3 里画过一个 `POST /internal/scheduler/recurring-things`，
> 但它**至今没实现，而且 V0.1 也不需要** —— 重复**小事**是在**完成时**生成下一条实例的
> （`thing.service.ts` 的 `spawnNextOccurrence()`，在「完成」那个事务里），
> 不需要每天扫一遍。⚠️ 配一个指向不存在路径的 Cron，只会得到一堆 404。
>
> ⚠️ 另外注意 `compensate` 是**每天一次**、不是每小时 —— `docs/02` §10.2 写的就是
> `0 3 * * *`。补偿是**运维兜底**，不是产品行为，低频是刻意的。

> 💡 **部署不需要本地 Docker** —— 云托管是**云端构建**，只把代码推上去就行。
> 本地 Docker 只服务于「本地跑 MySQL + Redis」。

| 小程序注册 + 认证 | 30 分钟 | ✅ 已完成 |
| 服务类目审核 | 1–3 个工作日 | ✅ 已完成 |
| 订阅消息模板审核 | **0（公共模板库现成模板，无需审核）** | ✅ 已完成 |
| **测试号申请** | **5 分钟（扫码即得）** | **否——这是它最大的好处** |
| **Worker 部署 + 验证** | **1–2 小时** | **⚠️ 阻塞 M2 推送主线** |
| 隐私指引审核 | 1–2 个工作日 | 否（但阻塞上线） |
| 云托管环境搭建 | 2–4 小时 | 否 |
| MySQL + Redis 开通 | 1 小时 | 否 |
| 域名配置 | 30 分钟（云托管免备案） | 否 |
| 小程序提审 | 1–3 个工作日 | 否 |
| 本地 Docker Desktop | — | **否 —— 云托管是云端构建，本地有没有 Docker 都不影响上线** |

> 💡 **部署不需要本地 Docker。** 它只服务于「本地跑 MySQL + Redis 开发」（§七 7.4），
> 而 M5-1 的镜像由**云托管云端构建** —— 本地只要把代码推上去。

> **勘误（2026-10-06）**：原先预估「订阅消息模板审核 1–3 个工作日」是**错的**。
> 实际是在**公共模板库**里挑现成模板，选完即用，**没有审核环节**。
> 这也意味着「选完类目再申请模板」这条依赖关系比预想的宽松得多。

**结论：第 1 天就把 1.6、3.1（测试号 + Worker）、4.1 全部提交。**
审核期间并行做本地环境（M0-19 ~ M0-21）和 M1 的骨架开发，时间完全够用。

> **关键洞察：测试号通道「5 分钟申请、无需审核」**，这是它相比「等小程序类目审核」
> 的压倒性优势。**主线不应该被审核卡住。**

## 十二、决策记录

| 决策 | 结论 | 理由 |
| --- | --- | --- |
| 小程序端框架 | 原生微信小程序 + TS | 功能不复杂，无编译层，调试最直接 |
| 后端形态 | 微信云托管容器（NestJS） | 无冷启动、完整框架能力、本地开发体验好 |
| 后端框架 | **NestJS + Prisma** | 前后端同语言 + 类型共享（`packages/shared`）；模块化匹配领域划分；个人开发者最贵的是调试时间 |
| 运行时 | **Node 22 LTS** | Node 20 已于 2026-04-30 EOL |
| 数据库 | 云托管 MySQL 8.0 | 保留已设计好的 11 张关系表 |
| 云开发定位 | 只用于云存储等能力 | 其云数据库是文档型，与关系模型冲突 |
| **推送通道** | **四通道降级**：公众号模板消息（wxpush）→ 订阅消息 → 站内消息 → 首页 | 订阅消息「1 授权 = 1 条」且必须接收人本人授权，**「阿妈叮阿爸」走不通** |
| **wxpush 定位** | **V0.1 验证期采用，产品化前拆除** | 换来「无限次 + 能推给别人」，代价是依赖测试号；已用通道开关隔离，拆除时只关配置 |
| **V0.1 是否上架** | **建议先不上架** | 不上架就不必拆 wxpush，推送体验最好；先验证「家人愿不愿意用」 |
| 订阅消息 | 一次性订阅（降为辅助通道） | 长期订阅仅限特定行业，本项目拿不到 |
| 域名 | 云托管默认域名 | 免 ICP 备案，节省 7–20 天 |
| 权限模型 | 成员平等 + 创建者管理权 | 避免变成「家庭版飞书」 |
| 是否做原生 App | **不做**（至少在小程序验证通过之前） | 解决推送但摧毁「家人愿意用」这个前提，详见 PRD 6.5.4 |
