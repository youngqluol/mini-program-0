## 三、推送通道准备 ⭐（V0.1 最关键）

> **为什么这一章最重要：** 小程序订阅消息只能「1 次授权 = 1 条」，且必须由**接收人本人**授权，
> 「阿妈叮阿爸」这个核心场景根本走不通。wxpush 通道解决了这个问题（PRD 6.5.7）。
>
> **完整方案见 `docs/08-wxpush推送集成方案.md`。**

> 少了这两个字段，模板消息就退化成机械通知了 —— 这两个字段承载的是
> 「阿妈，有个活儿到你啦～」和「有空的时候弄一下就行 😊」。
> 完整内容见 `docs/08` §10.2，可直接粘贴。
>
> ⚠️ **字段名必须与 `notify.templates.ts` 的 `MP_TEMPLATE_SPECS` 严格一致**，
> 否则微信返回 `47003`，且报错信息几乎无法定位。
>
> ⚠️ **3.1.11 是整个 M0 最重要的验证**，直接决定「阿妈能不能叮到阿爸」。
> 见 `docs/05` 的 M0-V1 / M0-V2。

| 3.2.4 | 选用「完成回执」模板 | **日程任务完成提醒**（模板编号 77364）<br>字段：`thing1` 备忘事项 / `thing2` 完成人 / `time3` 完成时间 | ✅ |
| 3.2.5 | 记录 3 个 templateId | 已填入 `server/.env` | ✅ |
| 3.2.6 | 配置模板到后端 | `WX_TEMPLATE_TASK` / `WX_TEMPLATE_NUDGE` / `WX_TEMPLATE_DONE` | ✅ |
| 3.2.7 | 配置到生产环境 | 云托管环境变量里同样要配这三个 | ⬜ |
| 3.2.8 | 实探链路 | `node tools/probe-subscribe.mjs <你的openid> TASK` | ⬜ |

**注意事项：**

- ⚠️ **订阅消息的模板 ID 与公众号模板 ID（`MP_TEMPLATE_*`）完全不是一回事，不能互换。**
  判别方法看**字段名**：`first` / `keyword1` 属于公众号，`thing1` / `time23` 属于订阅消息。
  （曾经踩过这个坑，见 `docs/08` §9.4。）
- 模板字段是**固定结构**的，不是任意文本 —— 公共模板库的模板**字段不可改**。
  代码里的 `data` 结构必须严格匹配模板字段名。
- 字段内容有**长度限制**：`thing` 类型**最多 20 个字符**，超长会发送失败（`47003`）。
  代码里 `truncateThing()` 会统一截断。
- `time` 类型只认 `yyyy-MM-dd HH:mm` 或 `yyyy年MM月dd日 HH:mm` 两种写法，
  代码里 `formatSubTime()` 统一格式化。
- **已知缺口**：`time23` 是必填的 `time` 字段，所以**派活不设时间时订阅消息发不出去**，
  会自动降级到站内消息（公众号模板通道不受影响）。见 `docs/未来需求池.md`。

> **重要：订阅消息是辅助通道，不是唯一通道。** wxpush 通道已能独立支撑核心场景，
> 这就是四通道降级的价值。
>
> 自检：`curl https://<你的域名>/api/health/templates` —— 两条通道的模板配置与字段名一次全查完。

```text

  ✓ 微信昵称、头像 —— 用于家庭成员识别与展示
  ✓ 相册图片 —— 用于「留个念」记录发布

  ✓ 家庭称谓 —— 用于在消息里正确称呼你

不收集：
  ✗ 手机号
  ✗ 位置信息
  ✗ 通讯录
  ✗ 微信好友关系

数据存储：腾讯云（微信云托管），境内存储

```

> ⚠️ **只声明实际收集的信息。** 声明了不用的信息会被驳回，收集了没声明的信息会被下架。
>
> ⚠️ **公众号 openid 是 V0.2.1 新增的收集项**，必须一并声明。用户可在「我的 → 微信提醒」随时关闭。

### 提审信息

- [ ] 填写功能页面路径（至少首页 + 各 Tab 页）
- [ ] 填写测试账号（如果审核员需要登录才能看）

  - 建议：提审时**临时开启一个「体验模式」**，或提供邀请码 + 说明
  - 更简单：审核时把首页做成未登录也能看到示例数据
- [ ] 填写类目对应的功能说明
- [ ] 截图符合规范（不含测试数据、不含二维码）

## 十、时间预估

| 事项 | 预估耗时 | 是否阻塞开发 |
| --- | --- | --- |
| 小程序注册 + 认证 | 30 分钟 | ✅ 已完成 |
| 服务类目审核 | 1–3 个工作日 | ✅ 已完成 |
| 订阅消息模板审核 | **0（公共模板库现成模板，无需审核）** | ✅ 已完成 |
| **测试号申请** | **5 分钟（扫码即得）** | **否——这是它最大的好处** |
| **Worker 部署 + 验证** | **1–2 小时** | **⚠️ 阻塞 M2 推送主线** |
| 隐私指引审核 | 1–2 个工作日 | 否（但阻塞上线） |
| 云托管环境搭建 | 2–4 小时 | 否 |
| MySQL + Redis 开通 | 1 小时 | 否 |
| 域名配置 | 30 分钟（云托管免备案） | 否 |
| 小程序提审 | 1–3 个工作日 | 否 |

> **勘误（2026-10-06）**：原先预估「订阅消息模板审核 1–3 个工作日」是**错的**。
> 实际是在**公共模板库**里挑现成模板，选完即用，**没有审核环节**。
> 这也意味着「选完类目再申请模板」这条依赖关系比预想的宽松得多。

**结论：第 1 天就把 1.6、3.1（测试号 + Worker）、4.1 全部提交。**
审核期间并行做本地环境（M0-19 ~ M0-21）和 M1 的骨架开发，时间完全够用。

> **关键洞察：测试号通道「5 分钟申请、无需审核」**，这是它相比「等小程序类目审核」
> 的压倒性优势。**主线不应该被审核卡住。**

## 十二、决策记录

| 决策 | 结论 | 理由 |
| --- | --- | --- |
| 小程序端框架 | 原生微信小程序 + TS | 功能不复杂，无编译层，调试最直接 |
| 后端形态 | 微信云托管容器（NestJS） | 无冷启动、完整框架能力、本地开发体验好 |
| 后端框架 | **NestJS + Prisma** | 前后端同语言 + 类型共享（`packages/shared`）；模块化匹配领域划分；个人开发者最贵的是调试时间 |
| 运行时 | **Node 22 LTS** | Node 20 已于 2026-04-30 EOL |
| 数据库 | 云托管 MySQL 8.0 | 保留已设计好的 11 张关系表 |
| 云开发定位 | 只用于云存储等能力 | 其云数据库是文档型，与关系模型冲突 |
| **推送通道** | **四通道降级**：公众号模板消息（wxpush）→ 订阅消息 → 站内消息 → 首页 | 订阅消息「1 授权 = 1 条」且必须接收人本人授权，**「阿妈叮阿爸」走不通** |
| **wxpush 定位** | **V0.1 验证期采用，产品化前拆除** | 换来「无限次 + 能推给别人」，代价是依赖测试号；已用通道开关隔离，拆除时只关配置 |
| **V0.1 是否上架** | **建议先不上架** | 不上架就不必拆 wxpush，推送体验最好；先验证「家人愿不愿意用」 |
| 订阅消息 | 一次性订阅（降为辅助通道） | 长期订阅仅限特定行业，本项目拿不到 |
| 域名 | 云托管默认域名 | 免 ICP 备案，节省 7–20 天 |
| 权限模型 | 成员平等 + 创建者管理权 | 避免变成「家庭版飞书」 |
| 是否做原生 App | **不做**（至少在小程序验证通过之前） | 解决推送但摧毁「家人愿意用」这个前提，详见 PRD 6.5.4 |
