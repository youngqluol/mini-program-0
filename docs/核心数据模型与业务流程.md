## 一、核心设计思想

整个产品围绕一个核心概念：

> **家里有一件小事 → 需要谁处理 → 什么时候处理 → 要不要提醒 → 最终有没有完成。**

因此：

* 「派活」= 把一件小事交给某个人
* 「叮一下」= 在某个时间提醒某个人
* 「吃啥呢」= 帮家里决定一件小事，并可以进一步产生“派活”
* 「留个念」= 把已经发生的家庭小事记录下来

形成：

**吃啥呢 → 决定 → 派活 → 叮一下 → 完成 → 留个念**

# 二、用户与家庭模型

## 1. User 用户

用户首先是一个独立账号。

```text
User
├── id
├── openid            （小程序 openid，登录身份）
├── unionid
├── mp_openid         （公众号 openid，推送用；与小程序 openid 不同值）
├── mp_bound_at       （绑定公众号的时间，NULL 表示未绑定）
├── 昵称
├── 头像
├── 创建时间
└── ...
```

> **⚠️ 一个必须记住的坑：openid 是「用户 × 应用」维度的。**
> 同一个人在**小程序**里有一个 openid，在**公众号**里有**另一个** openid，两者无法互相推导。
> 所以推送通道要用的公众号 openid 必须**单独一列** `mp_openid` 存，不能复用 `openid`。
> 绑定链路见 [`08-wxpush推送集成方案.md`](08-wxpush推送集成方案.md) 第四章。

用户和家庭不是一对一关系。

例如：

```text
用户 A
├── 家庭 1：阿爸
└── 家庭 2：儿子
```

这意味着：

> **“阿爸”不是用户的身份，而是用户在某个家庭中的称谓。**

---

## 2. Family 家庭

```text
Family
├── id
├── name
├── owner_member_id
├── created_at
└── ...
```

例如：

```text
家有小事
└── 我们家
```

以后甚至可以存在：

```text
我家
爸妈家
爷爷奶奶家
```

同一个用户可以加入多个家庭。

---

## 3. FamilyMember 家庭成员

这是非常重要的一张表。

```text
FamilyMember
├── id
├── family_id
├── user_id
├── role_name
├── joined_at
└── status
```

例如：

| 用户  | 家庭  | 称谓 |
| --- | --- | -- |
| 用户A | 我们家 | 阿爸 |
| 用户B | 我们家 | 阿妈 |
| 用户C | 我们家 | 宝宝 |
| 用户D | 我们家 | 奶奶 |

系统以后展示：

> 阿妈给阿爸派了一个活

而不是：

> 张三给李四派了一个活。

这会让产品更像一个真正的“家庭工具”。

# 三、核心对象：小事

我建议数据库中建立一个核心表：

```text
family_things
```

它代表：

> **家里的某一件小事。**

例如：

```text
拿快递
交物业费
明天带水杯
买牛奶
晚上做番茄炒蛋
提醒阿爸给宝宝洗澡
```

基础结构：

```text
family_things
├── id
├── family_id
├── creator_member_id
├── type
├── title
├── content
├── assignee_member_id
├── visibility
├── status
├── due_at
├── created_at
└── updated_at
```

### type

```text
TASK      派活
REMINDER  提醒
```

所以：

### 派活

```text
type = TASK
```

### 叮一下

```text
type = REMINDER
```

而：

> 阿妈让阿爸明天下午6点拿快递，并在5点50提醒阿爸。

实际上仍然是一件：

```text
TASK
```

只不过这个 TASK 同时拥有一个提醒配置。

# 四、为什么不把“派活”和“叮一下”完全拆开？

因为真实家庭场景里，两者经常同时出现。

例如：

> 明天下午6点帮我拿快递。

它其实包含：

```text
一件事情
    ↓
拿快递
    ↓
交给阿爸
    ↓
明天18:00
    ↓
18:00前提醒
```

所以数据关系应该是：

```text
             ┌── 派给谁
             │
             ↓
         ┌─────────┐
         │  一件小事 │
         └────┬────┘
              │
              ├── 是否需要完成
              │
              └── 是否需要提醒
                       ↓
                   Reminder
```

这样以后扩展会非常舒服。

---

# 五、Reminder 提醒模型

单独建立：

```text
thing_reminders
```

例如：

```text
thing_reminders
├── id
├── thing_id
├── recipient_member_id
├── remind_type
├── remind_at
├── recurrence_rule
├── status
├── last_sent_at
└── created_at
```

支持：

### 立即叮

```text
remind_type = NOW
```

例如：

> 叮一下阿妈：“记得拿快递”

点击之后立即发送。

---

### 指定时间

```text
remind_type = SCHEDULED
remind_at = 2026-09-27 18:00
```

---

### 重复提醒

例如：

> 每天晚上8点提醒阿爸给宝宝刷牙。

可以保存：

```text
recurrence_rule
```

第一版不需要自己设计特别复杂的重复规则。

可以先支持：

```text
每天
每周
每月
工作日
自定义
```

以后再升级复杂规则。

# 六、一个非常重要的设计：任务和提醒可以同时存在

例如阿妈创建：

> 明天下班记得买牛奶。

系统中：

```text
family_things
    ↓
TASK
    ↓
assignee = 阿爸
    ↓
due_at = 明天
```

同时：

```text
thing_reminders
    ↓
recipient = 阿爸
    ↓
remind_at = 明天 17:30
```

最终用户看到：

> 🥛 买牛奶
> 阿爸
> 明天完成
> 🔔 17:30提醒

这样就非常符合产品定位。

---

# 七、任务状态不要复杂

第一版坚决不要搞：

```text
待处理
已接单
处理中
等待确认
已提交
审核中
...
```

家庭工具不需要这些。

只需要：

```text
PENDING   待完成
COMPLETED 已完成
CANCELLED 已取消
```

例如：

```text
阿妈 → 派活 → 阿爸

        ↓

    🥛 买牛奶

        ↓

      待完成

        ↓

    阿爸完成

        ↓

      已完成
```

完成后可以给阿妈一个非常轻的反馈：

> ❤️ 阿爸已经把「买牛奶」搞定啦

**不需要“催办”。**

这和我们之前确定的：

> **只提醒，不监督**

是一致的。

---

# 八、家庭权限

这里我建议继续保持简单。

### 普通家庭成员

都可以：

* 派活
* 叮一下
* 吃啥呢
* 留个念
* 邀请家庭成员

### 家庭创建者

额外拥有：

* 修改家庭名称
* 移除成员
* 解散家庭
* 管理家庭基础设置

不要把家庭成员设计成：

```text
超级管理员
管理员
普通成员
访客
...
```

否则很快就会变成一个“企业管理系统”。

这个产品最重要的是：

> **家庭成员之间是平等的。**

---

# 九、“叮一下”的权限

这里我建议：

### 叮一下默认私密

例如：

> 阿妈 → 叮 → 阿爸

只有：

```text
阿妈
阿爸
```

能看到。

其他家庭成员不需要知道。

因为：

> “明天记得拿身份证。”

这种事情没有必要让奶奶也看到。

---

# 十、“派活”的权限

派活默认家庭可见。

例如：

> 阿妈派给阿爸：晚上买菜。

家庭其他成员可以看到：

```text
🛒 买菜
阿爸
今天 18:00
待完成
```

但这不是为了监督。

而是因为：

> **家庭成员需要知道家里有哪些事情已经有人负责了。**

例如阿妈就不会再次问：

> “菜买了吗？”

---

# 十一、“留个念”

单独建立：

```text
family_memories
```

例如：

```text
family_memories
├── id
├── family_id
├── creator_member_id
├── content
├── visibility
├── created_at
└── ...
```

附件可以另外：

```text
memory_attachments
```

支持：

```text
文字
图片
```

第一版甚至不需要评论、点赞。

首页可能出现：

> 📖 留个念
>
> 今天宝宝第一次自己穿鞋 👟
> 阿妈 · 2026-09-26

这其实会慢慢形成一个很有价值的东西：

> **属于这个家庭自己的时间线。**

# 十二、“吃啥呢”数据模型

第一版不要把它做得太复杂。

建立：

```text
menu_items
```

例如：

```text
番茄炒蛋
红烧肉
酸辣土豆丝
宫保鸡丁
饺子
面条
...
```

来源：

```text
SYSTEM   系统菜谱
FAMILY   家庭自定义
```

> **⚠️ v0.2.1 修订：系统菜谱不再入库。**
> 原先计划把系统菜谱作为 `family_id = NULL` 的记录写进 `menu_items`，现在改为**代码常量**
> （`miniprogram/config/default-menu.ts`）。
> 原因：系统菜谱是**静态内容**，不需要查询、不需要关联、不会变；放进数据库只会让
> 「新建家庭」多一步 seed、让迁移多一份数据依赖。
> 因此 `menu_items` 表**只存家庭自己添加的菜**，`family_id` 恒为非空。
> 随机决策时把「代码常量 + 本家庭自定义」合并成候选池。

## 吃啥呢的核心流程

打开：

> 🍽️ 吃啥呢

看到：

```text
今天吃什么？

        🎰
     转一转

[番茄炒蛋]
```

然后：

```text
      番茄炒蛋

[就吃这个]

[换一个]
```

点击：

### 就吃这个

可以出现：

```text
今天决定吃：

🍅 番茄炒蛋

要不要派个活？

[派给阿爸]
[派给阿妈]
[不用派]
```

如果选择：

> 派给阿爸

直接进入：

```text
派活
```

于是：

```text
吃啥呢
   ↓
决定吃什么
   ↓
派活
   ↓
谁去做
   ↓
需要提醒吗
```

这就是整个产品非常自然的一条业务链。

首页的核心不是“展示功能”。

> **打开之后，马上知道今天家里有什么事。**

# 十四、底部导航

四个（v0.2.1 由三个扩展为四个，新增「我的」）：

```text
┌────────┬────────┬────────┬────────┐
│  🏠    │  🍽️    │  📖    │  👤    │
│  家里  │ 吃啥呢 │ 留个念 │  我的  │
└────────┴────────┴────────┴────────┘
```

而：

```text
叮一下
派活
```

不要放到底部导航。

它们应该作为首页上的**高频操作入口**。

原因很简单：

> “叮一下”和“派活”是动作，不是内容频道。

「我的」承载的是**低频但必须有**的东西：家庭设置、成员管理、**微信提醒开关**、消息中心、关于。
它们不该占用首页的黄金位置，但也不能藏得找不到——所以给一个 Tab。

> 页面编号对应关系见 [`03-页面原型与交互流程.md`](03-页面原型与交互流程.md)：
> P01 家里 / P11 吃啥呢 / P16 留个念 / **P20 我的**（含 **P21 微信提醒**）。

# 十六、第一版完整业务链

最终我们希望用户第一次使用，就能走通这样一个闭环：

```text
              创建家庭
                  ↓
             邀请阿妈加入
                  ↓
             邀请阿爸加入
                  ↓
                  家
                  │
       ┌──────────┼──────────┐
       ↓          ↓          ↓
    叮一下      派活       吃啥呢
       │          │          │
       │          │       决定吃什么
       │          │          │
       │          │       要不要派活
       │          │          ↓
       │          └──────→ 派活
       │                     │
       └─────────────────────┤
                             ↓
                         指定成员
                             ↓
                          是否提醒
                             ↓
                     消息送达（四通道降级）
                             ↓
                           完成
                             ↓
                    “阿爸已经搞定啦 ❤️”
```

其中「消息送达」按优先级降级，任何一环失败都自动落到下一环：

```text
① 公众号模板消息（wxpush）  ← 无次数限制，但用户需先绑定
        ↓ 失败/未绑定
② 小程序订阅消息（一次性）  ← 需用户授权，一次授权一条
        ↓ 失败/无额度
③ 站内消息                  ← 永不失败，进「我的 · 消息中心」
        ↓
④ 首页「今天家里有什么事」  ← 产品承诺底线，用户主动打开就一定看得到
```

> 完整设计见 [`01-技术架构与技术选型.md`](01-技术架构与技术选型.md) 第五章、
> [`08-wxpush推送集成方案.md`](08-wxpush推送集成方案.md)。
> **注意：** 「完成」这个动作**不依赖**通知是否送达——通知只是提醒，不是监督。

然后某一天：

```text
📖 留个念

“今天一家人第一次一起包饺子。”
```

这样产品就完整了。

# 十七、MVP 数据库建议

如果后端使用 MySQL，我建议第一版先控制在这些核心表：

```text
users
families
family_members
family_invites

family_things
thing_reminders

menu_items
meal_records

family_memories
memory_attachments

notification_logs
```

一共大约 **11 张表**。

> **这 11 张表的可执行 DDL 已经写好：[`db/schema.sql`](../db/schema.sql)。**
> 相比 v0.1 的设想，落地时有四处变化：
> 1. `users` 增加 `mp_openid` / `mp_bound_at`（公众号推送绑定）
> 2. `notification_logs.channel` 增加取值 `3 = 公众号模板消息`；`status` 增加 `5 = 未绑定提醒跳过`
> 3. `menu_items` 只存家庭自定义菜（系统菜谱改为代码常量）
> 4. **全库不做物理 DELETE**，一律状态位逻辑删除（`status` / `enabled` / `deleted_at`）

不要一开始就设计几十张表。

尤其是：

> 积分、勋章、统计、复杂权限、聊天、评论、点赞……

全部先不要。

# 十八、第一版真正应该验证什么

这个产品最大的风险其实不是技术。

而是：

> **你的家人是不是真的愿意用。**

所以 MVP 不应该追求功能多。

应该验证三个动作：

### 第一件

老婆突然想到：

> “明天记得带宝宝的水杯。”

她会不会打开：

**🔔 叮一下**

---

### 第二件

老婆想说：

> “晚上你去买菜。”

她会不会打开：

**🎯 派活**

---

### 第三件

晚上：

> “今天吃啥？”

她会不会打开：

**🍽️ 吃啥呢**

---

如果这三个动作真的成为家庭习惯，那么这个产品就已经成立了一半。
