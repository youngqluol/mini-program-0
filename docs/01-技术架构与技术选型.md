## 一、最终技术栈

| 层次 | 选型 | 说明 |
| --- | --- | --- |
| 小程序端 | **原生微信小程序 + TypeScript** | 无编译层、调试最直接、性能最好；功能复杂度不高，不需要 uni-app/Taro |
| 小程序 UI | 自定义组件 + 原生组件 | 不引入重型 UI 库，保证包体积与视觉统一 |
| 状态管理 | 轻量全局 store（`mobx-miniprogram` 或自研） | 只有「当前用户 / 当前家庭」两个全局态，不需要大型状态库 |
| 后端框架 | **NestJS（Node 22 LTS + TypeScript）** | 与小程序端同语言；模块化天然匹配「家庭 / 小事 / 提醒 / 菜单 / 记录」的领域划分 |
| ORM | **Prisma** | Schema 即文档，迁移可控，类型安全 |
| 数据库 | **MySQL 8.0（微信云托管 MySQL）** | 完整保留已设计好的 11 张表 |
| 缓存 | **Redis（腾讯云，内网调用）** | 登录态、订阅额度计数、定时任务锁、幂等、绑定码 |
| 对象存储 | **云开发云存储 / COS** | 头像、留个念图片 |
| 部署 | **微信云托管（容器，自定义 Dockerfile）** | 免运维、免域名备案、天然内网调用 MySQL/Redis |
| 定时任务 | **云托管定时任务（Cron）触发 HTTP 端点** | 扫描 `thing_reminders.next_remind_at` 并下发提醒 |
| 消息通知 | **四通道降级**（见第五章） | 公众号模板消息（wxpush）→ 小程序订阅消息 → 站内消息 → 首页 |
| 推送服务 | **Cloudflare Workers（wxpush）** | V0.1 验证期主力通道；无需服务器，免费额度足够 |
| 日志监控 | 云托管日志 + 结构化日志（pino） | `notification_logs` 表承担业务级追踪 |

> **⚠️ Node 版本提示：** 早期文档写的「Node.js 20 LTS」**已于 2026-04-30 EOL**，不要再使用。
> 统一采用 **Node 22 LTS**（支持至 2027-04），本地 `.nvmrc` / Dockerfile / 云托管三处保持一致。

## 三、关键决策与理由

### 3.0 为什么后端用 NestJS 而不是更轻的框架

| 候选 | 优势 | 为什么不选 |
| --- | --- | --- |
| **NestJS（选定）** | 前后端同语言 + 类型共享；守卫/拦截器/管道/DI 开箱即用；模块化天然匹配领域划分 | — |
| 云开发云函数 | 免运维、极低成本 | 冷启动明显；无中间件生态；定时任务能力弱；数据库连接每次重建 |
| Express / Koa 裸写 | 最轻 | 需要自己搭一整套结构，个人项目反而更慢 |
| Hono 等新框架 | 轻量现代 | 生态与中文资料少，遇到问题无处可问 |
| Go / Java | 性能好 | 与前端不同语言，**失去类型共享**，个人项目不划算 |

**决定性理由只有一条：`packages/shared` 里改一个字段，前后端编译期同时报错。** 这省下的是联调时间，而联调时间是个人开发者最贵的东西。

### 3.1 为什么不用云开发自带的「云数据库」

云开发云数据库是**文档型数据库（类 MongoDB）**，没有 JOIN、没有事务、没有外键，也没有 SQL 迁移工具。而你现有的 11 张表设计是一套关系模型：

```text
family_things.assignee_member_id → family_members.id → users.id
```

这类「小事 → 成员 → 用户 → 家庭」的多跳关联，在文档库里要么做冗余嵌套（数据一致性难保证），要么做多次查询（性能与代码复杂度上升）。

**结论：保留 MySQL，用云托管一键部署 MySQL 实例。** 云开发只用来做「云存储 + 订阅消息」这类能力型服务。

### 3.2 为什么后端用容器（云托管）而不是云函数

| 维度 | 云函数 | 云托管容器（选定） |
| --- | --- | --- |
| 冷启动 | 明显，首屏接口容易 300ms+ | 常驻，无冷启动 |
| 框架能力 | 单函数，无中间件生态 | 完整 NestJS：守卫、拦截器、管道、DI |
| 定时任务 | 需配置定时触发器 | 原生 Cron，可跑长任务 |
| 数据库连接 | 每次冷启动建连，需连接池外置 | 常驻连接池 |
| 本地开发 | 需要模拟层 | 直接 `npm run start:dev` |
| 迁移成本 | 换平台要重写 | Docker 镜像，可迁移到任意容器平台 |

个人开发者的核心成本是**调试时间**，不是服务器钱。容器的本地开发体验和云函数不在一个量级。

### 3.3 鉴权方案

不使用云开发的免鉴权调用，走标准链路：

```text
小程序 wx.login()
        ↓ code
POST /api/auth/login  { code }
        ↓
后端用 code + appid + secret 调 code2Session
        ↓ 得到 openid / session_key
查或建 users 记录
        ↓
签发自有 JWT（payload: userId, openid），有效期 7 天
        ↓
小程序存入 storage，后续请求带 Authorization: Bearer <token>
        ↓
后端 JwtGuard 解析 → 注入 currentUser
        ↓
FamilyMemberGuard 校验「当前用户是否属于该 familyId」
```

**关键点：`familyId` 永远不从请求体信任，而是从 token 推导或做归属校验。** 否则任意用户可越权读取他人家庭数据。

- `session_key` **不落库**，需要时存 Redis（`session:{userId}`），用于解密敏感数据（如手机号，V0.1 用不到）。
- JWT 密钥放云托管环境变量，不进代码库。

### 3.4 权限模型落地

严格对应文档中的「家庭成员平等」原则，代码里只做两层判断：

```text
① 是不是这个家庭的成员？（FamilyMemberGuard）
② 这条内容是不是家庭可见？（visibility 字段过滤）
```

具体规则：

| 资源 | 可见性规则 |
| --- | --- |
| `family_things` type=TASK | `visibility=1` → 全家庭可见；`visibility=2` → 仅创建人 + 执行人 |
| `family_things` type=REMINDER | **默认 `visibility=2`**，仅发起人 + 接收人 |
| `family_memories` | `visibility=1` 家庭可见；`visibility=2` 仅自己 |
| 家庭管理操作（改名/移除成员/解散） | 仅 `families.owner_member_id` 对应成员 |

**不做角色表、不做权限矩阵、不做审批流。**

### 3.5 删除策略

| 对象 | 策略 |
| --- | --- |
| 小事 / 提醒 | 不物理删除，改 `status=3 已取消` |
| 家庭记录 | 不物理删除，改 `status=0` |
| 成员退出家庭 | 不删除记录，`family_members.status=0` + `left_at`，历史数据保留 |
| 家庭解散 | `families.status=0`，数据保留（可支持后续恢复） |
| 菜单项 | `enabled=0` 停用，不删除（避免历史 `meal_records` 关联断裂） |

**全库不做 `DELETE` 语句。** 这是有意的：家庭产品里「删掉的历史」往往比「留着的历史」更让人后悔。

## 四、定时任务设计

这是「叮一下」能否成立的技术底座。

### 4.1 调度链路

```text
云托管定时任务（每分钟触发）
        ↓ POST /internal/scheduler/tick  （内部密钥校验）
        ↓
SELECT * FROM thing_reminders
 WHERE status = 1
   AND next_remind_at <= NOW()
 LIMIT 200
        ↓
对每条提醒：
  ① Redis 加锁  lock:reminder:{id}，TTL 60s，防多实例重复发送
  ② 组装消息内容（家庭成员称谓 + 小事标题 + 时间）
  ③ 写入 notification_logs（status=1 待发送）
  ④ 调微信订阅消息 API
  ⑤ 成功 → logs.status=2，reminder.sent_count+1，last_sent_at=NOW()
     失败 → logs.status=3，记录 error_code / error_message
  ⑥ 若为重复提醒 → 计算下一次 next_remind_at；否则 status=2
```

### 4.2 幂等与防重

| 风险 | 措施 |
| --- | --- |
| 多实例并发扫描同一条 | Redis `SET NX EX` 分布式锁 |
| 网络超时导致重复发送 | `notification_logs` 加 `thing_id + type + 时间窗` 判重 |
| 任务执行到一半崩溃 | `status` 状态机单向推进，重试只处理 `status=1` 的记录 |
| 时钟漂移 | 时间戳统一由应用侧 `new Date()` 生成，不依赖数据库 `NOW()` |

### 4.3 时间与时区

> **v0.2.2 修正：** 本节原结论是「MySQL 连接串指定 `timezone=+08:00`，所有 DATETIME 存北京时间」。
> 经查证**这个方案不成立** —— Prisma 的 MySQL 连接器不支持该参数
> （feature request `prisma/orm#29517` 至今 open，写进连接串会被静默忽略），
> 它固定按 UTC 处理 DATETIME。下面是修正后的方案。

**结论：存储层统一 UTC，北京时间只在接口层格式化一次。**

Prisma 的实际行为（决定了我们只能这么选）：

| 操作 | 行为 |
| --- | --- |
| 写 `new Date()` / `@default(now())` | 按 **UTC** 格式化成字符串，作为绑定参数发出 |
| 读 DATETIME | 把库里的串**无条件当作 UTC**，构造带 `Z` 的 Date |
| DATETIME 列本身 | 原样存墙钟字符串，不随会话 `time_zone` 转换 |

所以「应用写入 → Prisma 读回」是自洽的；**但绕过 Prisma 写入的数据会差 8 小时**。

落地约定：

| 项 | 值 | 说明 |
| --- | --- | --- |
| MySQL 时区 | `+00:00` | 与 Prisma 对齐，避免 `DEFAULT CURRENT_TIMESTAMP` 产出北京时间 |
| 时间戳来源 | Prisma 侧 `@default(now())` / `@updatedAt` | 不用 `dbgenerated("CURRENT_TIMESTAMP")` |
| 容器时区 | `TZ=Asia/Shanghai` | 让本地 getter 直接产出北京时间 |
| 接口输出 | `common/serialize/beijing-time.ts` | 唯一的格式化出口 |
| 前端传入 | `"YYYY-MM-DD HH:mm:ss"` | 用 `parseBeijingDateTime()` 解析（显式拼 `+08:00`） |

**用户侧体验不变**：前端只看到北京时间，业务代码里不做任何时区换算 ——
「减少心智负担」这个原始目标是通过**把换算收敛到一个函数**达成的，而不是靠存储层用本地时间。

> **代价（要知道）：** 直接连数据库看数据时，时间是 UTC，比北京时间少 8 小时。
> 这是标准做法（存储用 UTC 消除歧义），但看库时心里要有数。

## 五、⚠️ 最大技术风险：消息送达

**这是整个 V0.1 最需要提前处理的问题，必须在写第一行业务代码之前就设计好。**

> **v0.2.1 重要变更：** 本章原本的结论是「只能靠一次性订阅额度累积」，**这个结论是不完整的**。
> 现已确认可接入 **wxpush（公众号模板消息）** 作为主力通道，订阅消息降为辅助。
> 完整技术方案见 **`docs/08-wxpush推送集成方案.md`**，产品决策见 PRD 6.5.7。

### 5.1 问题：为什么不能只依赖订阅消息

微信订阅消息分两类：

| 类型 | 下发能力 | 开放范围 |
| --- | --- | --- |
| **一次性订阅** | 用户授权一次 → 只能下发**一条**消息 | **所有小程序可用** |
| 长期订阅 | 授权一次 → 可长期下发多条 | **仅政务民生、医疗、交通、金融、教育等特定行业** |

「家有小事」属于家庭生活工具，**拿不到长期订阅资质**。更致命的是**授权主体的错位**：

```text
阿妈想「明天 7:00 提醒阿爸带水杯」

阿妈在自己手机上操作  →  拿到的是「阿妈自己」的订阅授权
7:00 要推的是「阿爸」  →  阿爸没授权过  →  这条推送发不出去  ❌
```

> **一次性订阅的授权必须由「接收消息的那个人」本人完成。**
> 这是家庭协作类产品的天然杀手——「帮别人设提醒」是核心场景，却正好卡在这里。

### 5.2 解法：四通道降级

```text
┌─────────────────────────────────────────────────────────────┐
│ ① 公众号模板消息（wxpush / Cloudflare Workers）              │
│    主力 · 无限次 · 能推给别人 · 有原生弹窗与声音              │
│    条件：接收人已绑定（关注过推送号）                          │
├─────────────────────────────────────────────────────────────┤
│ ② 小程序订阅消息（一次性）                                    │
│    辅助 · 有额度就用                                          │
│    条件：接收人有剩余订阅额度                                  │
├─────────────────────────────────────────────────────────────┤
│ ③ 站内消息中心                                               │
│    兜底 · 永不失败 · 所有通知无条件写入                        │
├─────────────────────────────────────────────────────────────┤
│ ④ 首页「今天家里有什么事」                                     │
│    最终底线 · 产品承诺：打开小程序一定看得到                    │
└─────────────────────────────────────────────────────────────┘
```

**降级顺序不可颠倒：先试 ①，失败试 ②，都失败也必须写 ③。**

#### 通道 ①：公众号模板消息（wxpush）

| 维度 | 说明 |
| --- | --- |
| 能力 | **无限次主动推送**，且**能推给别人**——这一条解开了 5.1 的死结 |
| 形态 | 微信服务通知，有原生弹窗 + 声音提醒 |
| 成本 | 0（Cloudflare Workers 免费额度每天 10 万次） |
| 代价 | 依赖微信「公众平台接口测试号」，**产品化前必须拆除** |
| 跳转 | 模板消息 `miniprogram` 字段（待实测）→ 中转页**小程序码长按识别**（主力） |

#### 通道 ②：订阅消息额度累积

`requestSubscribeMessage` 单次最多请求 3 个模板 ID，调用成功则每个模板各 +1 次额度。
在**所有自然交互点**顺手收集授权，而不是单独弹一次授权框：

- 创建派活 / 提醒时（主场景）
- 完成任务后（顺手弹「要不要也提醒你一下？」）
- 进入首页时（若额度不足且今天有待发提醒）

后端用 Redis 维护每个用户的剩余额度计数 `subscribe:quota:{userId}:{templateId}`，
前端在额度 < 2 时展示「再开一次微信提醒，就能多叮几次」的轻提示。

记账时机（代码位置见 `server/src/modules/notify/subscribe-quota.service.ts`）：

| 时机 | 操作 | 谁触发 |
| --- | --- | --- |
| 用户授权成功 | `grant()` **+1** | 前端 `POST /api/auth/subscribe-quota` |
| 下发成功 | `consume()` **-1** | 服务端下发前原子扣减 |
| 下发失败（网络 / 47003） | `refund()` **+1** | 服务端自动退还，不白扣 |
| 微信返回 `43101` | `reset()` **归零** | 说明本地账错了，以微信为准 |

> ⚠️ **待验证假设（A4）：** 「勾选『总是保持以上选择』后每次调用是否真的累积额度」，
> 需要在开发启动前写技术验证 demo 确认。**这是 M0 阶段必须完成的验证项。**
> 即使不成立也不致命——通道 ① 已能独立支撑。

#### 通道 ③：站内消息兜底

额度耗尽或未绑定时**不静默失败**：

```text
① notification_logs 照常写入（channel = 站内消息）
② 首页顶部出现家庭内提示
③ 消息中心（「我的」Tab）承载完整的历史通知，并展示每条的实际发送渠道
```

#### 通道 ④：首页承担主要提醒职责

> **产品承诺的底线不是「一定推送到微信」，而是「打开小程序一定看得到」。**

因此首页的「今天家里有什么事」区块是整个产品的**核心提醒载体**。

### 5.3 需要申请的两套模板

**两套模板并行，用途不同：**

**（A）小程序订阅消息模板** —— 在 `mp.weixin.qq.com` → 功能 → 订阅消息。
**✅ 已申请完毕（2026-10-06），共 3 个**：

| 用途 | 模板标题 | 模板编号 | 环境变量 | 字段（公共模板库定死，不可改） |
| --- | --- | --- | --- | --- |
| 派活通知 | 待办事项提醒 | 2983 | `WX_TEMPLATE_TASK` | `thing1` 事项主题 / `thing4` 事项描述 / `thing22` 提醒对象 / `time23` 提醒时间 |
| 叮一下提醒 | 备忘事项提醒 | 10938 | `WX_TEMPLATE_NUDGE` | `thing3` 备忘事项 / `time10` 事项时间 / `thing6` 相关人员 |
| 完成回执 | 日程任务完成提醒 | 77364 | `WX_TEMPLATE_DONE` | `thing1` 备忘事项 / `thing2` 完成人 / `time3` 完成时间 |

> ⚠️ **字段名由公共模板库定死**（`thing1` / `time23`），与公众号模板的自定义字段
> （`first` / `keyword1`）**完全不是一回事**，排查 47003 时别拿一个通道的字段去对另一个。
>
> ⚠️ 两个硬约束：`thing` 类型**最多 20 个字符**；`time` 类型只认
> `yyyy-MM-dd HH:mm` 或 `yyyy年MM月dd日 HH:mm`。超长或格式不对都报 `47003`，
> 且**不告诉你是哪个字段错了**。
>
> ⚠️ **已知缺口**：`time23` 是必填的 `time` 字段，所以**派活不设时间时订阅消息发不出去**，
> 通道二会自动跳过、降级到站内消息。详见 `docs/未来需求池.md`。

**（B）公众号模板消息模板** —— 在测试号后台「模板消息接口 → 新增测试模板」，**3 个**：

| 用途 | 模板标题 | 环境变量 |
| --- | --- | --- |
| 派活通知 | 待办事项提醒 | `MP_TEMPLATE_TASK` |
| 叮一下提醒 | 备忘事项提醒 | `MP_TEMPLATE_REMINDER` |
| 完成回执 | 日程任务完成提醒 | `MP_TEMPLATE_DONE` |

测试号的模板字段可以**完全自定义**，但字段名必须与后端组装的数据**严格一致**，
否则微信返回 `47003`。三个模板的字段与后台「模板内容」原文见 `docs/08` §10，
也可以直接跑 `cd server && pnpm run check:templates` 打印出可粘贴的原文。

> 部署后先打 `GET /api/health/templates` —— 两条通道的模板配置与字段名一次全查完。

### 5.4 发送状态对用户透明

发起人必须知道「到底叮到了没有」——**这是信任问题，不能含糊**。

| 返回状态 | 含义 | 用户看到 |
| --- | --- | --- |
| `SENT` | 已下发（通道 ① 或 ②） | toast「已经叮到阿妈啦 🔔」 |
| `NO_QUOTA` | 额度不足，已转为站内消息 | toast「已记下，阿妈再开一次微信提醒就能收到」 |
| `NOT_BOUND` | 对方还没绑定微信提醒 | toast「已记下，阿妈还没开微信提醒，她打开小程序就能看到」 |
| `FAILED` | 微信接口报错 | toast「没叮成功，稍后再试」 |

> **状态是三档而不是两档。**「有条件的成功」必须说清楚条件，否则发起人会以为对方已经收到了，反而制造误会。

## 六、图片上传方案

```text
小程序 wx.chooseMedia（限 9 张）
        ↓
本地压缩（wx.compressImage，质量 80，最长边 1600）
        ↓
wx.uploadFile → 后端 POST /api/upload
        ↓
后端校验（类型白名单 + 大小 ≤ 5MB + 内容安全检测）
        ↓
上传至云存储 / COS，返回可访问 URL
        ↓
小程序拿到 URL 后随记录一起提交
```

**内容安全**：图片必须调 `imgSecCheck`，文字必须调 `msgSecCheck`。这是小程序审核的硬性要求，留个念模块绕不开。

## 九、风险清单与应对

| # | 风险 | 影响 | 应对 |
| --- | --- | --- | --- |
| 1 | 消息送不到用户 | **高**（核心功能失效） | 四通道降级（第五章）；首页「今天家里有什么事」承担最终底线 |
| 2 | 长期订阅资质拿不到 | 高 | 已确认走一次性订阅路线，产品设计上不依赖长期订阅 |
| 3 | **wxpush 依赖测试号，上架前必须拆除** | 中 | 代码层用通道开关隔离（`NOTIFY_MP_ENABLED`），拆除时只关配置不改业务，见 `docs/08` 第十四章 |
| 4 | **测试号被微信回收 / 用户数上限** | 中 | Worker 保活心跳（`ALIVE_DAYS`）；站内消息兜底；家人规模远低于上限 |
| 5 | **用户不愿关注测试号** | 中 | 不做强制；未绑定用户自动降级为站内消息，产品依然完整可用 |
| 6 | 小程序类目审核（家庭/生活服务） | 中 | 提前准备类目材料，见《06 上线前环境准备清单》 |
| 7 | 图片内容安全检测不通过 | 中 | 上传即检测，不通过直接拒绝并提示 |
| 8 | 云托管冷启动 / 缩容到 0 | 中 | 关闭缩容到 0，保留最小实例数 1 |
| 9 | 定时任务漏发 | 中 | `notification_logs` 全量记录 + 每日补偿任务扫描未发送记录 |
| 10 | 成员称谓歧义（两个人都叫「阿妈」） | 低 | 创建/加入家庭时校验家庭内称谓唯一，冲突时提示 |
| 11 | 时间时区错乱 | 中 | 存储用 UTC、接口层统一格式化北京时间，见 4.3 |
