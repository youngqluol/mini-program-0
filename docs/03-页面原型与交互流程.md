① **P03 补六条交互细节**（分组只切不重排、「加载更多」要合并边界那一天、

**v0.2.8 变更：** P02 / P17 按实现落定 ——
① P02 的确认层是**页面自绘的底部面板**，不是 `wx.showActionSheet`
（后者最多 6 项，家里人多就选不全）；抬头只列菜名，**不写「今晚吃：…」**，
那句话由后端 `POST /menu/decide` 的 `summary` 给，前端原样透出；
自己的那一项显示成「我自己来」；`mealType` 按当前时刻推断；派活后**不自动跳详情**。
② P17 补五条：自带菜谱不给开关也不给左滑、「停用」不叫「删除」、
停用后仍留在列表里、添加与编辑共用一个表单面板、Switch 是乐观更新。
**v0.2.7 勘误：** P21 微信提醒按实现重写三处 ——
① 草图里的「**绑定好了**会自动跳回来」**自己带了禁用词**（AGENTS.md §6 的机制词表里有
「绑定」），改成「开好了，这里会自动变过来」；
② **删掉「重新绑定」那一行** —— 绑定关系挂在**用户**身上，换一个微信号就是换一个人，
这一行没有真实语义（挂一个点不出结果的入口，比不挂更糟）；
③ 补上二维码的**来源与身份说明**：这一页要的是**公众号二维码**，
不是**小程序码** —— 两者扫出来的结果完全不同，而 wxpush Worker 的
`MP_QRCODE_URL` 要的才是小程序码（中转页用），**两者不可互换**。
另：P20 的「微信提醒」那一行随本页一起加上了。

**v0.2.6 勘误：** P20「我的」按实现补六条约定，并**划掉三样本轮不露出的东西** ——
① **微信提醒那一行**（要跳 P21，而 P21 还没做）、② **隐私政策**、③ **注销账号**。
后两样是**上线前**的事（`docs/06` §4.6 / §264），①随 M2-F1 一起加。
共同的理由：**挂一个点了没反应的入口，比暂时不挂更糟**（和首页 M2-F3 同一个道理）。
另外**未读角标**这一条从「归 P20」落实成了具体做法（`onShow` 里 `setTabBarBadge`），
并明确 **0 条时要显式 `removeTabBarBadge`**。

**v0.2.5 勘误：** P12 消息中心按实现重写 ——
① 条目由「类型名 / 内容 / 时间」三行压成**两行**（类型只用 emoji 表达，
`title` 已经是一句带事项名的话，再挂一个「叮一下」标签是重复）；
② **未读改成「标题加粗 + 右侧小点」这种加法**，不再设想「已读置灰」——
消息列表里已读的是大多数，让大多数条目发灰会让页面看起来像坏了；
③ **删掉「条目可展开查看实际发送渠道（公众号提醒 / 订阅消息 / 仅站内）」**：
那三个词全是 AGENTS.md §6 的用户界面禁用词。改成一行只在「没推到微信」时
出现的轻标签，文案与判据见 `docs/02 §9.1`；
④ 未读数角标明确归 **P20**（角标该在「我的」Tab 的 `onShow` 里刷新）。

**v0.2.3 勘误：** P10 小事详情的操作区由**左右并排**改为**上下两行**，
并把「主操作槽位」的语义写清（放的是「此刻这个人真能做的动作」，
不是固定按钮）。原因：并排时长文案（「已完成 · 18:05 由阿爸完成」）
会和按钮抢宽度，且破坏性动作紧挨主按钮容易误点。同时补两条实现约定 ——
后端的「创建者也能完成 / 取消」兜底**不露出**；提醒行带的称谓按 V0.1 的
实际行为（执行人）说明。

**v0.2.2 勘误：** P08 / P09 的重复选项由「不重复 / 每天 / 每周」改为
**「不重复 / 每周 / 每月」** —— 原稿与 PRD §6.3 直接矛盾：那里明确把「每天」
划到 V0.2（一年 365 次，订阅额度撑不住；且高频重复实质上接近「自动催办」，
与「少打扰」原则冲突），同时 V0.1 是**支持每月**的。另补两处实现约定：
重复的周几 / 几号由「什么时候」推出，不单独再问一遍；P09 的「重复」与
「叮一下」在未定时间时一起置灰。

## 一、信息架构

> **v0.2 变更：** 底部导航由 3 个 Tab 扩展为 **4 个**，新增「👤 我的」。
> 原先挂在首页右上角的「家庭」入口整体搬进「我的」，为 V0.2 的「切换家庭」预留位置。
> 本节已与《产品需求文档》5.1 / 5.3 对齐。

```text
家有小事
│
├── 启动 / 登录（非 Tab）
│   ├── 授权登录页
│   ├── 创建家庭
│   ├── 加入家庭
│   └── 填写家庭称谓
│
├── 🏠 家里（Tab 1）
│   ├── 首页
│   ├── 叮一下（创建提醒）
│   ├── 派活（创建任务）
│   ├── 小事详情
│   └── 我的小事
│
├── 🍽️ 吃啥呢（Tab 2）
│   ├── 决定页（卡片）
│   ├── 菜谱列表
│   └── 菜谱管理
│
├── 📖 留个念（Tab 3）
│   ├── 家庭时间线
│   ├── 发布记录
│   └── 记录详情
│
└── 👤 我的（Tab 4）
    ├── 家庭信息
    ├── 家庭成员
    ├── 邀请成员
    ├── 家庭设置
    ├── 消息中心
    ├── 微信提醒（绑定 / 解绑）
    ├── 隐私政策
    └── 注销账号 / 退出家庭
```

**底部导航 4 个 Tab：家里 / 吃啥呢 / 留个念 / 我的。**
「叮一下」和「派活」是**动作**，不是内容频道，作为首页的悬浮高频入口存在。
**「消息中心」也从首页铃铛移入「我的」**——首页只负责「今天家里有什么事」，不再承担通知归档。

## 三、页面详细设计

### P01 首页 `pages/index/index`

**设计目标：** 打开之后，马上知道今天家里有什么事。

```text
┌──────────────────────────────┐
│ 我们家 👨‍👩‍👧                     │  ← 纯展示当前家庭上下文，不可点击
│ 9月28日 周一 · 今天家里有什么小事？│     （家庭管理入口已移至「我的」Tab）
├──────────────────────────────┤
│                              │
│   ┌──────────┐ ┌──────────┐  │
│   │  🔔      │ │  🎯      │  │  ← 两个高频动作入口（大按钮）
│   │ 叮一下   │ │ 派个活   │  │
│   └──────────┘ └──────────┘  │
│                              │
├──────────────────────────────┤
│  今天的提醒              更多 ›│
│                              │
│  17:30  接宝宝      阿妈      │
│  18:00  拿快递      阿爸  ✓   │
│                              │
├──────────────────────────────┤
│  最近的活                更多 ›│
│                              │
│  🛒 买菜          阿妈  待完成 │
│  🚗 洗车          阿爸  待完成 │
│                              │
├──────────────────────────────┤
│  ┌────────────────────────┐  │
│  │      🍽️  吃啥呢         │  │  ← 单行卡片，点击进 Tab2
│  │      今天吃什么？        │  │
│  └────────────────────────┘  │
├──────────────────────────────┤
│  ┌────────────────────────┐  │
│  │  📖 留个念              │  │  ← 最新一条记录预览
│  │  宝宝今天第一次自己穿鞋   │  │
│  └────────────────────────┘  │
└──────────────────────────────┘
│ 🏠 家里 │ 🍽️ 吃啥呢 │ 📖 留个念 │ 👤 我的②│
└──────────────────────────────┘
```

**元素与交互：**

| 元素 | 交互 | 跳转 |
| --- | --- | --- |
| 家庭名 | **不可点击**，仅作上下文提示 | — |
| 🔔 叮一下 | 点击 | → P08 叮一下创建页 |
| 🎯 派个活 | 点击 | → P09 派活创建页 |
| 今日提醒条目 | 点击 | → P10 小事详情 |
| 提醒条目右侧 ✓ | 点击 | 直接完成，卡片就地置灰后重拉 |
| 「今天的提醒」更多 | 点击 | → P11 我的小事 `?tab=ASSIGNED_TO_ME` |
| 「最近的活」更多 | 点击 | → P11 我的小事 `?tab=MINE` |
| 吃啥呢卡片 | 点击 | 切换 Tab 到 P02 |
| 留个念卡片 | 点击 | 切换 Tab 到 P03 |

**状态：**

| 状态 | 表现 |
| --- | --- |
| 加载中 | 两块**骨架屏**（灰块呼吸），不用转圈 |
| 今天一件小事都没有 | 一张空状态卡：「今天还没有小事 / 要不要先叮一下阿妈？」 |
| 下拉刷新 | 支持（`enablePullDownRefresh`） |

> **v0.2.4 实现约定（P01 落地时确定）：**
>
> 1. **区块标题不用 emoji。** 上面的草图里写了 🔔 / 🎯，但那是**速记**，不是设计 ——
>    `docs/07` 与 `app.wxss` 的 `.section-title` 约定「粉色小竖条，不用 emoji」。
>    卡片自己已经有类型 emoji 了。
> 2. **`stats.overdue`（过期未完成数）刻意不显示。** 「今天有 2 件事已经过了时间」
>    是一句催办话（AGENTS.md §6 禁用词里有「逾期」）。单条小事上那个变红的时间是
>    **信息**，聚合成一个数字挂出来就变成**监督**了。
> 3. **列表行直接躺在页面背景上，不套白卡片。** `thing-card` 自身就是白底圆角，
>    再套一层白卡片就分不出行与行的界线了（与 P11 同款 `.rows / .row` 结构）。
> 4. **用 `onShow` 取数**（不是 `onLoad`）：从 P08 / P09 / P10 返回时必须刷新。
> 5. **「未开微信提醒」提示条（M2-F3）本轮不做。** 它要求出现在「**别人**没开微信提醒」时，
>    但 `GET /notify/mp-bind/status` 只回**我自己**的状态，后端没有「家庭成员谁开了」的接口 ——
>    这个条件现在算不出来；且它要跳 P21（M2-F1），那一页也还没做。见 `docs/未来需求池.md`。
> 6. **「留个念」卡片的副标题是最新一条记录**（M4-11）—— 只取一条
>    （`limit=1`），拉不到时**保持**上一次的文案、不清空（副标题闪一下
>    比显示旧内容更糟），失败也**不弹 toast**（一个副标题不值得打扰用户）。
>    没有记录时显示「还没有记录」。

> **v0.2 变更：** 首页**不再有铃铛和家庭入口**。
> - 消息中心 → 移入「我的」Tab（P12）
> - 家庭信息 → 移入「我的」Tab（P13）
> - 未读通知数 → 以角标形式挂在底部「我的」Tab 上
>
> 理由：符合小程序用户习惯（设置类内容都在「我的」），并为 V0.2 的「切换家庭」预留了天然位置。
> **首页只做一件事：回答「今天家里有什么事」。**

**接口：** `GET /family-things/today` + `GET /notifications/unread-count`（合并成一次，或并行）

**状态：**

- **加载中**：骨架屏（灰色占位块），不用转圈
- **空状态（新家庭）**：两个大按钮下方出现引导
  ```text
  📭 今天还没有小事
  要不要先叮一下阿妈？
  ```
- **有人没开微信提醒**：顶部出现一条轻提示条（仅在**自己是发起人**且对方未绑定时出现）
  ```text
  ⚠️ 阿妈还没开微信提醒，她打开小程序才能看到。去帮她开一下 →
  ```
  > 点击 → P21 微信提醒页。注意文案**不能是催办语气**，只陈述事实 + 给一个轻量出口。
- **订阅额度不足**（辅助通道）：若订阅消息是当前唯一可用通道且额度 < 2
  ```text
  ⚠️ 提醒快用完了，点一下补上 →
  ```
- **下拉刷新**：重新拉取今日数据

### P08 叮一下 `pages/nudge/create`

**设计目标：** 3 步内完成，尽量少的输入。

```text
┌──────────────────────────────┐
│  ←  叮一下                    │
├──────────────────────────────┤
│  叮谁？                       │
│  ┌────┐ ┌────┐ ┌────┐        │
│  │阿妈│ │阿爸│ │阿公│        │  ← 头像 + 称谓，单选
│  └────┘ └────┘ └────┘        │
│                              │
│  叮什么？                     │
│  ┌────────────────────────┐  │
│  │ 明天记得给宝宝带水杯     │  │  ← 大输入框，自动聚焦
│  └────────────────────────┘  │
│  常用：带水杯 / 拿快递 / 交费  │  ← 快捷短语（历史记录生成）
│                              │
│  什么时候叮？                 │
│  ⚪ 现在就叮                  │
│  ⚫ 定时叮                    │
│     明天 07:00        修改 >  │
│                              │
│  要不要重复？                 │
│  ⚪ 不重复  ⚪ 每周  ⚪ 每月   │
│  每周六 09:00                 │  ← 周几由「什么时候」推出，只读回显
│                              │
├──────────────────────────────┤
│        [  叮 一 下  ]         │
└──────────────────────────────┘
```

**交互细节：**

1. 进入页面**自动聚焦输入框**，直接弹键盘（减少一次点击）

### P10 小事详情 `pages/thing/detail`

```text
┌──────────────────────────────┐
│  ←                           │
├──────────────────────────────┤
│                              │
│  🎯 派活                      │
│                              │
│  买牛奶                       │
│                              │
│  阿妈 → 阿爸                  │
│  明天 18:00 前完成             │
│                              │
│  🔔 17:30 提醒阿爸             │
│                              │
│  备注                         │
│  楼下超市，买两盒              │
│                              │
│  谁能看见：家里人都能看到      │
│                              │
├──────────────────────────────┤
│  [     搞定啦 ✓      ]        │  ← 主操作，满宽
│  [      取消这件事     ]       │  ← 次操作，另起一行
└──────────────────────────────┘
```

**交互细节：**

- 主操作槽位只有一格，**放的是「此刻这个人真能做的那个动作」**，不是固定的按钮：
  - 待完成 + 我是执行人 → 「搞定啦 ✓」→ `POST /family-things/{id}/complete`
  - 待完成 + 我只是旁观者 → **置灰的状态条**「待完成」（不给按不动的按钮）
  - 已完成 / 已取消 → 状态条：`已完成 · 18:05 由阿爸完成` / `已取消 · 昨天 12:00`，
    并播放一个轻量对勾弹出动画
- 次操作另起一行，且**只有我派的才有**：
  - 待完成 → 「取消这件事」，走**底部操作表**二次确认
    （`历史记录会保留，随时能重新打开`）
  - 已完成 / 已取消 → 「重新打开」，不二次确认（可逆、低风险）
- 每个动作之后**整页重拉**：完成一件小事会连带取消它下面所有未发出的提醒，
  只改本地状态会让「🔔 17:30 提醒阿爸」留在一件已经做完的事上
- 成功后**不弹「搞定啦」**——状态条已经说了。只有「顺手生成了下一次」
  （重复小事）才补一句 toast
- **已完成时，状态条下方出现一行极淡的「📖 记个念 →」**（M4-12，PRD §19.2）。
  点它进 P18，并把 `thingId` 与标题带过去（正文预填「买牛奶 搞定啦」）。
  ⚠️ 它是**安静的次要文字入口**，不是按钮：不弹窗、不提示、不打断。
  一旦主动问「要不要留个念？」，产品就从「家庭时间线」滑向「任务日志」
  （PRD §19.4）。只有 `status=COMPLETED` 才显示 —— 取消态不给。

**两条实现约定：**

1. **后端的「家庭创建者也能完成 / 取消」不露出。** 服务端允许创建者替别人收尾，
   那是防止一件事因执行人退出家庭而永远卡住的**数据阀门**，不是产品要主推的动作
   （「只提醒，不监督」）。所以界面只认「我是执行人 / 我是发起人」两种关系。
2. **提醒那一行带的是执行人的称谓**（「提醒阿爸」）。V0.1 成立：P08 / P09 创建
   提醒时都不传接收人，后端默认取执行人。哪天做了「提醒别人」的入口，
   这一行必须跟着改。

### P11 我的小事 `pages/thing/mine`

```text
┌──────────────────────────────┐
│  ←  我的小事                  │
├──────────────────────────────┤
│  [派给我的] [我派的] [都完成] │  ← 顶部筛选 Tab
│  待完成 ▾                     │  ← 状态筛子（第三个 Tab 不显示）
├──────────────────────────────┤
│  ☐ 买菜        阿妈  今天18:00 │
│  ☐ 洗车        阿爸  周六      │
│  ✓ 拿快递      阿爸  昨天      │  ← 已完成置灰
└──────────────────────────────┘
```

**三个 Tab 的组合**（不是三个并列的筛子，而是三个问题）：

| Tab | `scope` | `status` | 在问什么 |
| --- | --- | --- | --- |
| 派给我的 | `ASSIGNED_TO_ME` | 待完成（可切「全部」） | 我手上还有什么 |
| 我派的 | `MINE` | 待完成（可切「全部」） | 我托出去的事办得怎么样了 |
| 都完成 | `ALL` | `COMPLETED`（锁死） | 那些已经办完的，翻一翻 |

- 前两个 Tab 底下给「待完成 / 全部」筛子：派出去的活，「全部」才看得到自己派过什么；
  只给「待完成」会让人以为派完就没了。第三个 Tab 已锁死状态，不显示筛子。
- 上拉加载更多（`page` 分页，每页 20）

**左滑操作（随身份变化）：**

| 条目状态 | 我是执行人 | 我是发起人 | 与我无关 |
| --- | --- | --- | --- |
| 待完成 | 搞定啦 | 取消 | **不可滑** |
| 已完成 / 已取消 | — | 重新打开 | **不可滑** |

- 「不可滑」是真的**不响应手势**，不是滑开一个空抽屉 —— 一行没有任何能做的事时，
  滑开空抽屉比滑不动更让人困惑。
- 「取消」是破坏性操作，单独染色并走底部操作表二次确认。
- 同一时刻只允许滑开一行；点开着的卡片 = 先收回去，不跳详情。

**入口：** P01 首页两个区块的「更多 ›」都跳这一页，用 `?tab=` 决定落在哪个 Tab
（提醒 → `ASSIGNED_TO_ME`；派活 → `MINE`）。参数不认识就退回第一个 Tab。

**空状态：** 每个 Tab 一句自己的话（「手上没有活儿」「你还没派过活」「还没有办完的事」）——
说清楚「为什么这里是空的」，而不是统一一句「暂无数据」。

> **v0.2.4 实现约定：**
>
> 1. **用 `onShow` 拉第一页**，不用 `onLoad` —— 从 P10 详情页返回时列表必须刷新。
>    代价：已经上拉三页的，回来会收回到第一页。数据正确优先于位置保留。
> 2. **必须防「过期响应」。** 快速连点两个 Tab 时先发的那次可能后到，
>    结果就是「Tab 高亮着『都完成』，列表里却是『派给我的』」，而且不报错。
>    每次请求记下自己的筛选条件，响应回来对不上就丢弃。
> 3. **每个动作之后整页重拉**，不就地打补丁 —— 完成一件小事会连带取消它下面
>    所有未发出的提醒，只有重拉才看得到这个连带结果。
> 4. 左滑的**权限判断在 `utils/thing-view.ts` 的 `buildThingRowView()` 里算**，
>    页面不判。与 P10 详情页同一套规则，算错的后果很具体 —— 点一下就是一次 403。
>    后端还允许**家庭创建者**越过身份操作（数据阀门），界面上同样刻意不露出。

### P18 发布记录 `pages/memory/create`

```text
┌──────────────────────────────┐
│  ←  留个念         [ 发布 ]   │
├──────────────────────────────┤
│  来自 🎯 买牛奶               │  ← 只有「完成纪念」才有这一行
│  ┌────────────────────────┐  │
│  │ 买牛奶 搞定啦            │  │  ← 预填，可改
│  │                        │  │
│  └────────────────────────┘  │
│                              │
│  ┌────┐┌────┐┌────┐         │
│  │ 68%││img ││ ↻  │         │  ← 上传进度 / 失败重试
│  └────┘└────┘└────┘         │
│  ┌────┐                      │
│  │ +  │                      │  ← 最多 9 张
│  └────┘                      │
│                              │
│  谁能看见？                   │
│  ⚫ 家里人都能看到  ⚪ 只有我   │
│  ┌──────────┐ ┌───────────┐  │
│  │   取消    │ │   发布     │  │
│  └──────────┘ └───────────┘  │
└──────────────────────────────┘
```

**六条交互细节：**

1. **选图就上传，不等「发布」。** 用户选完图到按下发布之间可能过很久，
   那时才上传会让「发布」按钮转很久，而且失败要等到最后才知道。
   代价是「选了又删」会浪费一次上传 —— 家庭场景下这点浪费换体验值得。

2. **`sizeType: ['compressed']` 不是为了省流量，是为了过内容安全。**
   微信的图片检测接口（`img_sec_check`）有 **1MB 上限**，原图动辄 3–5MB
   根本检不了、只能 fail-open 放行。压缩后通常 100–500KB，落在限制内。

3. **上传失败的图留在九宫格里，点一下重试**（缩略图上盖一层红色「↻ 重试」）。
   悄悄消失会让用户以为「选上了」，发布后才发现少一张。

4. **有图在上传中时禁止发布**，否则会发出一条少图或空图的记录，
   而用户以为都传上去了。文案是「图片还在传，稍等一下」。

5. **发布按钮在还不能发时置灰，但仍然可点** —— 点了会 toast 说清原因
   （「写点什么，或者加张图片吧」）。比「点了没反应」好。

6. **「完成纪念」的关联靠 URL 参数带过来**（`?thingId=…&thingTitle=…`），
   不为它多发一次请求 —— P10 手里本来就有这两个值。
   正文预填（`买牛奶 搞定啦`）**可改**：它只是省一次打字，不是固定格式。
   ⚠️ 标题要 `encodeURIComponent`：活名里可能有 `&`、`#`、空格，
   不编码会把 URL 拆坏（`?thingTitle=买&牛奶` → 后半截丢了）。

- 发布中禁用按钮（防重复提交），成功后 toast 再返回 P03
- 可见范围两个选项各带一行小字解释（「阿爸、阿妈他们都能翻到这条」），
  让用户不用猜「家里人都能看到」包不包括自己
- 正文上限 1000 字（`maxlength`，与后端同一个镜像常量）

>    ⚠️ 这条依赖后端 —— 原实现把 `title` 写死成「提醒你一下」这种泛化短语，
>    20 条通知在列表里长得一模一样。已修 `notify.templates.ts`。
> 2. **未读不做「已读置灰」。** `thing-card` 那种「已完成整条 opacity .55」是对的
>    （少数、语义明确），但消息列表里已读的是**大多数** —— 让大多数条目发灰，
>    页面会看起来像坏了。改用「未读加粗 + 小点」这种**加法**。
> 3. **送达说明只在「没推到微信」时才显示。** 推到微信的不显示 —— 微信已经响过了，
>    再说一句「已发到微信」是废话。只在用户会疑惑的场景（「怎么没响？」）给答案。
>    文案与判据见 `docs/02 §9.1` 的表。
> 4. **「全部已读」之后就地把本地状态改成已读，不整页重拉。** 项目常规纪律是
>    「动作之后重拉」（完成一件小事会连带取消它下面所有提醒），但已读**没有任何
>    连带副作用**，重拉只会让列表闪一下、还可能把刚上拉出来的第三页收回第一页。
> 5. **点开一条不会把它变成已读。** 后端没有「单条已读」接口（docs/02 §9 只有
>    `read-all`），本地置灰只会让用户下次进来发现「怎么又未读了」。宁可如实显示 ——
>    缺口见 `docs/未来需求池.md`。
> 6. **不做「条目展开看渠道」。** 原稿写的是「条目可展开查看实际发送渠道
>    （公众号提醒 / 订阅消息 / 仅站内）」—— 那三个词**全是用户界面禁用词**
>    （AGENTS.md §6 的机制词表里有「公众号」「订阅」「模板消息」）。
>    改成一行轻标签，且只在异常路径出现。

**交互流程：**

```text
进入页面
   ↓
GET /notify/mp-bind/status
   ├─ bound = true  → 展示「已开启」
   └─ bound = false ↓
   手里还有没过期的数字？
     ├─ 有 → 直接展示（**不重新生成**）
     └─ 没有 → POST /notify/mp-bind/code（6 位数字，TTL 10 分钟）
   ↓
展示二维码 + 数字
   ↓
每 3 秒轮询一次 GET /notify/mp-bind/status（最多 20 次 = 1 分钟）
   ├─ 检测到 bound = true → 切「已经开启啦」
   └─ 1 分钟没等到 → 「还没收到哦，重新获取一个数字试试」+ [ 重新获取 ]
```

**文案纪律（重要）：**

| 场景 | 文案 |
| --- | --- |
| 标题 | 「微信提醒」——**不叫「绑定公众号」**，用户不关心技术名词 |
| 价值说明 | 「开启后，家里有事会直接弹到你的微信里」 |
| 未开启提示 | 「还没开」——**不是「未绑定」** |
| 那串数字 | 「把这串数字发给它」——**不叫「绑定码」** |
| 成功 | 「已经开启啦」 |
| 失败 | 「还没收到哦，重新获取一个数字试试」 |

**❌ 禁止出现：** 绑定、授权、公众号、openid、订阅、模板消息、测试号。

> **v0.2.7 实现约定（P21 落地时确定）：**
>
> 1. **二维码是「公众号二维码」，不是「小程序码」。** 两者长得有点像，
>    扫出来的结果完全不同：前者是关注那个号（P21 要的就是它），后者是打开小程序
>    （对这条流程没有任何帮助，会走进死路）。**怎么分辨：小程序码右下角有绿色小程序角标。**
>    ⚠️ 顺带记一笔：wxpush Worker 的 `MP_QRCODE_URL` 要的**才是小程序码**
>    （用在「中转页」让用户长按识别跳回小程序）—— **两者不可互换**，
>    这是本项目第二对「看起来一样、其实不能换」的东西（第一对是两套模板体系）。
>    📦 两张图已各归其位：公众号二维码 → `miniprogram/assets/mp-account-qr.jpg`
>    （就是这一页要的）；小程序码 → `wxpush/assets/miniprogram-code.png`（中转页用）。
>    ⚠️ **扩展名是常量的一部分**（`config.ts` 的 `MP_ACCOUNT_QR` 里写着 `.jpg`），
>    换格式要连常量一起改 —— 否则小程序找不到文件会**静默**降级成一句文字说明。
> 2. **图片加载失败要降级，不显示破图。** `<image binderror>` → 退回一句
>    「在微信里关注我们的推送号」。**少一个便利，好过给一张错的图。**
> 3. **只在「还没开、手里又没有还没过期的数字」时才生成新数字。**
>    `POST /notify/mp-bind/code` 会**换掉**正在展示的那一串，而用户此刻可能
>    正拿着它在微信里打字 —— 一进页面就换码会把他的操作作废。
>    所以 `onShow` 只重新**查**状态，不碰数字。
> 4. **轮询用「查一次、再排下一次」，不用 `setInterval`。** 查询本身是异步的，
>    固定间隔会在网络慢的时候叠起好几个并发请求，而且停不掉正在飞的那一个。
> 5. **`onHide` / `onUnload` 必须停轮询。** 不停的话，用户切走后定时器还在跑，
>    1 分钟后会 `setData` 到一个已经不可见的页面，期间还每 3 秒白打一次接口。
> 6. **不做「重新绑定」。** 绑定关系挂在**用户**身上，换一个微信号就是换一个人，
>    这一行没有真实语义。挂一个点不出结果的入口，比不挂更糟。
> 7. **六位数字按 3+3 分组显示（「735 241」）。** 用户要做的事是
>    **看着屏幕、在微信里把这串数字打出来** —— 一长串连读容易念错，也容易看串行。
> 8. **数字只有 10 分钟寿命，所以 `describeExpire()` 补了「分钟」档。**
>    原来只有小时 / 天两档，10 分钟会说成「1 小时内过期」，等于没说。

**兜底：** 用户始终可以只靠「打开小程序看首页」使用全部功能。
**这个页面不开启，产品依然完整可用**——它只是让提醒更及时。

> 完整技术方案见 `docs/08-wxpush推送集成方案.md`。

## 四、核心业务流程

### 4.1 主链路：吃啥呢 → 派活 → 叮一下 → 完成 → 留个念

```text
① 阿妈打开「吃啥呢」
        ↓
② 点「换一个」转几次，看到「番茄炒蛋 + 炒青菜」
        ↓
③ 点「就吃这个」
        ↓
④ 弹出：派给阿妈 / 派给阿爸 / 不用派
        ↓
⑤ 选「派给阿爸」
        ↓
⑥ POST /menu/decide-and-assign
   ├─ 写入 meal_records（今天晚餐吃什么）
   └─ 创建 family_things（type=TASK，title=今晚做饭：番茄炒蛋、炒青菜）
        ↓
⑦ 阿爸收到微信提醒「🎯 阿妈派了个活给你：今晚做饭」
        ↓
⑧ 阿爸点开 → 小事详情 → 点「搞定啦」
        ↓
⑨ 阿妈收到「❤️ 阿爸已经把「今晚做饭」搞定啦」
        ↓
⑩ 第二天，阿妈在「留个念」发一条：昨晚的番茄炒蛋，宝宝吃了两碗饭
```

### 4.2 新用户首次进入

```text
启动
  ↓
有 token？
  ├─ 否 → wx.login → POST /auth/login
  └─ 是 → 校验有效期
  ↓
families 为空？
  ├─ 是 → 进入引导页
  │        ┌──────────────────────┐
  │        │  家有小事，不必放心上  │
  │        │                      │
  │        │ [ 创建一个家 ]        │
  │        │ [ 加入家人的家 ]      │
  │        └──────────────────────┘
  │              ↓
  │        创建 → 填家庭名 + 我的称谓
  │        加入 → 输邀请码 → 预览家庭 → 填称谓
  │              ↓
  └─ 否 → 进入首页（默认第一个家庭）
```

### 4.3 叮一下的送达链路（四通道降级）

> **v0.2.1 变更：** 不再是「先查订阅额度」，而是**先看对方有没有开微信提醒**。
> 完整方案见 `docs/08-wxpush推送集成方案.md`。

```text
阿妈点「叮一下」
        ↓
POST /reminders/nudge
        ↓
后端按优先级依次尝试：

① 阿爸绑定了微信提醒？
   ├─ 是 → 发公众号模板消息
   │        ├─ 成功     → SENT      「已经叮到阿爸啦 🔔」
   │        └─ 已取关   → 清 openid → 降级 ↓
   └─ 否 ↓

② 阿爸有订阅消息额度？
   ├─ 是 → 发订阅消息
   │        └─ 成功     → SENT
   └─ 否 ↓

③ 写入站内消息中心（永不失败）
   ├─ 阿爸没开微信提醒 → NOT_BOUND「已记下，阿爸还没开微信提醒，他打开小程序就能看到」
   └─ 只是没额度       → NO_QUOTA 「已记下，阿爸再开一次微信提醒就能收到」

无论走哪条，notification_logs 都完整记录（含实际渠道与失败原因）
```

**给发起人的反馈只有三档，但必须说清楚是哪一档：**

| 结果 | 含义 | 发起人看到 |
| --- | --- | --- |
| `SENT` | 已经发到对方微信了 | 「已经叮到阿爸啦 🔔」 |
| `NOT_BOUND` / `NO_QUOTA` | 微信没发出去，但对方打开小程序能看到 | 「已记下，阿爸还没开微信提醒，他打开小程序就能看到」 |
| `FAILED` | 真的失败了 | 「没叮成功，稍后再试」 |

> ⚠️ **「有条件的成功」必须讲清楚条件。** 如果含糊地说「已发送」，发起人会以为对方已经看到了，
> 反而制造误会——这比直接说失败更糟。

## 五、通用状态设计

| 状态 | 处理方式 |
| --- | --- |
| 加载中 | 骨架屏（内容区灰色块），不用全屏 loading |
| 首次空 | 插画 + 一句有人情味的话 + 一个明确按钮 |
| 网络错误 | 顶部轻提示条 + 「重试」按钮，不弹模态框 |
| 无权限 | toast 提示后返回上一页 |
| 提交中 | 按钮置 disabled + 文案变「派出去了…」 |
| 长列表 | 上拉加载，底部「没有更多了」 |
| **对方未开微信提醒** | 顶部轻提示条（**只陈述事实，不催办**）+ 一个轻量出口 → P21 |
| **订阅额度不足** | 顶部轻提示条 +「去授权」；仅在订阅消息是唯一可用通道时出现 |
| **本人未开微信提醒** | 不主动打扰。仅在「我的」Tab 的对应行用 `--warning` 色标识 |

### 5.1 通知状态的可见性（v0.2.1 新增）

「消息中心」的每条通知都带上**实际发送渠道**，避免用户猜：

| 渠道 | 展示 | 含义 |
| --- | --- | --- |
| 公众号提醒 | 灰色小字「已推送到微信」 | 走通道 ①，对方微信收到了 |
| 订阅消息 | 灰色小字「已推送」 | 走通道 ② |
| 仅站内 | 灰色小字「对方打开小程序可见」 | 走通道 ③，微信没推出去 |

> 这不是给用户看的「技术信息」，而是**信任信息**——发起人需要知道「到底叮到了没有」（PRD 6.5.6）。

## 六、文案规范（重要）

产品原则里写明「有人情味」，所以文案必须统一：

| 场景 | ❌ 不要这样写 | ✅ 要这样写 |
| --- | --- | --- |
| 派活成功 | 任务创建成功 | 已经把活派给阿妈啦～ |
| 完成 | 任务状态已变更 | 搞定啦 ✓ |
| 完成通知 | 任务执行完成 | ❤️ 阿爸已经把「买牛奶」搞定啦 |
| 空列表 | 暂无数据 | 今天还没有小事，要不要先叮一下？ |
| 提醒 | 您有一项待办 | 🔔 阿妈喊你拿快递 |
| 出错 | 系统异常 | 出了点小问题，再试一次 |
| 加入家庭 | 操作成功 | 欢迎回家 👨‍👩‍👧 |
| 退出家庭 | 确认退出？ | 要离开「我们家」吗？以前的记录都会留着 |

**绝对禁止出现的词：** 任务逾期、超时未完成、待办事项、审批、流程、KPI、催办、监督、绩效。
